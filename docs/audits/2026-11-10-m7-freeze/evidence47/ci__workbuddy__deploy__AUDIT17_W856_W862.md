## 1 P0

### P0-1 「每 token 的 dense GEMV」两轮都算错，且互相矛盾

**W861 §3（`:65`、`:87`）**：

```
取 IQ4_XS 变体：单层 0.2655 ms ⇒ 48 层 = 12.74 ms + head 0.92 = 13.66 ms，占 23 ms 的 59%
```

**W862 §6**：

```
每 token 的 dense GEMV（48 层，按 6 列摊）：3.46 ms  ⇒ 占 21.8 ms/token 的 15.9%
```

两边用的都是 `q8_gemv_bench` 的 **9 个矩阵之和（106.54 MB/层）**，再乘 48。这个口径有三处没核：

1. **每层不是 9 个矩阵**。GGUF 元数据：`block_count=48`、`full_attention_interval=4`
   ⇒ **36 GDN 层 + 12 QSA 层**。qkv / gate / out 只在 GDN 层有，q / k / v 只在 QSA 层有。
2. **HC 的 Q8_0 实际远大于 bench 的假设**。生产日志逐字：
   `strata: STRATA_HC_Q8=1: 0.63 GiB of Q8_0 hyper-connection projections for the verify read`
   ⇒ **676 MB**；而 bench 里 `HC down 3.48 + HC up 3.48 = 6.96 MB/层 × 48 = 334 MB`，**少了一半**。
3. **token embedding 644 MiB 在 mapped host memory**（日志逐字 `token embedding Q8_0 in mapped host memory (644 MiB, 2.0 s)`），
   走的是 PCIe 而不是 HBM —— 它跟 `head` 是不是同一份、每 token 读不读，两轮都没查。

**除数也错了**：W861 除的是「每窗口接受 token 数（2.36）」，W862 除的是「列数（6）」。同一次测量，
两种除数差 **2.54 倍**。W862 的 `3.46 ms` 因此偏低约 2.5 倍；W861 的 `12.7 ms` 则因为 106.5 MB/层 高估而偏高。

⇒ **结论**：`R22`（PROGRESS.tsv，`count 1`）的「22–75%」和 W861 的「9.1% 总时间」都要撤。
正确做法：从 pack manifest 逐层枚举真正的 Q8_0 张量与字节数，再乘实测带宽；**不要再用 bench 的 9 个矩阵当每层总量**。

### P0-2 W861 §3 的逐矩阵表不可复现（22% vs 45–71%）

同一份 `q8_gemv_bench`，唯一差别是**缓存副本数**：

| 来源 | 副本公式 | 总 footprint | shared g/u | 每层合计 |
|---|---|---|---:|---:|
| W861 §3 | `min(16, 512MB/bytes)` | ~2.3 GB | **156.2 GB/s（22%）** | 279.5 µs |
| W862 §1 同口径重测 | `min(8, 64MB/bytes)` | ~320 MB | **~322 GB/s（45%）** | **210.9 µs** |

显存现在只剩 ~870 MB（生产占 33.5/34.3 GB），**2.3 GB 的配置已经跑不起来**，所以 W861 那张表
在新环境下无法复现、也没法证伪，只能作废重测。W862 的重测口径（≥2 份副本、8 份封顶、总 ~320 MB）
更接近生产（每层实际只触几十 MB）。

⇒ W861 里 `22%`、`9.1%`、以及 §3.3 的「22% 到 75% 之间」全部作废；`R22` 的表述要换成
「ncols=6 时原始权重带宽 25–40%，ncols=1 时 45–71%（重测值）」。
（**W861 原文至今没有更正标注 —— 本轮已在文件头加了横幅**。）

### P0-3 gfx906 hsaco 三个字节数，文件名与尺寸配对至少错一处

| 出处 | 文件名 | 字节 |
|---|---|---:|
| W858 `:48` | `Kernels.so-000-gfx906.hsaco` | **219 448** |
| W858 `:519` | `Kernels.so-000-gfx906-xnack-.hsaco` | 190 968 |
| W861 `:14` / `:48` | （只写"190 968 B ELF"） | 190 968 |

同一个文件名在 W858 是 219 448、在 W861 是 190 976；而 190 968 在 W858 挂在 **`-xnack-`** 那个名字下。

### P1-1 W857 的 R15 负对照是单臂、无重复，却写成了定论

W857 §0 写「把 `STRATA_PREFILL_RING` 钉到 8 后，read 三档 **1.43 / 2.82 / 3.72 s，与默认 ring 完全相同**」
⇒「ring 深度不是 `wait copy` 的约束」。

但同文件 §1 自己列了：**B 臂的 TIMING 因脚本 bug 丢了**，只剩 read 三档；而且**每档 1 次、无 repeat**
（A 臂是 2 warm + 1 rep）。read 是**端到端墙钟**，项目基线里 read 的 spread 本来就大
（AUDIT13 P0-2 记过 `read1300` 的 3/3 同向被误判）。
⇒ 该结论应降级为 **UNRESOLVED**，与 AUDIT13 对 `--pool-workers` 的处理同档。

### P1-3 W862 把生产源码树改了，但没部署（潜在静默变更）

`/home/albus/strata166/pr/strata-fork` 现在 `git status` = **`M src/kernels/cuda/native_mmvq.cu`**

⇒ 处置（三选一，需机主定）：① 保留并在下次建镜像时一并 A/B；② 回滚（`git checkout HEAD -- src/kernels/cuda/native_mmvq.cu`），
上之前再打；③ 挪到分支提交。**当前是 ①，且已在 `W862_HANDOVER.md` 顶部与本文登记。**

### P1-4 W862 的 R 表是公式，不是项目惯例的实测表

项目自己的 CUDA 惯例（`kIlRows_*` / `il_rows`）是：按 **类型 × ncols(2..8) × n_out 五档**建表，
**0 表示走普通 kernel**，且「只有每个实测形状都赢 ≥3% 的格子才保留」。

W862 给的是**两条公式**（`R×NCOLS≤12`、`n_out/(4R)≥120`），只实测了 **ncols=1 与 ncols=6**、
4-5 个形状。ncols 2/3/4/5/7/8 一格没测；`ncols 2..3 → R=4` 是照寄存器推的，无实测。
⇒ 现在能上，但只能算「有实测支撑的近似」；要按项目标准，得跑一遍
`--group single` 扫 ncols 1..8 × 各形状并 `--emit-table`（工具已在 `albus/w862/`，缺的是扫全表）。

### P1-5 W861 的 hipBLASLt `DONE_NEG` 理由引用了作废数字

W861 §4 的第三条理由是「收益上限 ≈ 0：§3 已证明 decode 瓶颈在 GEMV 带宽（22–75%），不是 GEMM」——
引用的正是 P0-1/P0-2 作废的那组数。

`DONE_NEG` 这个结论**仍然成立**，但理由要换成**结构论证**：
gfx906 的 ISA 没有矩阵指令（W858 L4 已证）⇒ hipBLASLt 只能用 VALU kernel ⇒ 与 rocBLAS 同构；
叠加 non-MI codegen 的 17 个 `MI*` 字段未维护（W861 §5）⇒ **即便全通也不会比 rocBLAS 快，且有静默算错风险**。
⇒ 把「收益 ≈0」改成「**结构等价 + 上游路径未维护**」，不要再挂性能数字。

### P1-6 「不动生产进程」被当成了「不动生产资产」

W860 §5 立的规矩是「停服许可制」。W862 全程没停服、没重启、没换二进制 —— **合规**；
但改了生产源码树（P1-3），这条规矩管不到。⇒ 制度要扩一条：
**凡改动 `pr/strata-fork` 工作树（含未提交修改），视同改生产资产，须登记在案（改了哪个文件、备份在哪、怎么回滚）。**

1. **表是能出的**：`tools/hip/tune_rocblas.cpp` 单文件、只依赖 hip+rocblas，`hipcc -O3` **4.6 s** 编完；

2. **但收益集中在 T<=4096**：`T=8192`（**我们的 chunk 就是 8192**）上多数形状 gain=1.00-1.27。
   按相位折算 ≈ **prefill 的 2.5%**，不是上游说的 6x。**上游那个 6x 是 gfx1030 在 T<1152 的形状上量的**，
   我们根本不在那个区间 —— 这正是 `W786` 的教训（把别人的靶当自己的靶）。
3. **真正的发现在别处**：`N=320, K=10240`（**HC down**）在 T=8192 只有 **10.4 TFLOPS = fp16 峰值的 39%**，
   表能把它抬到 1.27x；`N=4, K=10240`（**HC inject**）与 `N=1, K=2560` 是 rocBLAS 的病态形状（2.4x / 6.6x），
   因为它们本质上是不该走 GEMM 的 GEMV。
4. **P1 之后稠密 GEMM 已经贴着硬件上限**：`N=10240,K=2560,T=8192` 实测 22.14 ms = **19.4 TFLOPS = MI50 fp16 峰值(26.5) 的 73%**；
   `N=6144,K=2560` 同 19.3 TFLOPS。=> 稠密 GEMM 这条路的总天花板是 **剩下那 27%**，按占 prefill 33% 折算 ≈ 9%，实际能拿一半。
5. **【R44 更正 · 2026-11-02 02:3x】`qsa attn`（19.5%，第二大项）在 gfx906 上不是「结构性缺口」，是「硬件没张量核 + FP32 没吃 packed fp16」**（原文写的「整段 prompt 用 decode 核跑」**不准**，见下）：`qsa_prompt_attn.cu:2346` 逐字
   `#if defined(STRATA_HIP_GFX906) return false;` —— 张量核/WMMA 路径对这块卡直接否决。**但注释的原文是**（`qsa_prompt_attn.cu:2379`，行号现在是 2378-2380）：
   *"gfx906: the tensor-core and WMMA kernels are not for it; **the FP32 kernel runs**"* ⇒ 跑的是 **FP32 核**，不是 decode 核。

   **【R44 外部核实 + 定性修正】**
   - Vega 20（MI50）**Tensor Cores = 0**（`thegpucatalog` 逐项列示），架构 GCN 5.1 / gfx906；FP16 **26.8 TFLOPS**、FP32 **13.4**、INT8 53.6（AMD 官方）。
     每 CU **128 个 FP16 单元 vs 64 个 FP32** ⇒ **packed fp16 的理论上限是 2× fp32**，不是 6×。
   - ⇒ 所以「张量核路径被拒」**是硬件事实的正确处理，不是我们漏开的开关**。原文说「结构性缺口」会把读者带向「去移植张量核代码」这条死路。
   - **真正的空间在别处**：`STRATA_HIP_PROMPT_F16` **只作用于 GEMM**（`src/prefill/gemm.cu:588`，全库仅此一处读它），
     **不覆盖 attention** ⇒ prompt attn 是一块**没有任何调优开关能碰到**的 FP32 区域。
   - **上界**：attn 19.2% × 2× ⇒ 最多省 **~9.6% prefill**（**仅长 prompt**）。
   - **【已用生产相位表量过，2026-11-02 02:3x】** `prefill timing` 三档实测 attn 占比：
     **893 tok → 2.4%**（78/3195 ms）· **21,822 tok → 18.9%**（6,202/32,880）· **99,382 tok → 19.2%**（29,513/153,872）。
     ⇒ **原文的 19.5% 在长 prompt 上是对的**，但它不是「普遍 19.5%」——**短 prompt 只有 2.4%**，所以这条只对长上下文成立。
> **【W887 续 · 2026-11-02 02:4x】第三层修正：这不是「结构性缺口」，也不是「漏开的开关」，而是「实现只跑到峰值的 11–16%」。**
> GGUF 元数据实测 `full_attention_interval=4` ⇒ **只有 12/48 层跑 QSA**，`indexer.top_k=2048` ⇒ 每 query 读 2048 cell，
> 于是每 token **604 MFLOP**；用生产相位表三点反算有效算力 **1.51 / 2.13 / 2.03 TFLOPS**（FP32 峰 13.4）= **11.3 / 15.9 / 15.2%**。
> ⇒ 「结构性缺口」这个说法真正的错是**把硬件上限当成了实现上限**：硬件上限（无张量核、fp16 2×）是真的，
> 但当前先要解决的是那 85% 没打出来的算力。详见 `W887`。

     ⇒ 已据此开 **`R46`**（`B5本机缺口`）：第一步不是改 kernel，而是**读 GGUF 的 head 配置算 attn 的有效 TFLOPS**——
     贴着 FP32 峰值 13.4 才说明「只能靠 packed fp16」，远低于它就是「效率不足」，两条路的改法完全不同。

## 4 折算：这条路的真实价值

以 M 档（3 个 chunk，2×8192 + 5438）为准，只算 T=8192 桶：

| 项 | 每 chunk 调用数 | 每 chunk 省 |
|---|---|---|
| HC down（1.27x） | 96（48 层 × 2 half） | 96 × 1.113 = **107 ms** |

| HC up（1.06x） | 96 | 96 × 0.156 = 15 ms |

| 其余小形状 | — | ~20 ms |
| **合计** | | **≈ 260 ms/chunk** |

## 5 顺带查实的结构性缺口：`qsa attn` 在 gfx906 上跑的是 decode 核

`src/kernels/cuda/qsa_prompt_attn.cu:2346` 逐字：

```cpp
#if defined(STRATA_HIP_GFX906)
        return false;   // gfx906: the tensor-core and WMMA kernels are not for it; the FP32 kernel runs
#endif
```

`qsa_prompt_attn_batch()` 返回 false 后，`prefill.cpp:3506` 落到：

```cpp
for (int64_t t0 = 0; t0 < T; t0 += m.attn_batch) {          // attn_batch = 32（硬编码成员默认值，prefill.cpp:908）
    strata::kernels::qsa_decode_attn_batch(m.q + t0 * ZV, pools, m.sel_ids + t0 * m.cap, ...);
}
```

即：**一个 8192 token 的 chunk，每个 QSA 层要跑 256 次"decode 注意力"**，每次只带 32 条 query。
`qsa attn` 占 M 档 19.5%（6.9 s）、L 档 15.3%（32.9 s），是 P1 之后**第二大项**。

**三条可行方向（按代价排）**：
1. **提高 `attn_batch`**（32 → 128）：只是少发 4 倍 launch、少重复解析 KV 页表。SCRATCH 代价 =
   `attn_batch × qsa_decode_attn_scratch_floats(cap, s)` ≈ 100 KB/query ⇒ 32→128 多 9.5 MB VRAM。
   **但它大概率收益很小**：每 chunk 6144 次 launch（8 个 QSA 层 × 3 chunk × 256）按 5 µs/次只值 30 ms。
   真正的成本在**每条 query 重新读一遍 KV**（O(T·cap) 的显存读），batching 不改变这一点。=> **不排**，除非先量出 launch 占比。
2. **写 gfx906 专用 prompt 注意力**（fp16 dot2 + LDS 分块）：这是 P5 的正题，工作量按"一个新 kernel"算。
3. **先量 roofline**：`qsa attn` 每 token 的 FLOPs = 选中 cell 数 × head_dim × 2 × n_head；M 档 6.9 s / 21.8K token
   = 316 µs/token。把这个数与"KV 读字节数 / 805 GB/s"比，才知道它是算力受限还是带宽受限 —— **这是下一步的第一件事**。

## 6 举一反三

1. **别人的靶要按自己的形状重算**。上游 6x（gfx1030、T<1152）在我们这里变成 1.0（gfx906、T=8192）。
   同一个工具、同一张表，**收益是形状的函数，不是卡型号的函数**。规则 K 的第二次应用：先算自己落在哪个桶。
2. **"默认选得差"通常是启发式在退化区间失效，不是库差**。rocBLAS 在 compute-bound 的大 T 上选得很好（19.4 TFLOPS/73%），
   在瘦 N（320×10240）和极小 N（4、1）上才失手。=> **优化前先确认自己是不是在退化区间**。
3. **调优器本身可能是零成本资产**。`tune_rocblas.cpp` 45 KB、4.6 s 编译、不依赖引擎，却能直接回答"这张表值不值得做"。
   **先找有没有现成的、可独立编译的测量工具，再决定要不要重编 25 分钟**。
4. **P1 把问题换了形状**：P1 之前"GEMM 有多快"是主问题；P1 之后 GEMM 已经 73% 峰值，
   **剩下的主问题是专家 MMQ（34.7%）与注意力（19.5%），两个都是自研 kernel**。=> 后续都是内核工作，不是开关工作。

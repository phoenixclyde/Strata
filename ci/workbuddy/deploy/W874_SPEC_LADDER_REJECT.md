# W874 · `--spec` 阶梯判否：窗口长度不由上限决定，而由草稿概率与后缀匹配决定

**日期** 2026-11-02 00:30–01:00（第 11–12 次部署）
**引擎** `0.1.55t`（r27）；两处改动都只是 config（`--spec 4↔5`），二进制始终是同一份 `0.1.55t`（`e0c6f250…`）
**重启** 本轮两次：①`strata-ci deploy --apply`（`--spec 5`，221 s）；②`docker restart`（回落 `--spec 4`，285 s 到 `/health`）
**结论** `--spec` / `--mtp-max-t` 在 4..7 区间对窗口长度 **无影响**（进程内 9 臂，T 恒 3.58–3.63，ms/tok 恒 12.78–12.92）。
真限制是 `dprob` 与 `--spec-min-p 0.70`；而 min-p 已有三条独立证据判 0.70 最优（P06 / P154 / R24）。
⇒ **「抬 T」这条方向在本机上封顶**，decode 的剩余空间全在 GPU 效率（115 GB/s = 屋顶 13%）。

### 2.1 为什么 `S=2` 也压不住窗口：覆盖点选错了（负面结果，写下来防再踩）

r27 的覆盖加在 `generate.cpp:12405`（serve 主循环）与 `18497`（decode 函数头）。运行时路径证明它**没有生效**：

- suffix 草稿走 `sfx.propose(o.spec - 1, ...)` —— 用的是 **`o.spec`**，不是 `S_mtp`（`18686`）；
- 而 `if (gated_proposal)` 分支里窗口由 `T = proposal.T;` 决定（`18662`），`S_mtp` 只是被传进 `prepare_gated_window` 当参数。

⇒ 要真正压窗口必须改 `o.spec`（启动参数，且它决定了 buffer、`DraftPolicy` 和 capture 的图）。
**`/data/strata-spec` 在 r27 里是无效杠杆，不要再用。** 这条与本轮的其他判否一起进账本。

## 3 窗口成本模型（两点拟合，与九臂一致）

用 §1 的两组数：`41.13 = c0 + 3.11·c1`、`46.20 = c0 + 3.59·c1`

```
每窗口 = 8.3 ms（固定） + 10.6 ms × T
```

- **固定 8.3 ms**：draft（3.4）+ host（2.1）+ commit + 图发射的固定部分；
- **边际 10.6 ms/token**：每多一个 token，多为它读一批专家。

⇒ 平均 13.2 ms/token 里，**有 2.6 ms 是摊不掉的固定成本**（T=3.11）。
若 T 能到 6：8.3 + 6×10.6 = 71.9 ms ⇒ **12.0 ms/token（+10%）**。这就是「抬 T」的理论上限——而它已被 §2 证明走不通。

## 4 窗口长度真正由什么决定（`STRATA_SPEC_DEPTH` 逐位读数）

同一次请求的日志三行合起来看：

```
drafts accepted 349 of 365
suffix drafts: 111 windows, 335 of 335 drafts accepted
spec depth: accepted/tested  14/30  10/10  7/8  4/5  0/0
```

- **suffix（后缀匹配）335/335 = 100% 接受**，111 个窗口 ⇒ 平均每窗口贡献 **3.0 token**；
- **MTP 只有 30 个草稿被检验、14 个接受 = 47%**（`dp_tested[d]`/`dp_ok[d]` 是「第 d+1 个草稿」的检验/接受，
  `generate.cpp:17099` 逐字：`for (int d = 0; d < T_mtp - 1 && d < 8 && d <= a; ++d)`）。

⇒ **生产 decode 的窗口长度基本由 suffix 撑起，MTP 只占小头**。这解释了为什么 `--mtp-max-t` 4→7 毫无变化（MTP 本来就没发满）。
也与账本里三条既有结论严丝合缝：P39（有效接受长度 1.797）、P42（`--suffix-draft 3` 已生效、`--lookup-chain ≤2` 是空操作）、
P47（`draft_policy.cpp` 的 `kShape[]` 是 RTX 5070 曲线，本卡从未标定）。

## 5 decode 的剩余空间（下一轮的靶，已量化）

> **【撤回 · W875，同日 01:00】** 本节下面的「115 GB/s = 屋顶 13.0%」和「每专家 22 μs vs 理论 3.5 μs = 6.3×」
> **用的是不适用的屋顶**：884 GB/s 是「大块连续读」的实测值，而 M≈3–4 的 GEMV 在本机只能跑
> **280–350 GB/s（fp16 探针，W875 §2）**。按形状取屋顶后，4-bit 生产的 136 GB/s 与它同量级（元素数 4 倍），
> **不是「浪费了 87% 带宽」，而是「GEMV 这个形状本身跑不满带宽」**。数字留着做算术记录，结论以 W875 为准。

| 量 | 值 | 口径 |
|---|---:|---|
| 每窗口专家读 | 31.42 × 3.13 MB × 48 层 = **4.72 GB** | 3.13 MB/专家是 UD-Q4_K_XL 的实测均值 |
| 窗口时间 | 41.13 ms | 引擎自报 |
| **有效读带宽** | **115 GB/s** | 4.72 GB ÷ 41.13 ms |
| 屋顶（W863 实测） | 884 GB/s | ⇒ **13.0%** |
| 每专家 GPU 时间 | 33.11 ms ÷ 48 层 ÷ 31.42 = **22 μs** | 而 3.13 MB ÷ 884 GB/s = **3.5 μs** |

**每专家比理论慢 6.3×。** 这不是 PCIe（本档 0.00）、不是 host（2.15 ms = 5%）、不是草稿（3.37 ms = 8%），
是 GPU 自己在 1772 个专家 GEMV 上跑不出带宽。

下一轮要回答的就是这一个：**22 μs 里 GPU 在等什么**。三条可查的线：
1. `STRATA_VERIFY_NODES=1` 数一个窗口的图节点数 ⇒ 如果是 ~1772 个小 kernel，问题就是发射/尾效应；
2. 每个专家的 GEMV 用了几个 block（占用率）—— R30–R35 的 wave-rows 表已经在这条线上；
3. `ROUTE_TAIL_SKIP=7` 现在是开的（启动横幅自证），它跳过 rank ≥7 的专家 ⇒ 已经是「少读」形态。

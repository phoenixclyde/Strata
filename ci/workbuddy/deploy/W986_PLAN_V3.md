1. **首块串行**是短 prompt 的主要损失（2K 请求里 1.3 s 是固定成本，占 32%）。

3. **NVMe 已就位**：稳态 0 磁盘读、加载 3.43 GiB/s ⇒ 磁盘不再是热路径变量，**不要再往数据分层上投**（W975 已证）。

## V3.3（W993）：R95 归因后重排 —— 移植项才是对的路

**R95 结论**：2K 的 1.9× 来自 `gemm gate/up + down` 与 `dequant/gather`，不是主机缝隙、不是 CPU 池、不是预取。J=64 在四张架构表上都是 K-quant 下限（A 已否决）。

**C（dequant/gather）的现成实现**：`STRATA_MMQ_DIRECT=1` —— 文档实测 170/1217 token 的 read-in **−18~24%**、greedy token 一致；但需要构建 `-DSTRATA_MMQ_TAB=ON`（我们 build-r32 只有 `STRATA_MMQ_KQUANTS/TQ/TQP`），且**"多数专家从 RAM 流式读入时收益 <1.5%"**（docs/DETAILS.md §1511）——我们 VRAM 只放 21.79 GiB，正是流式情形 ⇒ **暂不重编**。

### 优先级改排（把机主要求"必须做完"的移植项提上来）

| 序 | 项 | 为什么现在更值钱 |
|---|---|---|
| 1 | **R87 q8_1 激活复用** | 直接减 "dequant/gather" 侧的重复量化，外证 +2.2~2.6%，bit-exact，范围最小 |
| 2 | **R86 Q5_1 down 布局重排** | 减少 gather 时的行去别名/重排，88.6% 专家字节 |
| 3 | **R91 dot8 接 MMQ** | 针对 gate/up 的 Q4_K 小批 GEMM（R95 的主战场） |
| 4 | R95-B 小专家 small-M 分流 | 天花板高但改路由/边界 |
| 5 | R94 质量门 / R89 / R46 / R49 / R50 | 并行 |
| — | ~~R88 预取~~ | 已证伪（主机缝隙仅 15 ms） |

**判据不变**：所有臂 n≥10、基线同重启状态、2×CV、不显著即回退；prefill 类必须看 `--lengths` 2K/8K/16K 三档。

## V3.8（W1000）：撤回 W999 的 R86 判否，队列重排

**W999 的 A/B 不能作为判据**（机主质疑成立）：① 未按 mx 的 `use_w32` 分派，小行数档用错 64-wide kernel；② 激活用了标准 `block_q8_1` 而非 grouped `block_q8_1_mmq_h`。⇒ **R86 回 OPEN，P278 作废**。

**「完整生产移植」的三条通道（mx README）与我们的差距**：权重上传需加 GPU 侧 repack kernel（我们没有 ggml extra buft，专家按需上传）；compute dispatch 需重写自有 `mmq::Context::run` 的形状路由 + `repack_tile_off` + `expert_stride`；fused FFN 仅单 token，prefill 拿不到。⇒ 这是**在自有 prefill 路径里重写一套**，不是接入。

**完整的会不会好？** 公开数据（P280）：fused FFN 类 +1.9~14.7%（强依赖硬件）、MoE 版 +17.2% 无对照；mx 的 repack 主场景是 Q8_0/MXFP4 且融合红利只在 decode 单 token。⇒ 完整移植**可能从「慢」变「持平或小幅正」，但没有依据期待大幅收益**；唯一确定方法是做完再测。

**举一反三：队列重排为 R96 → R86 → R91 → R95 → R94 → R89 → R46/R49/R50**。
理由：R96（gate/up+GLU 融合，PR #29948 已合并、有跨硬件对照、直接打在 R95 的 gate/up 20.6% 主战场）比 repack 证据强得多、且不需要动权重布局；R86 补齐 A/B 的两个前置条件后重测，再做去留。

## V3.9（W1001）：公平 A/B 后，R86 从「判否」改为「混合分派」

修掉 W999 两个缺陷（按 `use_w32` 分派 + 两臂共用同一份 `mmq::quantize` grouped 激活）后重测：

| rows/expert | canonical | repacked | 比值 |
|---:|---:|---:|---|
| 32 | 0.237 ms | **0.156 ms** | 0.659（快 34%） |
| 128 | 0.542 ms | 0.507 ms | 0.935（快 6.5%） |
| 320 | **1.245 ms** | 1.430 ms | 1.149（慢 15%） |
| 1024 | **3.437 ms** | 3.460 ms | 1.007（持平） |

**结论**：repack 在小行数明显更快、大行数变慢 ⇒ W999「四档全慢」作废，R86 重新有价值。但 W991 的 2K 请求每专家 ncols **p50=331 / p90=742**，大头正落在变慢区间 ⇒ 全量替换端到端未必赚。

**⇒ 立 R97：按 `expert_bounds` 每段行数做混合分派**（小段 <128 行走 repacked w32，大段留 canonical），一次 group 内混合 launch；吃到小专家的 34% 而不付大专家的 15%。判据：六长度档 + 2×CV，prefill@2K 提升 ≥5% 才继续。

**执行序**：**R97 → R96 → R86（完整移植）→ R91 → R95 → R94 → R89 → R46/R49/R50**。
R86 的完整移植仍要做（三条通道见 V3.8），但方向从「全量替换」改为「只为小段提供 repacked 路径」。

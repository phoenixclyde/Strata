## 1 「最优」怎么定义 ---- 可证伪的判据

「最优」必须相对**一个明确的目标函数**和**本机的分辨力**才成立，否则任何差异都能被说成"更优"。

### 1.1 目标函数（分层，按本机实际用法排序）

| 层 | 指标 | 测法 |
|---|---|---|
| D1 解码吞吐（**主指标**） | 单流 512-token 生成 tok/s | `temperature 0 / top_k 1 / top_p 1`，预热后取 **3 次中位** |
| P1 预填吞吐 | 固定 18,083-token 冷 prompt 的 tok/s | 同上，3 次中位 |
| **P2 多轮 TTFT** | 同 doc 续写（prompt + 追加一句）的首字延迟 | 前缀探针：冷 / 温各 2 次，读 `reused` |
| C1 容量 | KV token / 并发 | 启动期读数 |
| R1 资源代价 | RAM / VRAM | 启动期读数 + rocm-smi |

### 1.2 本机分辨力（"要不要采纳"的门槛，实测得出）

| 指标 | 同臂内 3 次极差（本波读数） | 结论 |
|---|---|---|
| 预填 | **1.2 ~ 1.7%** | 改善须 **>2%** 才算事实变化 |
| 解码 | **9.5 ~ 15.0%** | 单次口径**不可分辨**；须交错多轮中位，或依赖上游 calibrate 的交错 3x3 |
| 多轮 TTFT | 两轮**逐位级一致**（5.861 / 5.877；23.072 / 23.074） | 该指标极稳，**-74% 量级一眼可判** |

> 前两行来自技能 §7.8 的既有结论（本机存在约 12% 的、既不能归因于配置也不能归因于 arm 序号的波动），
> 本波读数**再次复现**了它。

### 1.3 采纳规则（必须全部满足）

1. **单变量**：一次只改一处；A/B **交错**（A B A B）而非顺序（A A B B）；
2. **超分辨力**：中位改善超过 §1.2 对应门槛；
3. **两种测量实现交叉印证**：取上游 calibrate 与本机 A/B 的**交集**（本轮 4 项采纳 / 3 项否决都满足）。
   **这不是"独立复现"**：同一台机、同一个引擎、同一时间窗，只换了测量实现；
4. **机制前提成立**：flag 的机制有效域必须先自证（本波栽过一次，见 §7.2）；
5. **不牺牲其它层**：主指标改善不得让其它层掉出分辨力之外。

## 3 多轮复用（本波最值钱的一项）

### 3.1 关键机制（三条实测拼出来的）

1. **`--prompt-cache-every` 默认 16384** => 只有 prompt 超过 16384 token 才有 fresh-token checkpoint；
2. **可复用的前缀必须与 prefill chunk（8192）对齐**：18,083-token prompt 上恰好 `reused=16384`；
   把 interval 降到 **4096 反而一点不复用**（`reused=0`，因为 4096 不与 8192 对齐）。
   **[!] 证据等级**：本条只有"4096 无效 + 8192 有效 + 18k 复用 16384"三处观测支撑，属**与观测一致的机制解释，尚未被独立证实**（没有第二类独立实验，如改变 chunk 大小来看对齐点是否随之移动）；
3. **`--prompt-cache-tail` 与 `--prompt-cache-every` 重复**：它要"an existing chunk boundary"，
   而 `prompt-cache-every 16384` 已在同一位置放了 checkpoint => 无增量。

### 3.2 实测：`--prompt-cache-every 8192`（采纳）

| 臂 | prompt | 冷 TTFT | **温 TTFT** | **reused** |
|---|---|---|---|---|
| A 默认 16384 | ~10,000 | 23.44 ／ 23.46 | **23.072 ／ 23.074** | **0** |
| B **8192** | ~10,000 | 23.55 ／ 23.50 | **5.861 ／ 5.877** | **8192** |
| Δ | | | **-74.6%** | |

**实机验收**（部署后在现役服务上跑，引擎日志同口径自证）：

```
prompt 9982 tokens =    0 reused + 9982 read in 23354 ms (427.4 tok/s) ... 2 checkpoints   ← 冷
prompt 9993 tokens = 8192 reused + 1801 read in  5801 ms (310.4 tok/s) ... 2 checkpoints   ← 温
```
=> **冷 23.48 s -> 温 5.91 s = -74.8%**，且 `2 checkpoints`。

> 对照：`--prompt-cache-tail`（18,083-token prompt，各 2 轮）温 TTFT **5.787(B) vs 5.828(A)**、`reused` 恒为 16384
> => **无效果，否决**。
> 另：默认值下 18,083-token prompt 的多轮复用**本来就是工作的**（`reused=16384`，40.2 s -> 5.8 s）；
> 盲区在 **8192 ~ 16384 这一段**，`8192` 正是补它。
>
> **[!] 适用区间（未测部分）**：本项只在 **~10,000 token** 一档上实测。`> 16,384` token 的 prompt 默认已有 checkpoint、`8192` 只是多一个，**是否有增量收益未测**；`< 8192` token 无效（无 chunk 边界）。

### 3.3 资源代价

`checkpoint` 计入 `--prompt-cache N`（默认 6）上限，help 记 **~118 MB/个** => **推算**上限约 **0.7 GB RAM**（**这是推算值，未实测 RAM 曲线**）。
实机复核：VRAM `33,957,462,016`（部署前 `33,910,767,616`，+47 MB 级）、RAM available **82 GB**、解码专家缓存命中 **95.1%** ---- **无可见代价**。

## 7 方法论教训（本波真实踩到）

### 7.1 给"停生产 / 独占资源"的窗口做兜底：标志物要用**窗口自身**
看门狗 v1 用"有没有 calibrate 进程"当判据 -> 它在窗口开始后 **13 秒**检查，此时 `docker exec` 还没起来
=> 误判"窗口没开始"=> **把生产容器拉回来了，两个引擎同时抢 GPU**。
实测后果可控（校准先拿到 33.8 GB，生产刚起只占 42 MB 就被停），但**这是真事故**。
v2 改用"**窗口包装进程是否还在**"---- 载荷在窗口内的出现时刻是不确定的。

### 7.2 判"某 flag 无效"之前，先确认**它的机制前提成立**
第一轮测 `--prompt-cache-tail` 用了 6.8k-token prompt ---- 而该 flag 需要"**已存在的 chunk 边界**"，
chunk 是 8192 => **根本无边界**，测出来必然是"无效果"。**那是无效测试，不是结论。**
=> 泛化：**任何"实测无效果"都必须先自证"测的场景落在该机制的有效域内"。**
（同一个坑在后面又出现一次：`--prompt-cache-every 4096` 的"无效"其实是**对齐问题**，不是 flag 无用。）

### 7.3 本机 shim 会把 `/data/x.py` 这类参数转成 Windows 路径
驱动脚本里 `sys.argv[2]` 传 `/data/bench_prefix.py` -> 收到 `D:/Program Files/.../data/bench_prefix.py`。
**修法：只传短记号（`prefix220`），真实路径在脚本内拼。**
（同族：`%%{http_code}` 在非格式化字符串里会让 curl 打出字面量 => 探针永远不等于 200，看起来像"服务挂了"。）

### 7.4 只读探针也要"落盘 + 每步时间戳 + 断言 rc"
本波有 3 次"看起来卡死"，实为**输出被管道块缓冲**、或**探针用宿主路径查容器内文件**。
固定姿势：`python -u` + 重定向落文件 + 每步时间戳 + 断言 rc。

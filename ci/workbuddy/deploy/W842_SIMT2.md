## 3 读数（**只有一档可配对**）

两臂的 mt_read 请求集逐字相同：2575 / 5512 / 19358 / 3014 / 5282 / 18980 token。

| read | A2 `=1` | B `=2` | 可配对？ |
|---|---:|---:|---|
| 18980 tok（两臂都有） | 27161 ms（698.8 tok/s） | 27130 ms（699.6） | ✅ **−0.11%（齐平）** |
| A2 日志里的 2987 / 5299 / 19066 | — | — | ❌ 这三个 token 数**不在 A2 自己的请求集里** |
| B 的 5512 / 3014 / 5282 | — | 8174 / 5468 / 8073 ms | ❌ A2 对应档的日志行被 `tail -8` 截掉 |

prefill 夹在两条 decode 之间；而脚本是 mt_read 跑完才 mt_gen，单客户端不可能出这个序。配套算术：p1 的
wall 32.2 s，其自身 read+decode 只有 5.25 s，差的 ~27 s 正好等于那条 19066 的 27216 ms
⇒ **A2 会话期间有第二个客户端在同一实例上抢 GPU**。对照臂因此不成立。

## 4 判词

**不采纳 `=2`，生产保持配方 `=1`**。依据按性质写清：

1. **没有证据支持有收益**：唯一可配对的 19K 档 **−0.11%**（齐平）；三档因对照臂被污染而**不可判**。
2. **机理上没有预期**：`=2` 与 `=1` **同 bits**，只把 tile 从 32/64 放大到 32/128。上游 #3073 的 −6.5%
   是「`=2` vs 该卡**默认 warp 内核**」那一步的收益 —— 我们生产早就在 `=1`（tiled），那一步已经吃到了。
3. decode −7.9% 只有 n=3，**不能据此说"=2 更慢"**；只能说"没有理由换"。

⇒ 记 **DONE_NEG（不采纳）**，不是"已证有害"。

## 5 成本与操作教训（按审计后的归因重写）

| 项 | 事实 |
|---|---|
| 有效臂 | 2（A2/B），各 ~245 s 载入 + ~2 min 测量 |
| A 臂失败 | 18:16 那次 A 与 B 都是 `ABORT: container restarting (i=26)`，而 A2 成功；**B 的 exe 与 A2 逐字相同却起不来** ⇒ 与"路径写法"无关。真实原因：脚本在 26 s 就判 `Restarting` 并放弃，而该容器 `stop` 需要 ~20–30 s（释放 71 GiB），加上前一晚崩溃留下的 `--restart` 循环尚未清。**这是"判据太急"，不是引擎崩溃**（该时段日志里没有 n3 的报错） |
| 真正的路径坑（18:01 那次） | config 的 `exe` 写成宿主路径 `/home/albus/...` 会让 serve 启动器 `FileNotFoundError` + `Restarting` 循环（三臂全废在那一轮）。**必须是容器内 `/data/bin/...`**。两件事不能混成一条 |
| 第二个坑 | 长跑容器直接 `docker restart` 后，26 s 内仍可能 `Restarting`；改 `stop -t 30` → 等 `exited` → `start` 后一次成功（ready 247 s） |
| 第三个坑 | 新补丁文件（`qsa_select.cu`）不在 `sync_gfx906.sh` 的 `FILES` 里 ⇒ ninja "no work to do"。**已补进 FILES** |
| 第四个坑 | `sync_gfx906.sh` 会 `git reset --hard origin/<branch>` ⇒ **未 push 的 commit 被丢弃**（`cc8a071` 崩过一次，靠 reflog 找回）。**改 → commit → push → sync** |
| 第五个坑（本轮新发现） | 对照臂运行期间**不能有第二个客户端**：本轮 A2 被外部请求插队，三档 read 全部作废。**实验脚本应加"实验期间拒绝/检测外来请求"**（例如在 mark 段内比对 `/metrics` 的 requests 增量与自己的请求数） |

## 0 三句结论

1. **decode 现在是「等 GPU」**：单窗口 **41.07 ms** 里 **32.54 ms（79%）是 `GPU-reach wait`** ——
   主机线程在 `wait_flag_ge` 上等 GPU 跑到下一层的同步点（`verify.cpp:3291` 逐字计的是 `b - a`）。
   CPU 侧真正干活的只有 **2.47 ms（6%）**（plan 0.19 + actq 0.16 + jobs 0.04 + CPU 专家 1.95）。
2. **不是 PCIe、不是换专家**：`PCIe 0.00`、`swaps/window 4.2`、VRAM 命中 **30.87 专家/层-窗口**。
   每窗口的专家读量 = 48 层 × 30.87 × 3.13 MB ≈ **4.64 GB**，除以 41.07 ms = **113 GB/s**
   ⇒ **只有 884 GB/s 屋顶的 13%**，GEMV 是**延迟/占用率受限**，不是带宽受限。`[实测+算术]`

> **【口径作废 · AUDIT20 / W875，2026-11-02 01:3x】** 这句「13%」用的屋顶不适用本例：
> 884 GB/s 是**大块连续读**的实测值，而 M≈3–4 的 GEMV 在同一张卡上只有 **280–350 GB/s**（`gemv_shape_probe`）。
> 按形状取屋顶重算：每窗口 **31.42 专家 × 3.135 MB（**W891 更正：2.99 是算错的，`21.79 GiB ÷ 7463 = 3.135 MB`**） × 48 = 4.73 GB** ÷ 41.13 ms = **115 GB/s**，
> 占形状屋顶的 **31–39%**，不是 13%。方向（延迟/占用）仍成立，**百分比作废**。见 `W875` §2、`P250`。
3. **最便宜且从未扫过的旋钮：`--spec`（窗口大小）**。P05 的证据栏写的就是「基线」——**没扫过**；
   而窗口成本主要由专家读决定（与 T 共享），所以 **T 从 3.08 抬到 4.5–5 几乎不额外付专家读的钱**。

## 2 这笔预算说明了什么

| 项 | 值 | 含义 |
|---|---:|---|
| GPU-reach wait | **32.54 ms (79%)** | 主机无所事事地等 GPU —— **GPU 是墙** |
| per-layer host | 2.47 ms (6%) | 计划/取任务/CPU 专家都在这里，**不值得优化** |
| draft | 3.26 ms (8%) | MTP 草稿 |
| adapt wait + join | 0.48 ms | 自适应层基本不挡路 |
| PCIe 专家 | **0.00** | 本档完全没有走 PCIe |
| VRAM 命中 | 30.87/层-窗口 | 专家都在 VRAM 里 |

⇒ **「让 GPU 少等数据」这类改法（预取、更多槽、PCIe 优化）在这个档没有空间**；
能动的只有两件事：**让 GPU 每窗口算更多 token（T↑）**，或者**让每个 token 的 GPU 工作更少**（kernel 效率，R30–R35 那条线已挖过：dp4a +73~117%、wave-rows 表 +4%）。

## 3 下一轮：`--spec` 阶梯（判据用同一行计时器）

`--spec 4` 是**从来没有被扫过**的默认值（P05 证据栏：「基线」）。窗口成本 ≈ 专家读（共享）+ T 行计算，
所以这是一个「花小钱换大 T」的杠杆：

| 臂 | `--spec` | 预期 T/窗口 | 若窗口成本只涨 10–20%，净收益 |
|---|---|---|---|
| A | 4（现状） | 3.08 | 基线 72 tok/s（短上下文） |
| B | 5 | ~3.8 | +15~20% |
| C | 6 | ~4.5 | +25~35%（上限受接受率与 draft 成本约束） |

- 风险：T 变大 ⇒ 每窗口计算/草稿变多；接受率若掉，反而退化。**先量 T 与 ms/window，再算 tok/s。**
- 做法：`--spec` 是启动参数，逐请求文件开关需要动到窗口规划（比 short_read 深），
  所以**先按传统两/三次重启的方式测**（每臂 warm 一发 + 测一发 512 token，约 3 分钟/臂）。
- 判据（P188）：`ms/window` 与 `tokens/window` 同臂 ≥3 样本；tok/s 只作旁证。

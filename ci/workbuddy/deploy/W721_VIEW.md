- **组合后的一句话结论**：**一个开关的收益，严格等于"它省掉的那一环在总时延里的占比"。**
  我们这台机的时间几乎全花在"**每轮把上下文重新算一遍**"上 ---- 所以只有打中**重复计算**的开关拿到两位数收益；

## 2 组合起来看：一条规律

把上表按收益排序，规律很清楚：

```
-93%  P31   重复计算
-74.6% P34   重复计算
-70.6% P10   重复计算（但改答案）
+10.9% P25/P06  解码主循环
--------------------------------  两位数分界
  ~3%  P28   kernel
  ~1%  P32   显存
   0%  P23 / P98  搬运
   0%  P33   驱逐（预算够）
```

**收益 = 该环节在总时延里的占比。** 这不是巧合 ---- 一个开关最多只能把"它作用的那一环"清零，
所以它的**收益上限就是那一环的份额**。

**我们这台机的份额构成**（全部实测）：

| 环节 | 份额 | 证据 |
|---|---|---|
| **多轮时的"重复预填"** | 约 **90%**（轮 1 的 11.8 s 里，轮 2 只花 0.83 s） | W719 实测 |
| 冷预填 | 大（4,877 token / 11.8 s ≈ 414 tok/s） | W719 |
| 解码 | 中（11-56 tok/s） | W716/W719 |
| **专家搬运** | **≈ 0**（`pcie experts 1.83 distinct/layer` ---- 专家几乎全在 cache/RAM） | W718 |
| **KV 显存** | **≈ 0.9%**（204 MiB / 21.98 GiB） | W720（W735 更正） |
| **kernel 本身** | **小**（GPU 在等专家与路由，不是算不过来） | W718 的 `on the CPU` 实验 |
| **驱逐** | 该窗口 **0**；**W735 更正：现役 `evictions=5`**（4096 MiB 预算会用满） | W719 + W735 |

## 3 由此得出的筛选启发式（可直接复用于未来的候选）

**第一步（分诊）---- 问它省的是哪一类：**

| 类型 | 预期收益 | 处置 |
|---|---|---|
| 省**重复的上下文计算** | **两位数百分比**（历史：-93% / -74.6% / -70.6%） | 值得发车 |
| 省**搬运 / 显存 / kernel / 驱逐** | **0 ~ 3%**（低于解码分辨力 9.5-15%、预填分辨力 1.2-1.7%） | **先读源码算作用面**，多半零发车关掉 |

**第二步（算作用面）---- 不要问"这个开关好不好"，要问"它作用的那一环有多大"：**

- 搬运类 => 先问"**有没有东西要搬**"（P23：专家全在 cache => 无）
- 显存类 => 先问"**省下的量占总池多少**"（P32：204 MiB / 21.98 GiB => 0.91%）
- 驱逐类 => 先问"**会不会真的驱逐**"（P33：该窗口 `evictions=0`；**W735 更正**：预算会被占满，现役已 5 次驱逐 => 该项在长期运行下**有**作用面）
- kernel 类 => 先问"**kernel 是不是关键路径**"（P28：GPU 在等专家 => 不是）
- 重复类 => 先问"**它的复用条件在我的会话形态下成立吗**"（P34：必须与 chunk 整数倍对齐）

**第三步（一票否决，与收益无关）：**

1. **会改答案 / 破坏位一致** => 直接否（P10 的 -70.6% 就是这么被否掉的；P28 的 "sums in another order" 同）
2. **官方说不该在我们这类硬件上开**（P23 的宏缺陷：banner 误开）=> 显式关回去
3. **编译期/结构上不可能命中**（P30：HIP 分支恒 false）=> 不适用，不必测

### P1-2 `W788` 的占用率算错 2 倍：gfx906 的 wavefront 是 64，不是 32

- **原算法**（`W788 §3`）：`WARPS = THREADS/32 = 8`；"每 CU 只有 8 warps（容量 40）-> 20% 占用"；"41 blocks < 60 CU -> 68% x 20% = 13.6%"。
- **实测设备属性**（`rocminfo`，166）：
  - `Compute Unit: 60`（GPU agent；另一个 44 是 CPU agent 的核数，不要混）
  - `Wavefront Size: 64(0x40)`
  - `Max Work-item Per CU: 2560` -> **每 CU 最多 40 个 wavefront**
- **正确的数**：256 线程 = **4 个 wavefront**（不是 8 个 warp）。内核确实按 32 lane 分组（`fused_gr.cu:310` `warp = t >> 5`，一个 32-lane 组算一行），但在 64 宽的 wavefront 上，**两个 32-lane 组共用一个 wavefront**，所以"8 个 32-lane 组"只占 **4 个 wavefront 槽**。
  - 每 CU 占用 = 4 / 40 = **10%**（不是 20%）
  - 聚合 = 41/60 x 10% = **6.8%**（不是 13.6%）
- **为什么这条重要**：`13.6%` 是 `P95`、`P96`、`W788` 三处引用的核心数字，也是"9.5 倍差"的唯一解释。数值错 2 倍不影响"差得很多"这个方向判断，但**它把可解释性夸大了**：实测 9.5 倍对应 1/0.105，与 6.8% 同量级但更接近"6.8% 的 1/0.068 = 14.7 倍"这一档，说明除占用率外还有别的损失（否则应该更接近 14.7 倍）。
- **性质**：把 CUDA 的 warp=32 语义直接搬到 AMD wave64 上。这类错在 `W785` 已经出现过一次（`qsa.cu:428` 的 `o=16` 循环只覆盖 32 lane 的疑问），当时列为 D0 门禁"必须核实"，**但没人真的核**。

### P1-3 路径 A（`TILEV` 2560 -> 1280）**结构上不可能有效**，而它正是 R5 唯一排队的动作

三条独立理由，都可从源码判定：

1. **块数不变**：`DOWN_BLOCKS = LR / WARPS = 320/8 = 40`，与 `TILEV` 无关（`fused_gr.cu:42`）。grid 仍是 41 块，而 CU 有 60 个 -> **每 CU 本来就最多 1 块**。减小 shared（34 KB -> 17 KB）只在"块数多于 CU"时才能提高每 SM 块数，**这里块数比 CU 还少，改了也不会有第二块落到同一 CU**。
2. **tile 的唯一收益条件在我们的 T 上不成立**：小 tile 的作用是"8 个 token 装进一次 launch"。实测 `chunk = usable/(tv*4)`：`tv=2560` 时 `65536/10240 = 6`（`kFusedGrMaxT=8` 封顶），`tv=1280` 时 `12.8 -> 8`。而我们的 **T = 3.2-3.5**（日志 `avg T 3.33-3.47`），**本来就只有一次 launch**。所以小 tile 省不到任何一次 launch。
3. **预取深度减半**：`TQ = TILEV/8/32`，2560 -> **10**，1280 -> **5**。每 lane 在飞的权重块从 10 降到 5，`ldw` 的 MLP 直接减半。在"占用率本来就 6.8%、靠 ILP 撑"的内核里，这是**负向**改动。

- **预测**（发车前可写）：臂 B 会在 `hc0 down` 上持平或变慢，不会出现 `-20%`。
- **这解释了 R5 的实际观测**：臂 A（默认 2560，等于基线路径）三档 `hc0 down` = 1.33+0.44=1.77 / 1.37+0.46=1.83，与基线 1.33+0.45=1.78 基本一致 -> 说明**镜像本身没问题**（这正是切生产前该做的验证，现在等于事后补上了）；而"臂 B 从未跑"其实是**避免了白跑**。
- **性质**：`W788 §5` 写的修复（"shared 34->17 KB，3 blocks/CU"）**与它自己 §3 的诊断前提矛盾** —— §3 说瓶颈是"19 个 CU 空转"，那就必须**增加块数**，减小 shared 反而只在块数过剩时才有意义。诊断对、处方错，而且处方是最便宜的那一条，所以最容易被直接执行。

### P1-4 全部基线都在 `performance` governor 下测，而生产现在是 `schedutil`

- **时间线**：`performance` 是 W776（10-22）为了测"governor 对预填的影响"设的；`P91`（今天 04:3x）、`W788`（05:2x）、R5 臂 A（05:5x）**全部测于该状态下**；`schedutil` 是 06:0x 才改回的（44 核，`intel_cpufreq` / passive）。
- **后果**：现存的 decode 基线（46.35 / 47.35 / 39.90、51.58、53.17、53.02）**其口径与生产当前状态不一致**。任何拿它们做对照的 A/B，都会把"governor 差异"算进改动里。
- **是否要紧**：prefill 是 CPU+GPU 双满载（`P92`），持续满载下 `schedutil` 通常也会顶到最高频，所以差异**大概率小**——但这正是**不能假设**的东西。上一条 P1-2 就是"假设 warp=32"导致的。
- **处理（本轮）**：不重启生产做 governor A/B（每次重启都是风险，且今天已经因重启出过一次 10 分钟中断）。**登记为口径约束**：现有基线标注"governor=performance"，后续任何 A/B 必须**当场记录 governor 并前后一致**；如果要长期以 `schedutil` 为基线，需在下次必要重启后重测三档。

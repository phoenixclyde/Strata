现状：5 类参数是"上游在另一台机器上的默认值"，我们一个都没标定过。

| 参数 | 现值 | 上游前提 | 动作 |
|---|---|---|---|

### L4 并发层（`--batch`，16 行窗口唯一用处）

机制（`docs/BATCHING.md`）：`--batch N` 时**每个 verify 窗口携带每个对话的一个 token**，dense / 共享专家 / head / 两个对话共同路由到的专家**每窗口只读一次**。
上游在 RTX PRO 5000 上 2-4 客户端测到 **+31~39% 总吞吐**，单流不变。

| 项 | 成本 | 判据 |
|---|---|---|
| `--batch 2`（窄版，窗口 4 行足够） | 第 2 个 slot 的 KV ≈ **2.95 GiB**（k8v4 × 256K，引擎日志实测；原文 214 MiB 是 32K 的口径，差 14 倍 —— AUDIT12 更正）⇒ 槽位 **−2016（−27%）** | 单流延迟不回归 + 双流合计 tok/s |
| `--batch 4` | KV ≈ 11.8 GiB（4×2.95）⇒ 槽位 −4000 量级（**原文 856 MiB/−285 已作废**） | 同上 |
| `--batch 9..16`（**只有宽版能跑**） | KV ≈ **26.6–47.2 GiB ⇒ 装不下**（W828 §6.4 实测：16 slots 需 47 GiB，8 slots 已 OOM；原文 1.9-3.4 GiB 作废） | 只有真需要 9+ 并发才做 |

## 3 不做（附理由，避免反复讨论）

| 项 | 理由 |

| 把 `--spec` 提到 8 以上 | **上游硬拒**（`generate.cpp` 新增检查），不是我们能调的 |

### 5.2 更新后的判断

1. **参数层（L3）已经挖空，五项全部结清**：`--pcie-frac`（0.20 最优，0.35 起掉 11%）、`--spec-min-p`（0.5 只高 0.4%）、
   `--pool-workers`（默认最优）、`--adapt-*`（512 token + `ms/window` 判为慢 2-4%）、`STRATA_SH_STREAM`（四臂两对方向相反，均值差 0.7%）。
   **现有的 33 args / 14 env 就是这台机器的最优点**——这不是"没找到"，是把官方工具和自建四臂都跑过之后的结论。
2. **`--adapt-*` 与 `STRATA_SH_STREAM` 的机理判据都指向同一件事**：它们优化的都是"GPU 等 CPU 池"那段。
   我们命中率 97.3%、每层窗口只有 0.58 个 CPU 专家 ⇒ 那段本来就不存在。
   **以后看到"某卡上 +7~10%"的开关，先看自己的 `CPU experts per layer-window`**，再看要不要测。
3. **并发层（L4）被实测否掉**：每个 slot 要 2.95 GiB VRAM（262144 上下文），`--batch 16` 起不来，
   `--batch 2` 也要付 5.9 GiB（槽位 −28%）。
4. **calibrate 重跑一次，它自己不可重复**（P190）：同机器/引擎/配置跑两次，settings 完全不同
   （`pcie-frac` 0.20 vs 0.00、`spec-min-p` 0.50 vs 0.70、`adapt` 1/80 vs 1/160、`SH_STREAM` 1 vs 未设）。
   拆开看：**单实例内扫描三项高度可重复**（pcie 曲线差 ≤3.3%、workers 几乎逐位相同、confirm 一致），
   **"每值重启"两项两次结论相反**（adapt：1/80 赢 +10.3% → 1/160 赢 +9.1%；sh_stream：+7.5% → −1.0%）。
   ⇒ **以后只采信 calibrate 的单实例内扫描结果**，其余必须自己 ABBA。
5. **顺带量到一个可重复的大数**：引擎按带宽自己算的 `--pcie-frac 0.36`，比最优（0 或 0.2）**慢 13.7% / 17.8%**
   （两次 `confirm` 都是 3 轮交替）。我们显式写 0.20 不是"手调碰巧"，而是**必要**的——不写就慢 13.7%。
6. **"所有 AMD 优化都扩展到我们平台"这句话，本轮已经穷尽**（P191）：上游给 gfx1151 集显开的 **19 项** exact 优化里（原文写 15 项，AUDIT12 按 `arch_defaults.cpp:58-90` 逐条数得），
   实测 5 项（`ATTN_LANECELL` / `MMVF_ROWS` / `LFUSE` / `EXPERT_V2` / `GDN_SPLIT`）全部 ±1.5% 内无效。
   ~~统一解释：`GPU-reach wait` 占窗口 77%，所有"省算力/省 launch"的优化都被这个等待淹没。~~
   **这条解释已在 §6.12 更正（P195）**：那 77% 是**宿主机在等 GPU 里程碑**（host 空转），不是 GPU 等数据。
   逐 kernel 分解后，一个窗口的 GPU 时间摊在 **15+ 个 kernel** 上：专家 VRAM 读取 **23.4%**、两条 dense MLP **16.6%**、
   GDN 主体 15.6%、各类等待 14.5%、QSA 主体 13.1%、路由 8.5%、shared+量化 4.5%、head 3.8%。
   **最大单项只有 23.4%，所以任何一个单项开关都只值 ±1.5%**——这不是"被淹没"，是分母本身分散。
7. **`--batch 2` 的等待账算完了，也不通**（P192）：槽位 −27%（7463→5447），单流 −3~5%，
   双流合计只有 **49.18 tok/s**（比单流 45-47 高 5-8%，远非 2 倍），每流 22 → **40 ms/token**。
   机理：并发只能共享"每窗口读一次"的 dense/head；**专家读取跨请求共享率约 1%**（K=10 路由、512 专家，交集期望 0.2 个/层，
   而每层 VRAM 命中 21.4 个）。上游 +31~39% 是 dense 主导的小模型。
   ⇒ ~~77% 的等待既不能省算力绕开，也不能并发摊薄。~~
   **更正（P195）**：等待不是主项（`VRAM hits` 才是，23.4%）。真实的结论是"单项都太小"，
   而并发不通的机理仍然成立：专家读取跨请求共享率约 1%。

9. **投机窗口策略也结清了**（P194，8 臂 6 配置）：`--spec` 上限 4→8 是空操作（门槛先截断）；
   放松门槛（0.50）明确亏 **−15.1%**；收紧门槛（0.85/0.90）无收益（47.01 / 45.66）；
   引擎自己的成本感知规则（`STRATA_SPEC_COST=1`）把 T 收到 **2.28**，与基线 2.18 重合。
   ⇒ **T ∈ [1.6, 2.4] 是一段平地（45.7–47.1 tok/s），生产站在正中；T>3 才是悬崖。**

10. **自适应层不能关**（P196，4 臂）：`--adapt-swaps 0` 两臂 44.52 / 43.49，对基线 46.28 / 45.48 = **−3.8% / −6.0%**。
    机理：关掉后 VRAM 命中/层-窗口 20.3→14.3、**CPU 专家 0.61→2.93（+380%）**，swap 省下的不抵 host 计算。
    顺带纠正：稳态 `adapt wait` 只有 **0.11 ms/窗口**（1.4–2.4 ms 是含冷启动的臂均值）。

    每窗口读 **~3.2 GB**（21.4/层 × **48 层** × 3.1 MB）⇒ 实测 **~300 GB/s**（MI50 峰值 ~30%）。换 UD-Q3_K_XL 约 **+6% decode**，

    **补测长端**：7.2K → auto 11.80/11.26 vs `=0` 11.68/11.34；14.3K → 20.25/20.36 vs 20.26/20.34（**完全收敛**）。
    ⇒ **`=0` 在任何长度都不赢，生产维持 `auto` / 3072**；原先"长文档切 `=0` 省 26%"是按三点拟合外推出来的，**实测作废**。
    机理部分仍成立（`=0` 的固定项 4.74 s ≈ PCIe 搬 **52 GB** @**11 GB/s**；原文按 60 层写 72 GB/15 GB/s，AUDIT12 更正 —— 15 GB/s 已超 PCIe 3.0 x16 上限）。**新规矩 P200：拟合不许外推到取样区间 2 倍以上。**

**本轮到此，性能的结论是"已经到界"**：在这台机器（262144 上下文 + UD-Q4_K_XL + 32 GB）的三个约束下，
参数层、引擎开关层、并发层、**投机窗口策略层**都量过了，没有剩余的正收益。**要再往上只能改约束本身**——
更低位宽（Q3_K_XL，代价是质量）、更小上下文（16-32K，换 `--batch`/16 行窗口可用）、或更大显存。

**"到界"的量化依据（§6.12）**：一个 decode 窗口的 GPU 时间摊在 15+ 个 kernel 上，最大单项 23.4%。
所以"再压 5%"意味着要同时动三四个 kernel，而不是找到一个开关。这也解释了为什么历史上每一个
单项优化都是 ±1.5%：**不是没找到，是分母分散。**
8. **数值债部分结清**（P193，AUDIT12 收窄）：账本 8 项里实测只翻了 5 项（`MMQ_KQ` 保留、`GDN_HEAD`/`GDN_PP` 未动），所以下面这个数是 **5 项**的总账，**KL mean 0.0293 / median 0.0001，argmax 一致 97.8%，
   top-10 重叠 0.85**；底噪逐字节为 0（两份同配置 md5 相同）。这是账本上第一次有"我们的近似总共值多少 KL"这个数。
   落在 0.02–0.05 区间，不必二分；median≪mean 说明代价集中在少数位置。口径提醒：这是 **4-bit 权重之上再加的近似**，
   不是相对 fp16 模型的偏差。


4. **16 行窗口在 gfx906 上：编得出、跑不到**。宽构建证明 kernel 全部可编（含 `moe_grouped_s2_wide`、
   `resident_plan<256>`、`native_mmvq` 9..16 列、`fused_gr` 切片），但要用它必须 `--batch ≥ 9`，而 9 slots 要 26.6 GiB（实测 8 slots 已 OOM：23.60 GiB 时只剩 156 MiB）。

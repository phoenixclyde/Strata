## 7 原因：单一主导变量 = VRAM 专家层命中率

**方法**：把生产日志里的 per-request 摘要与**紧随其后的** `decode expert cache hit rate` 行配对（148/149 条配对成功），
再按「同一 prompt 长度 + 同一生成长度」对拍。

### 7.1 相关与分桶（n=143）

**Pearson r(命中率, 解码 tok/s) = 0.607，r^2 = 0.369**（命中率单独解释约 37% 的方差；其余是上下文/生成长度与噪声）。

| 命中率桶 | n | 解码均值 |
|---|---|---|
| <80% | 8 | 32.3 |
| 80-85% | 15 | 36.7 |
| 85-90% | 35 | 35.9 |
| 90-95% | 56 | 41.0 |
| **95-100%** | 29 | **45.7** |

### 7.2 同形状对拍（prompt 与 gen 完全相同，只差命中率）

| pt | gen | 命中率 -> 解码 | 比值 |
|---|---|---|---|
| 85 | 400 | **85.3% -> 34.5** vs **95.0-96.0% -> 42.6-49.0** | 1.36x |
| 4877 | 8 | 83.3% -> 26.2 vs 91.0% -> 48.3 | **1.84x** |
| 4903 | 8 | 87.4% -> 26.1 vs 93.4% -> 41.0 | 1.57x |
| 18085 | 32 | 87.7% -> 30.1 vs 95.8% -> 42.3 | 1.41x |
| 62 | 64 | 74.3% -> 28.9 vs 90.3% -> 37.7 | 1.30x |

### 7.3 算术闭合（pt=85 / gen=400，冷 3 发 vs 温 15 发）

| | n | 平均 decode_ms | 命中率 | 平均 lookups |
|---|---|---|---|---|
| 冷（`reused=0`，新会话首发） | 3 | **12,012** | **85.5%** | 219,012 |
| 温（`reused=80`，同会话连发） | 15 | **8,668** | **95.1%** | 同上 |

- **delta时间 = 3,345 ms**；**多出的专家取数 = 9.59% x 219,012 = 20,996 次**
- **=> 每次多取数摊到 0.159 ms**（与「从 RAM/PCIe 搬一个专家 blob 进 VRAM 层」的量级相符）

=> **缺口被「多出的取数次数」按合理的单价完全吸收**，不需要引入时钟（DVFS）就能解释；DVFS 未被独立排除，但**不是必要项**。

### 7.4 上游触发是什么（不是驱逐）

同批日志里 `conversation cache: ... evictions=0`、`parked=1`，且 `resident RAM: 33.45 GiB` 恒定
=> **不是容量驱逐、不是老化**。触发是**会话是新的**：prompt 缓存未命中（`reused=0`）**同时**该会话的专家路由工作集还没进 VRAM 层。

### 7.5 由此，两个「变慢」观感是同一条链

| 观感 | 中间变量（实测） | 上游触发 |
|---|---|---|
| 空闲后首发慢约 28% | 命中率 95% -> 85%，多 2.1 万次取数 | **新会话**（prompt 未命中 + 专家工作集未驻留） |
| 长上下文慢（43-60 -> 26-41） | 命中率 95-97% -> 81-90% | 长/新上下文的路由专家集合更宽、更不驻留 |

`gen=400` 那条 18 连测里的「冷 / 温」交替（ln945/1056/1165 冷，其余温）正好是这条链的天然对照。

### 7.6 结论与可操作项

1. **不是退化、不是机器问题、不是时钟**：硬件/二进制/config 指纹全未变，命中率才是主导变量。
2. **要每发都快**：**同一会话连续发**（`reused>0`）就是 43-49 tok/s；**每开新会话第一发必然 32-35**，这是设计使然。
3. **要长上下文也快**：方向是**专家层命中率**（容量/驻留面），不是引擎版本、不是时钟。属容量面议题，不在本轮范围。
4. **报告口径**：任何「我们快了多少 / 慢了多少」的结论，**必须带上命中率与 reused 两个协变量**，否则是混比。

## 8 「59.9 那条凭什么高」-- 是 MTP 草稿全中，不是机器能力

机主指出：59.9 与常规 43-49 差得太大。查清了：**那是一条「草稿 22/22 全接受」的运气发。**

### 8.1 全部 >=52 tok/s 的读数（含草稿）

| ln | pt | gen | 解码 tok/s | decode_ms | ms/token | 草稿接受 | 接受率 | **每步净出** |
|---|---|---|---|---|---|---|---|---|
| **254** | 6849 | **32** | **59.9** | 535 | 16.72 | **22/22** | **1.000** | **3.20** |
| **244** | 6849 | **32** | **59.8** | 535 | 16.72 | **22/22** | **1.000** | **3.20** |
| 137 | 27985 | 64 | 55.3 | 1156 | 18.06 | 42/48 | 0.875 | 2.91 |
| 249 | 6838 | 32 | 53.0 | 604 | 18.88 | 16/18 | 0.889 | 2.00 |

**两条 59.9 / 59.8 都是 `gen=32` + `草稿 22/22`**，即每一步的 5 条草稿几乎全被接受。
它们只有 **10 个 verify 步**（`32 - 22`），样本小。**W748 更正**：这**不是运气**而是重复文本的必然结果 ----
用 `bench_prefix.py` 的原 payload 复跑，**8/8 全部 >= 59.2、收敛 64.2**（草稿 22/22 或 23/23 全中）。

### 8.2 解码的分解式

`tok/s = 每步净出 token / 每步耗时`

| 例 | 每步净出 | 每步耗时 | 得 |
|---|---|---|---|
| ln254（22/22） | **3.20** | 53.5 ms | **59.8** |
| ln952（193/237，命中 95%） | 1.93 | 42.2 ms | 45.7 |

=> **差在「每步净出」（3.20 对 1.93，+66%）**，而不是机器更快；每步耗时反而**更慢**（53.5 对 42.2 ms）。

### 8.3 按生成长度分桶（草稿接受率是主因）

| gen | n | 解码均值 | ms/token | **草稿接受率** |
|---|---|---|---|---|
| <=16 | 17 | 32.1 | 33.73 | **0.682** |
| **17-64** | 17 | **44.3** | 23.88 | **0.872** |
| 65-256 | 37 | 39.8 | 25.43 | 0.824 |
| 257-600 | 45 | 39.4 | 26.42 | 0.805 |
| 601-2000 | 22 | 39.4 | 25.51 | 0.752 |
| >2000 | 11 | 40.6 | 24.76 | 0.732 |

=> 草稿接受率**随生成长度单调下降**（0.872 -> 0.732），这正是「短生成看起来更快」的主因；
而 `<=16` 那一档虽短却最慢（32.1），因为固定开销 + 接受率只有 0.682。

### 8.4 公平头条（以后一律用这三档）

| 档 | 解码 | 条件 |
|---|---|---|
| **稳态（正常用）** | **43-49 tok/s** | 同会话连发、`reused>0`、命中率 95%+、gen 400-512 |
| 新会话首发 | **32-35 tok/s** | `reused=0`、命中率 85% |
| 峰值（**W748 已复现，稳态下界**） | **59.9 tok/s**（W748 复跑收敛到 **64.2**） | gen=32 + 草稿 22/22 全中 + hit 96.8% |

=> **口径**：引用「最高」必须同时给 **gen、草稿接受率、命中率**；只报 tok/s 一定会误导。
本报告 §2 的 43.4-45.2 与 §5 的 59.9 之间**不是能力差，是接受率差**。
**W748 更正**：59.9 **可稳定复现**（复刻 8/8 >= 59.2、收敛 64.2）；当时显得不可复现，
只因**生产容器刚重启、专家缓存未热**（hit 0.774 -> 0.963 才把每步从 92 ms 压到 53 ms）。见 `W748_REPRO_59.md`。

### 9.2 真余地一：上游 §4「按位等价」那族，我们只测了 2/12

| 8K / 128K | +6.7% / +6.4% | +4.0% / +4.2% |

**我们只测过 2 个成员**（`EXPERT_V2` = P36 REJECTED / -5.60%；`TSUM` = P37 REJECTED / 中性但不可复现）。
**其余 10+ 个全部未登记** => 本轮已登记为 **P40 / P41 / P42（CANDIDATE）**。

**首选单点 `STRATA_SH_STREAM`**：上游对 UD-IQ4_XS 给 **decode +1.8%**，机制是「共享专家与路由专家跑第二条流做重叠」，
**与 gfx1151 的统一内存无关**，且上游明说它**在 HIP 上默认关（#816）** => gfx906 上未知，是最像白捡的一格。

**警告（必须写进判据）**：该族是为 **gfx1151（统一内存）** 调的，而我们已测的两个同族成员在本卡是**负的**
=> **不能整族照搬**，必须逐个单变量体检；且 `STRATA_HCD_EXACT` 与 §5 若干项依赖 **WMMA**，而 gfx906 **无 MFMA/WMMA**
（W740 ISA 探针：`v_mfma_f32_16x16x16f16` 如期被拒）=> 该类先剔除。

### 9.3 真余地二 / 三：R6 与 R4

- **R6**：`--lookup-chain` / `--suffix-draft`（默认 3）**从未测**。旁证：日志里有 `suffix drafts: 22 windows, 45 of 66 accepted`
  与 `9 windows, 26 of 29`（接受 0.68-0.82）。期望低（与主 MTP 同源）。
- **R4**：`--kv` 四档（fp16 / int8 / q4_0 / k8v4）的**质量门（KLD 主门）从未做**。它只影响**长上下文**容量与速度，不动短上下文。

### 9.4 空白：并发面 0 数据点

`--batch` / `--slots` / `--batch-mtp` 在 P97 登记为「单用户不需要，每槽吃 VRAM」=> **我们从未测过并发吞吐**。
若「最快」指的是「能同时服务多少」，**答案是不知道**（不是"已经最快"）。

### 9.5 天花板：内核面

W740 全二进制普查：IQ4 走 **dp4a + 解包**（`v_dot4_i32_i8` 62,596 条 / `v_dot8_i32_i4` **0** 条），
是 routeK 速率表里**最慢那格**（1,375 对 49,600 GMAC/s）。换 dot8 需**双方 i4**（换权重格式 + 换激活格式），
**不是参数能解决**。布局类改动只在 multi-token 侧赚钱（押预填）。

### 9.6 结论

**单流 + 现 pack + 现引擎 => 参数面已近最优；但不是「最快」。** 剩下三块按性价比排序：

1. **补测 §4 未测开关**（先 `SH_STREAM`；上游对同 pack 给过 output +3.9-5.0%）-- **唯一有上游量级且完全未测的面**
2. **R6 drafter**（低期望）
3. **R4 KV 档**（质量门，不是提速旋钮）

**并发吞吐是空白，尚无任何数据点。**

3. §4/§5 是给**统一内存**（gfx1151，专家不流式）调的；我们是**离散卡 + PCIe 流式**。

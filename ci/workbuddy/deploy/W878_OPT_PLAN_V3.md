## 2 一次源码核实（推翻了我自己刚下的外证结论）

**外证**（本轮上网查到的）：有人用 C99 手写 MoE 引擎，实测 1.90 vs llama.cpp 13.79 tok/s（**7.3× 差距**），
根因是「把 Q4K 权重展开成 F32 再算」= 8 倍带宽 ⇒ 我据此怀疑本仓也在展开。

**核实结果：假设不成立。** `src/kernels/cuda/native_mmvq.cu` 头两行逐字：

```
// Adapted from llama.cpp 3cf03257f219afbe7334045ff7c6a06ac68c627d:
// ggml/src/ggml-cuda/{quantize.cu,vecdotq.cuh,mmvq.cu,common.cuh}
```

文件里有 `native_quantize_q8_1_kernel`（激活量化到 Q8_1）与 `native_q5_k_mmvq_kernel` / `native_q3_k_mmvq_kernel` / `native_q2_0_mmvq_kernel`
（每类量化一个 fused kernel，带 `template<bool SmallK>`）——**这就是外证里说的「fused Q4K matvec」形态，本仓已经是 llama.cpp 血统。**

⇒ 结论：**4-bit 融合不是待办，是既有事实**。这条外证不能套用，只能用来确认「我们没走那条弯路」。
（记一笔方法教训：外证要看「对应物是否存在」，不能一见外部案例就套到本仓。）

## 3 方案（三步，按「便宜→贵」）

### 第 1 步（零成本，30 分钟）：把形状探针正规化

现在的探针每 block 只读 **8 KB**（384 block、每线程 2 次迭代）⇒ 测到的是「小 block 地板」，不是纯带宽。

**改法**：每 block 处理多行 + split-K；**判据**：

| 结果 | 含义 | 下一步 |
|---|---|---|
| 3 MB / M=4 能上 **≥600 GB/s** | 「生产 110 只是 4-bit 元素数的代价」成立 | **合并方向无利可图，decode 线收口** |
| 仍卡在 **300 左右** | 形状（3 MB/384 block）本身就是墙 | 做第 2 步 |

### 第 2 步（一次重启 + 改 kernel，风险中高）：合并一层内的专家 GEMV

一层 31.42 个专家 = 31 个独立 kernel（图里 48 层 × 45 节点 ≈ 2162）。合并成 1 个 grouped kernel：

- 块数从 384 → ~11900，多 wave 填满 60 CU；
- 图节点从 2162 → ~670；
- 探针上限：**1.25×（M=4）–1.7×（M=1）**。

**判据**：窗口时间 41.1 ms → **≤33 ms**（1.25×）为达标；`ms/token` 13.21 → **≤10.6**。
**风险**：verify 是 HIP graph capture 的，grouped kernel 要动 capture 结构与 hand-off；回滚成本 = 一次部署。

### 第 3 步（只有第 2 步达标才做）：把合并推广到跨层

若单层合并拿到 1.25×，跨层合并（2–4 层一起）可再摊薄启动开销；此时图节点进一步下降。
**不建议先做**：跨层要改 KV/hand-off 的层间依赖，风险比单层高一档。

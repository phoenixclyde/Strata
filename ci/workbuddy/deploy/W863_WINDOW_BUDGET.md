# W863 · 窗口预算（123 张表中位）+ dp4a 的真实代价

> 两个起因：① 我一直在引用**单张**相位表（6.89 ms / 15.3%），该用中位；② 我说「HC 的 dp4a
> 版本在源码里存在但被编掉」，**这句是错的**——查全树后 HC 路径一条 dp4a 都没有。
> 这一份把两件事都定死，并按真数字重排优先级。

## 0 结论（三句）

1. **窗口里最大的一块不是 HC，是专家读**：**11.78 ms = 24.9%**（VRAM hits 8.85 + waitB 1.28 +
   PCIe 0.81 + copy 0.84），而 **HC 全部 7.49 ms = 15.9%**。
2. **dp4a 要新写内核，不是翻开关**：`fused_gr.cu` 里没有任何 `__dp4a` / `sdot4`；全树的 `__dp4a`
   只在 DeepSeek 路径（`dsv41/ds4_gguf.cu`）真用。`gr_up_q8_q32_kernel` 是**量化输出**的变体，
   不是 dp4a 矩阵乘。
3. **代价有实测参照**：upstream 自己的注释记着，激活量化成 int8 会让结果差 **0.9498% 相对**
   （`s2_gemv_q8.cu:9`），并明说「dp4a 属于数值定下来之后的阶段」。

## 1 全窗口预算（123 张相位表，表内求和后取中位）

total 中位 **47.22 ms/窗口**（范围 33.19–66.84）。

| 阶段 | 中位 ms | 占比 |
|---|---:|---:|
| **VRAM hits（专家读）** | **8.85** | **18.7%** |
| router + plan + bell | 3.80 | 8.0% |
| q8+qkv / q-idx gemv | 3.24 | 6.9% |
| out-proj（GDN+QSA） | 2.81 | 6.0% |
| shared + quant | 2.42 | 5.1% |
| z（GDN 门控） | 2.15 | 4.6% |
| attention | 1.93 | 4.1% |
| **head** | 1.91 | 4.0% |
| q+q-idx | 1.91 | 4.0% |
| **hc0 down** | 1.76 | 3.7% |
| **hc0 up** | 1.72 | 3.6% |
| **hc1 up** | 1.72 | 3.6% |
| **hc1 down** | 1.70 | 3.6% |
| waitB | 1.28 | 2.7% |
| waitCPU | 1.03 | 2.2% |
| hc0/hc1 norm | 0.59 | 1.2% |
| PCIe grp | 0.81 | 1.7% |
| copy + combine | 0.84 | 1.8% |

**成块看**：

| 块 | 中位 ms | 占比 | 状态 |
|---|---:|---:|---|
| **专家读**（VRAM hits + waitB + PCIe + copy） | **11.78** | **24.9%** | **字节从未算过**（`R26`） |
| **HC**（norm + down + up × 2 流） | **7.49** | **15.9%** | 已知是算术受限（`R32`），dp4a 有上限 |
| **路由**（router + plan + bell） | **3.80** | **8.0%** | 从未单独看过 |
| dense GEMV 其余（q8+qkv / q+q-idx / out-proj / z / ab / rec） | ~10.8 | ~23% | 部分已结（R23 表） |

三条读数：

1. **HC 的 15.9% 是上限，不是净收益**：即使把 down+up 全按 dp4a 的 1.73× 算，
   收益 = 6.9 × (1 − 1/1.73) ≈ **2.9 ms = 6.1% 墙钟**，而且要改数值。
2. **专家读 24.9% 连字节都没算过**。按 11.78 ms 反推，若它跑在 400 GB/s，一个窗口就是 **4.7 GB**
   ——这比 dense 权重（4.26 GB）还多。**这不是"带宽利用率低"，这是"读得太多"**，方向完全不同：
   该优化的是**每 token 命中多少专家**，不是把读做快。
3. **router + plan + bell 8.0%** 对一个 top-k 选择来说大得可疑，且从来没被单独量过。

## 2 更正：dp4a 在 HC 路径里不存在

上一轮我写「源码里 HC 的 dp4a 版本存在但被编掉（`#if !STRATA_GR_FAST_BUILD`）」。
查全树后：**`src/` 与 `include/` 里 HC 相关文件一条 `__dp4a` / `sdot4` 都没有**。

| 文件 | 有什么 |
|---|---|
| `dsv41/ds4_gguf.cu:297-307` | **真的用** `__dp4a`（DeepSeek 路径） |
| `s2_gemv_q8.cu:11` | **注释**：「速度收益在这里就是 `__dp4a`……属于数值定下来之后的阶段」 |
| `s2_expert_grouped.cu:7` | **注释** |
| `iq_kernels.cu:474/3416` | **注释**（sm_60 无 `__dp4a` 的 fallback） |
| `fused_gr.cu` | **无**；`gr_up_q8_q32_kernel` 是「每 block 拥有一个 q8_1 组」的**量化输出**变体 |

⇒ **R35 从"翻开关"变成"写新内核"**。upstream 那句注释还给了代价的实测参照：
激活走 int8 与走 FP16 的输出差 **0.9498% 相对**，他们因此把 dp4a 推到后面阶段。

## 3 按真数字重排

| 新序 | 条目 | 为什么 | 风险 | 上限 |
|---|---|---|---|---|
| **1** | **R26 · 专家读的字节表** | 24.9%，窗口最大块，**字节从未算过**；可能根本不该读这么多 | **零**（纯枚举，不停服） | 若确认读得太多，改的是路由/驻留，不是 kernel |
| **2** | **R36 · router+plan+bell 3.80 ms（8.0%）** | top-k 选择花 8% 不合理，从未单独看 | 零（读源码 + 相位） | 未知 |
| 3 | **R35 · HC 的 dp4a** | 上限 6.1% 墙钟，但要新写两个内核 | **高**：改数值（≈0.95% 相对），须过 KL/argmax | +73% 在 HC 段 |
| 4 | R30' · split-K 上真实内核 | 探针 +12%，正交、可分批 | 中（改求和序） | ~1.5% |
| — | ~~R34~~ / ~~R31~~ | 已撤回 / 判否 | — | — |

**一句话**：我前几轮一直在 HC 上打转，因为它有清晰的"5.6× 缺口"；但窗口预算说
**真正的大头是专家读（24.9%）和路由（8.0%）**，而那两块连账都还没建。
先把账建起来，再决定要不要为 6% 去改数值。

## 1 门的来源：上游自带的 teacher-forced logprob 探针（不是自建）

`generate.cpp:9543-9546` 逐字：

> `STRATA_LOGPOS=<path>`: the teacher-forced log-probability of every token read here
> (every token is committed and `nxt[t]` is the prompt's own next token), appended to `<path>`;
> the last column is the log-probability of `STRATA_LOGPOS_EXTRA` (default 248046, `<|im_end|>`)

实现是 `verify.cpp:2202 Verifier::window_logprobs()`（native 路径）。每行 8 列定值 + `K` 个 `id:logprob`：
`pos / tgt / logprob(tgt) / top_id / logprob(top) / is_top / logprob(extra) / logprob(tgt|without extra)`。
**`is_top` 列本身就是 greedy 一致率**；`extra` 列给出 stop 概率。

方法学出处（上游自己的）：`docs/UNSLOTH_Q4.md` · 配方源头 `bench/results/2026-10-03-v100-prompt-attn:63-66` ·
复现 `bench/results/2026-10-04-rdna2-fp16-prompt:67-72`。

**被否掉的两条路（源码级）**：
- `--dump-logits`（逐位置原始 logits）**在 native pack 上不可达** -- `generate.cpp:11815` 逐字
  *"A native pack never runs the per-token loop `--dump-logits` reads"*；其诊断工具
  `tools/logits_identical.py` **不在 0.1.41 树内**（规格已写、实现未做）。
- 上游的 `bench/results/.../quality.py`（HellaSwag+Winogrande 配对 + 精确 McNemar，明说不需要 logprobs）
  其两个数据集**不在树内**。

### 1.1 评分区间要靠**两次请求**（`--short-read` 的语义）

`generate.cpp:9397`：`if (no_short || b - a > req_short_read) return false;`
=> **只有「本次 fresh 文本 <= `--short-read`」时整段才走 verify 窗口被评分**。

=> 先发 `[长首消息 + 固定回复]` 灌前缀，**再**发 `[... + 尾段]`，此时 fresh 只剩尾段。
探针实测（`--short-read 1024`）：

```
request A: prompt  25222 tokens =      0 reused + 25222 read (434 tok/s)
request B: prompt  25662 tokens =  25217 reused +   445 read
logpos  : 448 行，位置 25217..25660          <- B 的 445 个 fresh token 全部被评分
```

**本车每一臂都通过这道方法自证**（5 臂 x 7 行，全部 `reused` 与 A 的 prompt 对齐、`read` <= 1024）：

```
f16a/i8/q40 皆同形：
  25222 =      0 reused + 25222 read      25662 =  25217 reused +  445 read
  38845 =      0 reused + 38845 read      39205 =  38840 reused +  365 read
 110992 =      0 reused +110992 read     111574 = 110987 reused +  587 read
                                         111568 = 110987 reused +  581 read
```

=> **1,394 个配对位置/臂**，两臂评分的 token 序列**逐字相同**（同一段文本、同一 teacher-forcing）。

## 3 结论

1. **门建成了，而且比原计划强**：用上游原生的 teacher-forced 探针，**self 对照 = 0 / argmax 100%**，
   读数下限为零（routeK/vLLM 的 self 是 2.97e-3，噪声底把信号吞掉）。**这是本项目以后所有质量门的首选件。**
2. **KV 档位对分布的影响是真实的、可复现的、剂量单调的**：`int8 < k8v4 < q4_0`，
   生产值 `k8v4` 相对 fp16 在 **18.1% 的位置上 argmax 不同**，KL 高于上游"只改舍入顺序"对照 **6~13 倍**。
3. **但方向不可判**：PPL 反降、top1 命中的反升、自身 top-1 logprob 反降、停止质量反降，**四个标量互相"矛盾"**
   => **分布门只能说"实质不同"，不能说"更好/更坏"。** 要判质量必须做**任务级门**（needle /
   HellaSwag+Winogrande 配对 McNemar），那是下一步。
4. **不改任何参数**：`P04 --kv k8v4` 的值不动（本件是它的证据，不是推翻它）。改与不改要在任务级门之后才谈。

## 4 限制（照实写，含一条未排除的替代解释）

1. **未排除的替代解释：专家驻留路径。** 各臂的 `--expert-cache auto` 因 KV 占量不同而不同
   （fp16 8047 槽 / k8v4 **9761** / q4_0 10125），而引擎对**命中**与**未命中**的专家走不同代码路径
   （日志 `R4 hit path ON` / `token graph hit path`）=> **驻留集合不同可能带来舍入顺序差异**。
   自比臂（两遍 fp16）驻留完全相同，所以它给 0 **不能**排除这条。
   **支持 KV 解释的证据**：差异随上下文档显著变大（tier1 的 KL 只有 tier2/3 的 1/4 ~ 1/5），
   而驻留差异在各档是恒定的。
   **便宜的排除实验**（下一步，约 2 臂）：两臂都显式给同一个 `--expert-cache N`，
   使驻留集合严格相同，只留 `--kv` 一个变量。
2. **绝对量级依赖估计器**：`kl_inter` 只有 `kl_prop` 的一半（见 2.4）。**排序稳、绝对值不稳。**
3. **分档不能当"随上下文增长"的因果证据**：三档用的是**不同文本**，所以 tier 间差异同时含
   **文本难度**与**上下文长度**两个因素（tier2 比 tier3 还差，即为此）。同档内的臂间比较是干净的
   （配对在同一段文本上），**跨档比较不是**。
4. **一机一 pack 一版本**：只有 gfx906 / 本 pack / 0.1.41。上游的 KV 规格表（`turboquant/config.py` 的
   `4bit_nc 3.8x/+2.71%` 等）是**上游评测集**的代价，**不是本配置的**（本配置 hybrid，只有部分层吃 KV）。
5. **任务级门未做**：本件只到分布层。
6. **`--short-read 1024` 与 `--adapt-every 100000` 是仪器**：五臂完全相同，且**不是生产配置的一部分**；
   `--max-context 262144` 与生产相同。

## 7 一并查出并修掉的一处**工具缺陷**：五断言里那条「P 编号齐」是空心的

`mem_slim.py` 的 `assertions()` 原文逐字：

```python
nums = sorted(int(m) for m in re.findall(r'\bP(\d+)\b', text))
chk(bool(nums), 'P 编号齐', 'n=%d' % len(nums))
```

**它只判「至少存在一个 P 编号」，不判任何具体编号是否还在**；`_land` 里两处"独立核验"同样只写
`len(set(...)) > 0`。也就是说：**这条判据不可能因"编号丢失"而红。**

**本波实测的后果**：走 `auto` 时反解器的 L3/L4 缩减把
**`P50/P42/P41/P97/P39/P46-49` 从 `MEMORY.md §4` 整段删掉**、把 §3 那行的**读数**删掉，
而五断言**全部报 PASS**、文件照常落盘。（我上一波以为"判据抓到 P40 丢失"是技能在起作用
---- 其实是**我自己 dry-run 脚本里的集合比较**在做；本波直接走 `auto`，这个比较就没人做了。
=> 这是一条"**我依赖的保护其实是我自己的临时脚本**"的教训。）

**修法**：三处判据全部改成**与改前文本的集合差**（`assertions(text, tag, ref)`，`ref` 默认取盘上
`MEMORY.md`；两处独立核验用 `t0`），任何编号丢失即 FAIL、**不落盘**。

**正控与反例**（技能明令：审计器自身判据必须先跑正控与反例）：

| 控制 | 结果 |
|---|---|
| 原文不动（负控，必须 PASS） | `[PASS] P 编号零丢失 n=18` |
| 故意删 `P43`/`P38`/`P10`（正控，必须 FAIL） | **`[FAIL] P 编号零丢失 lost=[10, 38]`**（43 未删净，故不在丢列表 => 判据精确） |

**新判据第一次运行就抓到一次真丢失**：修正波首试 `lost=[36, 37]`，`AUTO ABORT`、未落盘；
把带 P 编号的行逐一用内容 op 保护（`protect` 机制：内容 op 改过的行不被 L3/L4 削减）后才通过。

**最终态**：`MEMORY.md` **2872 字符**（对 3000 余 128），P 集合
`{0,1,10,23,28,29,30,31,32,33,34,36,37,38,39,40,41,42,43,46,50,97}`，
归档 `Z-30`，独立核验 7/7 **含新的 `P 编号零丢失`**。

## 8 驻留对照（W768）：**§3 的因果归因不成立 -- 本件的第 2 条结论作废**

W767 §4 限制 1 记了一条未排除的替代解释：各臂 `--expert-cache auto` 随 KV 占量而不同，
而引擎对**命中**与**未命中**的专家走不同代码路径（`R4 hit path ON` / `token graph hit path`）。
W768 把它做成了**正面反例**：固定 `--expert-cache`，**只改这一个数**，`--kv` 一动不动。

| 比较 | `--kv` | `--expert-cache` | **实测驻留** | 驻留差 | n | KL mean | KL median | argmax | top10 |
|---|---|---|---|---|---|---|---|---|---|
| `f16a` vs `f16b`（W767 self） | 同 fp16 | auto | 8047 -> 8047 | **0** | 808 | **0.00000** | 0.00000 | **100.00%** | 100.00% |

每臂起车前都从备份恢复同一份 profile，md5 `ff1bc6544d3f...`。）

**读法（这张表把话说死了）**：

1. **驻留相同 -> 恰好 0**（`f16a` vs `f16b`，两遍 fp16、同 8047）。
2. **驻留不同、`--kv` 完全不变 -> 0.36554 / argmax 87.38%**（`rc9` vs `rc6`，只把 `--expert-cache` 6000 改成 9000，
   实测驻留 +1224）。**这是一个纯粹容量旋钮造出来的差异。**
3. 主车的差值 **0.40416 落在"驻留对照 0.366"与"KV 对照 0.516"之间** => **无法把主车的差归因给 `--kv`。**

=> **§3 的第 2 条结论（"KV 档位对分布的影响是真实的、可复现的、剂量单调的"）作废**。

**更正后仍然成立的部分**：

- **门本身成立且可用**：self 对照恰好 0，说明这套 teacher-forced 探针在本卡是**逐位确定**的，
  读数下限为零（§2.1、§7 不变）。
- **量级对照成立**：KV 档、驻留、以及上游的舍入顺序对照（0.023-0.090）**都是"分布会动"**，
  但**本卡上"动"的量级可以由一个非语义旋钮产生** => **分布层面的差异在本卡不是质量判据**
  （这与 §2.6 里"四个标量互相矛盾"是同一件事的两种表现）。
- **`--kv` 与 `--expert-cache` 各自的效果量级相当**，是两条**独立**的观察；
  要分开必须让驻留严格相等（见下）。

**为什么这一车仍然改不了"驻留"**：`rf6` 与 `rc6` 的 `--expert-cache` 同为 6000，但 fp16 的 KV 多占
VRAM，实际驻留仍差 489 槽 => **本车没有一对是"驻留严格相等"的**。

**下一步（已定方案）**：把 fp16 臂的 `--max-context` 降到 `262144 x 816/2112 = 101376`，
使其 **KV 占量与 k8v4@262144 相等**，两臂都 `--expert-cache auto` => 自由 VRAM 相同 =>
**实测驻留数相同（这是"驻留已固定"的门）**，此时再比才是干净的 `--kv` 效应。
（我们的 prompt 最长 39205 token，远小于 101376，故降 `--max-context` 不截断、也不改这段的算术。）

**另有价值的一点**：`--expert-cache` 这个**容量**旋钮能在同权重同输入下把分布推动 KL 0.37，
这是引擎层面的数值敏感度事实，值得单列（也值得回头看是否与 `native_moe_combine_*_hits_gated`
这类"命中专用合并"的累加顺序有关）。

## 9 落盘过程中又查出**两处**压缩器/判据缺陷（同一族：静默的语义丢失）

W767 §7 修的「P 编号齐」只是第一处。把 W768 的结论写进 `MEMORY.md` 时又撞上两处。
三处都属同一族：**判据看不见的那种丢失**。

### 9.1 `protect` 的行号基准错了（T315）

`mem_slim.py` 的 `cmd_auto` 原文：

```python
for op in plan['ops']:
    for n, ln in enumerate(t0.split('\n'), 1):   # t0 = 改**前**的文本
        if op['old'] in ln: protect.add(n)
base, clog = apply_ops(t0, plan['ops'])           # base = 改**后**的文本
... _auto_solve(base, target, protect=protect)
```

行号是对**改前**文本算的、却拿**改后**文本用。任何**增删行**的 op（本波有一次"3 行并 1 行"、
一次删行）都让其后的行号整体位移 => **保护集指错行** => **本波刚写进去的内容照样被 L3/L4 削掉**。
（上一波看着能用，只是因为那些 ops 全是"单行改长"、不位移。）

**已修**：改为在 `base`（改后）上定位每个 op 的 `new` 文本所在行。
**控制测试**：夹具含"3 行并 1 行 + 删 1 行 + 改 1 行"，新算法给 `protect=[2,3]` 与预期一致，
**旧算法给 `[6]`（指错行）**。

### 9.2 L3「去括号补充（保留主句）」会删掉最关键的那一句

`_auto_solve` 的 L3 是"去括号补充"：把行内 `（...）` 拿掉。**只要关键结论写在括号里，它就被整段删除**。
实测：我把 W768 的核心结论写在 `（同 --kv 只改 --expert-cache ... 即给 KL .366 / argmax 87%）` 里，
一次 `auto` 之后**那半句消失了**，而五断言（含新的 P 判据）**全绿**。

**对策**（已落实）：(1) 关键结论一律写在**括号外**；(2) 该行由本波的内容 op 保护（保护机制修好后有效）。

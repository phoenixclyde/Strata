## 0 先说结论

1. **Avalon 是真实存在且直接对标我们的**：它以 **Qwen3.8-Flash-Next（512 专家 / 10 活跃 / 48 层）** 为唯一优化目标，
   而 README 的对比表里把 **Strata 0.1.43 (HIP)** 当基线。**同一模型、同一 MoE 结构。**
2. **它 91.0 t/s（MTP）vs 它的 Strata 基线 61.9**；**我们 0.1.55t 是 75.8** —— 比那个基线快 22%，但**仍比它慢 17%（1.20×）**。
3. **差距主要不在架构，在卡**：它是 RX 7900 XT（RDNA3，fp16 **68.6 TFLOPS**、96 MB Infinity Cache），
   我们是 MI50（Vega20，fp16 **26.8 TFLOPS**、L2 **4 MB**）。W879 已证明我们的 decode 是**算术受限**（不是带宽受限），
   所以 2.6× 的 fp16 算力差会直接映射到 1.2× 的实测差 —— **我们并没有做错什么**。
4. **它有 3 条具体做法，逐条查完只剩 1 条能用**（见 §4）：
   ①`--mtp-draft-vocab` **= 真候选**（`X4`，MTP 逐位接受仅 47%）；
   ②宿主 CPU 1.95 ms —— **不是优化点**（CPU 86 μs/专家 vs PCIe 249 μs，引擎选得对）；
   ③等长 batch —— **我们已有**（`equal_chunk`，注释 `EQUAL size (no tiny tail)`）⇒ 判否。
   另：GDN kernel 融合（它 53→39 次启动）**形态不同、无可抄**（我们 GDN 层已拆 8 个计时阶段 = 11.64 ms/窗口 = 23.9%，W883）。

## 1 同表对比（全部是自报数，不是我推的）

| 项 | Avalon（RX 7900 XT 20 GB） | 它测的 Strata 0.1.43 | **我们 0.1.55t** |
|---|---:|---:|---:|
| 生成，短 prompt，**无 MTP** | 62.4 t/s | 49.0 | — |
| 生成，短 prompt，**MTP** | **91.0 t/s** | 61.9 | **75.8**（T=3.11） |
| 256k 上下文 / 已填 250k，无 MTP | 50.5 | 41.8 | — |
| 同上，MTP | 69.8 | 50.0 | — |
| 最大预填充 | 1,613 t/s | 1,376 | 1,475（温）/ 4,093（全量加权，含 89% 复用） |
| 专家缓存 | **9–14 GiB**（20 GB 卡的 45–70%） | — | **21.79 GiB / 7463 槽**（32 GB 卡的 64%） |
| 命中率 | 未给数字，靠 LFU 准入 + 热度预填 | — | **98.9%**（246525/249243） |
| 量化 | Avalon IQ3_KS hybrid（2–4 bit 专家） | IQ3_S（GSQ-RCO） | **UD-Q4_K_XL**（4 bit，2.99 MB/专家） |

一个反直觉的点：**它的专家缓存只占 20 GB 卡的 45–70%，我们占了 64% 且命中 98.9%** ——
也就是说**我们的 VRAM 条件更好**，却更慢。这进一步指向「卡本身」。

## 2 它的架构：我们哪些已经有

|---|---|---|

## 3 差距的真实来源：算力，不是架构

| 量 | MI50（我们） | RX 7900 XT（它） | 比 |
|---|---:|---:|---:|
| fp16 算力 | 26.8 TFLOPS | **68.6 TFLOPS** | **2.56×** |
| 显存带宽 | 1024 GB/s（实测块读 884） | 800 GB/s | 0.78× |
| L2 / Infinity Cache | **4 MB** | **96 MB** | 24× |
| 实测 decode | 75.8 t/s | 91.0 t/s | **1.20×** |

**算力差 2.56× 只换来 1.20× 的实测差** —— 说明它自己也受限于别的东西（PCIe 3.0、CPU 算专家、4.29 bpw 更重）。
按 W879 的结论（我们是算术受限），算力比才是硬天花板，而它并没有吃到 2.56×（因为它的专家有 30–55% 在 RAM）。

⇒ **我们的 75.8 t/s 在 MI50 上已经接近这张卡能给的上限**，可提升余量 < 20%，且要靠抄它的具体技巧。

## 4 三条可以直接测的（按性价比排序）

### ① `--mtp-draft-vocab`（账本 **P47 CANDIDATE**，一直没测）

Avalon 逐字：*"MTP draft head（对 **65k 高频 token 截断 LM head**）"*，且它的 MTP 让生成从 62.4 → 91.0（+46%）。

我们现状：MTP 逐位接受率只有 **47%**（`spec depth 14/30`，W874），suffix 100% 但只覆盖重复文本。
**缩小 draft 词表能让 draft 步更快**（head 从 151k 降到 65k），代价是接受率可能略降。

- 成本：一次重启（`--mtp-draft-vocab <file>`，或文件开关）
- 判据（P188 规矩）：`ms/window` 41.1 → ≤38（-8%）为达标；旁证 `spec depth` 逐位接受率不降超过 3pp
- 风险：低（只影响 draft，不影响 verify 的正确性）

### ② ~~查清 `per-layer host` 里那 1.95 ms CPU~~ —— **已查，不是优化点**

查法：decode timing 的 `CPU %.2f` 取的是 `(d1.run - ds0.run)/w`（`generate.cpp:17250` 的参数表），
即 Verifier 的 host-run 累加器；同一行还打着 `per layer-window: CPU experts 0.47`。
换算：0.47 专家/层-窗口 × 48 层 = **22.6 个专家/窗口**，1.95 ms ÷ 22.6 = **86 μs/专家**。

对照两条路：
| 路径 | 每专家代价 |
|---|---:|
| CPU 算（现状） | **86 μs** |
| PCIe 搬 2.99 MB @13.2 GB/s + GPU 算 | 227 + 22 = **249 μs** |

⇒ **CPU 快 2.9 倍，引擎选它是正确的**。这 1.95 ms 不是「采样开销」，是「1.4% 的冷专家走 CPU」的必然代价，
换成走 PCIe 反而要 5.6 ms（+3.6 ms/窗口）。**这条排除，不抄。**

（Avalon 的「后端贪心采样 0.37→0.02 ms/步」是另一件事，我们的 `commit/emit` 只有 0.05 ms/窗口，**没有这个开销**。）

### ③ prompt 等长 batch 切分 —— **判否，我们已有（W883 查源码）**

Avalon 逐字：*"prompt 按等长 batch（`-b`/`-ub 9536`）切分，避免短末批的开销 → 新 19k prompt 从约 1,410 提升到 1,660 t/s（+18%）"*。

~~我们不确定是否「等长」~~ —— **查过了，我们本来就有，这条判否。**

`generate.cpp:8570` 的 `planned_chunk` → `equal_chunk`（`:8556-8564`），注释逐字：

> *"a longer one reads in n = ceil(tokens / plan) chunks of **EQUAL size (no tiny tail)**, at most `cap`"*

实现：`per = tokens / n + (tokens % n != 0)`，再向上取到 256 的倍数，**末批和其余批同长**。`--batch` 路径那条
（`:17819`）注释更直接写着 `// equal chunks, no tail`。生产无 `--batch`，走的是同一族的 `planned_chunk(tokens, o.prefill_chunk, pf_plan_chunk)`（`:15126`）。

这跟 **R18 撤回**是同一条代码：R18 当时的判词是「生产 chunk 已是 8192 上限、4096/8192 同为 18.5 TFLOPS ⇒ 无空间」，
现在补上另一半——**切分本身就是等长无尾的**。⇒ **不进队列，不重测。**

## 5 明确「不抄」的

| 它的做法 | 为什么不抄 |
|---|---|
| Hosted MoE（CPU 并行算缺失专家） | 我们命中 98.9%，缺失只有 1.1%；CPU 算一个 3 MB 专家约 100+ μs，比 GPU 的 22 μs 慢 5 倍。**它这么做是因为 20 GB 装不下，我们有 32 GB** |
| 借还机制（KV tail 归缓存） | 我们的弹性 KV 初值只 0.27 GB，可借的尾巴量级远小于它的 256k×17KB=4.4 GB |
| Avalon IQ3_KS 量化 | 它自己测的困惑度：IQ3_KS 1.443 vs **UD-Q4_K_XL 1.316** —— **我们现在用的量化质量更好**；换 3-bit 是拿质量换速度，不在调参范围 |
| 96 MB Infinity Cache 的依赖 | 硬件没有，只能承认 |

## 6 一句话

**Avalon 把我们当基线、在同一模型上做到 91 t/s（基线 61.9），而我们 0.1.55t 已经是 75.8，比它测的基线快 22%。**
它赢的那 20% 主要来自 RDNA3 的 2.6× fp16 算力与 96 MB Infinity Cache；
架构上我们没有漏掉机制。**可抄的三条已逐条查完，只剩 `--mtp-draft-vocab`（`X4`）一条**；宿主 CPU 与等长 batch 均判否（后者我们已有 `equal_chunk`），GDN 融合不适用 —— 三项判词都在 `W832` §5.3 ——
第一条最便宜（一次重启，账本里已挂 CANDIDATE 一年没测）。

## 0 结论（三句）

1. **全表扫完**：9 个形状 × ncols 1..8 × R∈{1,2,4}，共 **216 格**（`sweep_cols.txt` 144 + `sweep_r24.txt` 72）。
   实测表已生成（§3），可直接替换树里的公式。
2. **现在树里的公式有真缺陷**：ncols=1 时它选 R=4，整层 **0.982×（比不改还慢 1.8%）**；
   多个格子的选法比最优慢 8–95%（§2）。**原样上生产会在最常见的窗口尺寸上倒扣。**
3. **R23 的真实墙钟收益 ≈ 2.8%，不是 1.52×**。原因不是补丁不行，而是**生产的典型验证窗口是 T≈2，不是 6**
   （三证见 `W863_R22_DENSE_BYTES.md` §5）。1.52× 只在 T=6 的窗口上成立，而那种窗口是少数。

⇒ **按项目铁律「引擎级 A/B 只判 ≥5%」，R23 单独上生产是测不出来的。建议与「窗口长度」那条线合并批处理**（§5）。

## 2 树里那条公式的缺陷（逐条实测）

树里现在（`patch_wave_rows.py` 打的）是公式：

```cpp
int R = 2;
if (ncols <= 2 && n_in/32 >= 32 && n_out >= 2048) R = 4;
while (R > 1 && n_out / (4*R) < 120) R >>= 1;
```

| 缺陷 | 实测代价 |
|---|---|
| **ncols=1 选 R=4**（qkv / out / q / gate） | qkv 58.4→63.8 **慢 9.3%**；out 28.4→31.3 **慢 10.2%**；整层 **0.982×** |
| **ncols≥3 一律 R=2**，但 qkv/out 在 n3..n4 上 R=4 更快 | qkv n3 73.3→62.9（R=4 快 **16.5%**）；out n4 44.1→41.0（快 7.6%） |
| **`n_out/(4R)≥120` 把小矩阵一律压回 R=1** | HC down n4..n8 上 R=2 快 **45–95%**；k/v n5..n8 快 8–12% |
| `n_in/32>=32` 这个条件没有对应的实测依据 | 未发现问题，但属未核条件 |

**最要紧的是第一条**：ncols=1 是**最常见**的窗口（草稿被 `--spec-min-p 0.70` 截断时就是 1 列，
以及一切非投机步），公式在那里倒扣 1.8%。

## 3 实测表（可直接替换，文件 `albus/w863/measured_table.cpp.txt`）

```cpp
// W863: MEASURED rows-per-wavefront table (real kernel, production flags, gfx906).
// 0 = R=1 (the old behaviour). Cell = fastest of R in {1,2,4}, kept only when it beat R=1
// by >= 3 % on that shape at that column count; ncols=1 forced to R=1 (differences there
// were not reproducible across arms). Measured 2026-11-01, 40 iters/cell.
static const struct { int n_in, n_out; const unsigned char r[8]; } kWaveRows[] = {
    { 2560, 10240, {0, 4, 4, 4, 2, 2, 2, 2}},   // GDN qkv
    { 2560,  6144, {0, 2, 2, 2, 2, 2, 2, 2}},   // GDN gate
    { 6144,  2560, {0, 2, 4, 4, 2, 2, 2, 2}},   // GDN/QSA out
    { 2560, 12288, {0, 2, 2, 2, 2, 2, 2, 2}},   // QSA q
    { 2560,   512, {0, 0, 2, 2, 2, 2, 2, 2}},   // QSA k/v
    {10240,   320, {0, 0, 2, 2, 2, 2, 2, 2}},   // HC down
    {  320, 10240, {0, 2, 2, 2, 2, 0, 2, 0}},   // HC up
    { 2560,   640, {0, 0, 2, 2, 2, 2, 2, 2}},   // shared g/u
    {  640,  2560, {0, 0, 2, 2, 2, 2, 2, 2}},   // shared down
};

int wave_rows_for(int ncols, int n_in, int n_out) {
    if (g_wave_rows > 0) return g_wave_rows;          // STRATA_MMVQ_WAVE_ROWS / setter
    if (ncols < 1 || ncols > 8) return 1;
    for (const auto& e : kWaveRows)
        if (e.n_in == n_in && e.n_out == n_out) {
            const int R = e.r[ncols - 1];
            return R == 0 ? 1 : R;
        }
    return 1;        // an unmeasured shape keeps the old behaviour
}
```

设计取舍：**按精确 (n_in,n_out) 匹配**而不是 n_out 分档。理由——本模型的 dense 形状只有这 9 个，
分档会在档内混入不同 n_in 的张量（例如 2560→640 与 640→2560 同一个 n_out 量级）；
未测形状一律 R=1，fail-safe。

## 4 R23 的真实价值（用真实层组成 + 实测相位算，不用「9 矩阵」口径）

### 4.1 每窗口节省（T≈2，用实测表）

| 层类 | 张量 | 每层节省 |
|---|---|---:|
| GDN ×36 | qkv (69.3→59.5) 9.8 + gate (40.1→30.5) 9.6 + ssm_out (36.1→32.6) 3.5 + HC up ×2 (13.7→12.9) 1.6 | **24.5 µs** |
| QSA ×12 | attn_q (67.0→55.5) 11.5 + attn_output (36.1→32.6) 3.5 + HC up ×2 1.6 | **16.6 µs** |

⇒ 36×24.5 + 12×16.6 = 882 + 199 = **1.08 ms/窗口**；head 按 n=2 再省 ~0.2 ms ⇒ **≈1.3 ms**。

### 4.2 折成墙钟

| 口径 | 值 | 算法 |
|---|---:|---|
| decode 窗口总时长 | 44.98 ms | 相位表 100 窗口 |
| R 表可加速的部分（native dense） | 8.37 ms（18.6%） | 相位表三阶段之和 |
| 在 T≈2 的实际增益 | 1.156× | §1.1 |
| **净节省** | **1.3 ms = 2.9% 墙钟** | 1.08/8.37 × 18.6% ≈ 2.4%，含 head ≈2.9% |
| 若 T 能到 6（同一补丁） | 1.593× ⇒ **6.0% 墙钟** | 43% × 18.6% |

⇒ **同一个补丁，价值完全由「窗口长度」决定**：T=2 时 2.9%，T=6 时 6.0%。
W862 报的 1.52× 是**每层微基准**的比值，不是墙钟，二者差 18 倍（1.52 vs 0.029 的加速比换算）。

### 4.3 为什么不能靠生产 A/B 判

- 铁律：`引擎级 A/B 只判 >=5%`（`MEMORY.md` §3，来源 W809）。
- 2.9% < 5% ⇒ 生产 A/B 的结论必然是「噪声内」，白停一次服。
- 微基准能判（本文件即是），但它判的是 kernel，不是墙钟。

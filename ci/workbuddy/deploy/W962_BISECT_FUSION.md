# W962 · 版本 bisect：−6% 就出在 fusion 那一次提交（`#29948`）

- 日期：2026-11-04 20:1x–20:3x
- 目的：`W960` 测到 0.8.0 的 prefill 比我们慢 6%，但不知道是哪一串改动造成的。用**中间版本**定位，而不是猜。
- 一句话：**0.7.0 = 594.1 tok/s**，落在 0.4.1 的区间里（599–604），而 0.8.0 是 552–577
  ⇒ 那 5–6% 是 **0.7.0 → 0.8.0 之间唯一的大改：MMQ fusion（`#29948`）**。

---

## 1 三个点

| 点 | 树 | `mmq.cuh` 状态 | prefill（tok/s） | 样本 |
|---|---|---|---:|---|
| **A** | 0.4.1（生产） | 1605 行，无 prec/J_best | **601.74 / 604.28 / 599.17**（均 601.7） | 3 |
| **C** | **0.7.0**（`620d222`） | 1588 行 + prec + `J_best`，**无 fusion** | **594.11** | 1 |
| **B** | 0.8.0（`b12099`） | 1659 行 = fusion 版 | 568.41 / 552.15 / 576.82（均 565.8） | 3 |

- **C 与 B 差 28.3 tok/s（5.0%）**，且 C 高于 B 的最大值（576.8）17 tok/s。
- **C 与 A 差 7.6 tok/s（1.3%）**，单次样本，尚在 A 的离散度边缘（A 的 SD 2.6，range 599–604）。
- 0.7.0 的 `ggml` 版本 = **0.27.0**（0.4.1 是 0.24.0，0.8.0 是 0.28.0），`J_best` 出现 3 次 —— 已实查。

⇒ 归因：**fusion（10-25，`c49edf09`，283 行）拿走 ~5%**；从 0.4.1 到 0.7.0 的其它所有改动合计约 1%（可能更小）。
这与 `W961 §4` 的硬证据对得上：0.8.0 的 `mmq.cuh` **逐字节等于** fusion 版，之后再没动过。

## 2 为什么"编得过"却没发现它慢

fusion 自述 "The MMA loop is unchanged: same tile, warp layout, vec_dot and one `sum[]` per thread"。
**MMA 循环确实没变，变的是 loader 与写回**（`mmq-load-tiles.cuh` 322 行差异）：为了把 gate/up 交错进同一个 tile，
loader 多了第二个权重指针与交错寻址。非 fused 路径虽然 `has_fusion=false`，仍与它共享同一份模板骨架 ——
寄存器压力/取数序变了，指令数就变了（`W955` 量到 0.8.0 的对象大 15.9%、fatbin 大 10.9%）。

## 3 一个顺带的观察（未采信）

0.7.0 的 decode = **24.39 tok/s**，而 A/B 都在 19.0（A 有一次 40.4 的异常）。
单次样本 + `W958` 已证 decode 受专家驻留抖动影响（2× 级），**不作结论**；要判需要 3 次以上、且固定驻留。

## 4 结论

1. **0.8.0 整树升级不划算**：−5~6% prefill，收益不可见（`mmq-config-gcn.cuh` 逐字节相同）。
2. **0.7.0 也不划算**：相对 0.4.1 约 −1.3%（单次，需补样本），没有正向收益。
3. ⇒ **留在 0.4.1**；若将来要新基线的某个修复，按 `W961 §5` **摘单个修复**（首推 `#29953` 的越界 padding）。
4. 这条也修正了 `W954` 的原始假设（"4 个 minor 的修正能换收益"）：**四个 minor 里没有对 gfx906 prefill 的正向改动，
   只有 fusion 这一次负向改动**。

## 3 一个以前没记过的事实：短档的"贵"是固定开销，不是算力

用 2.1 的表反推每 token 的固定成本（`ms = a + b·tok`，用 0–128 与 4–16K 两点估）：

```
短档 70 tok:  1008 ms  → 每 token 14.4 ms
4–16K 档:     2039 ms/1k → 每 token 2.04 ms
⇒ 差值 12.4 ms/token × 70 ≈ 866 ms 与 token 数无关的固定部分
```

这 866 ms 里已经知道有两块（W857/W860 相位）：`dequant`（MMQ 下的 group gather + q8_1 量化）216 ms@248tok、
`wait copy`（等专家 blob 拷贝事件）137 ms@248tok，两项就 **353 ms**，占固定开销的 41%。
剩下的大头是**首个 chunk 的 staging + 专家冷读**（PCIe 1.1–3.8% 那部分）。

> 这与 W804「1–3K 瓶颈是 staging + CPU」方向一致，但把量级钉住了：**短档每 token 贵 9.5×，其中 41% 已定位**。

## 5 停服许可制（写死，后续所有轮遵守）

**背景**：单卡、模型驻留 33.5/34.3 GB ⇒ **起不了第二个实例**，任何引擎级 A/B 都必须停服。
而机主**正在用这个模型干活** ⇒ 停服 = 直接打断他。

规则：

1. **默认不碰生产**。需要停服的实验，一律先攒批（一次窗口验多件事），把「要停多久、验什么、回滚怎么做」写成一条，**等机主说"可以停"**。
2. 允许在**未经许可**下做的：读日志、读源码、CPU-only 构建（必须 `nice 19` + `taskset` 限核）、
   `--rm` 容器里的编译/探针（不挂 `/data`、不占 GPU 或只占数秒）。
3. **禁止**：未经许可 `docker stop/start/rename`、换 `/data/bin` 下的二进制、改 config 里的 `exe`/`env`。
4. 每次停服窗口结束后，**必须**：`/health` ok + `TIP-OK` + `restarts=0` + 记 `started` 时间。
5. 停服窗口的**最小化**手段（下次用）：先把要验的两三件事排进同一个窗口，单次重启验完；
   不必为每一臂单独重启（本轮 A/B 重启了 4 次 = 4 × 5 分钟重载，这是浪费，也是堵机主的直接原因）。

## 2.4 【自查推翻】"长生成衰减"不存在 —— MTP 接受率与长度基本无关

§2.2 里我看到「120K/4480 gen → 59.9%」就推了"更像长生成后期衰减"。**这个推断是错的**，
用同一份日志做二维分桶（`albus/w860/mtp_decay.py`，3254→5356 条有效样本）直接否掉：

| prompt \ gen | 0–64 | 64–256 | 256–1024 | 1024–4096 | 4096+ |
|---|---:|---:|---:|---:|---:|
| 0–1024 | 79.3 (155) | **68.5** (476) | 70.7 (127) | 70.6 (2) | — |
| 1K–8K | 82.6 (95) | 90.0 (192) | 88.5 (173) | 68.1 (8) | — |
| 8K–32K | 76.7 (30) | 80.3 (38) | **94.1** (306) | 62.9 (13) | 68.9 (9) |
| 32K–131K | 71.7 (36) | 86.1 (548) | 81.7 (751) | 77.9 (394) | 77.7 (69) |
| 131K+ | 81.4 (1) | 86.3 (50) | 83.3 (87) | 79.9 (33) | **75.8** (30) |

**只看 gen 维度**（接受率）：78.8 / 79.5 / **83.3** / 77.4 / 76.5（%）—— **中间最高、两端略低，没有单调衰减**。

**最硬的反例**：日志里有两条 32768 token 的生成，接受率 **97.3%**（prompt 71 195）与 **92.1%**（prompt 90 962）。
如果"长生成会衰减"，这两条不该出现。

**只看 prompt 维度**：0–1024 档 **69.8%** ← 最低；1K–8K **86.1%** ← 最高；8K–32K 82.3%；32K–131K 79.2%；131K+ 77.9%。
⇒ 长上下文只掉 **6–8 个百分点**（86.1 → 77.9），远不是断崖。

### 结论（R20 改判）

| 原判 | 现判 |
|---|---|
| 长生成导致接受率衰减，值得调 `--spec`/`--spec-min-p` | **不存在这个衰减**。接受率由**内容可预测性**主导，不由长度主导。那条 59.9% 是**单次异常值**（大概率是代码/表格类内容），不能当规律 |
| — | 真正稳定的规律是：**短 prompt（≤1K）接受率最低 69.8%**，与 R19「短档每 token 贵 9.5×」同向、同一个根因（**上下文少 ⇒ draft 没有信息可依**） |

⇒ **R20 结案为"无需调参"（DONE_NEG）**，并入 R19 一起看。
**教训**：单条极端样本不能推机制，至少要看二维分布——这是本轮第二次自查推翻（前一次是 R18 的 chunk 前提）。

### 6.1 源码注释自己写了瓶颈

`src/kernels/cuda/fused_gr.cu:723-731`（hc read v3 的注释，逐字）：

> The norm kernel runs on only T blocks (~16 us of pure latency per call) and `down` on **41 blocks (~280 GB/s)**.
> v3: `down` is split over (row group, stream[, column half]) = **164 or 328 blocks** …

**41 个 block 对 60 CU 的 MI50 = 68% 占用**，而 280 GB/s 只有实测 HBM（711 GB/s）的 **39%**
—— 两个指标同时指向"这块没吃满"。

### 6.2 有现成开关，而且我们从没测过

`STRATA_GR_V3=1`（纯环境变量，**不用改源码、不用重建**）。源码里的默认逻辑是
`gr_v3_default_on (a 12.0 card with > 13 GiB)` —— **gfx906 不在默认开启之列**，所以生产一直跑 v1。

约束（注释原文）：动态共享内存 `T * (N/S)` floats，`S` 取能放进**该卡 opt-in 上限**的最小值
（Ampere 99 KB → S=1；**Turing / HIP 64 KB → S=2**）⇒ gfx906 会取 **S=2**，块数 328。
风险：**another summation order**（不是逐位等于默认），采纳必须过提示侧 KL。

`grep -rn "GR_V3" deploy/` 只命中 dryrun 的源码副本 ⇒ **方案里从没提过这一项**。

### 6.3 为什么它能零干扰验证

`src/kernels/fused_gr_bench.cpp` 就是这个 kernel 的独立微基准（里面还专门
`_putenv_s("STRATA_GR_V3", "0")` 做默认路径对照）。⇒ 可以在 `--rm` 容器里编一个 bench，
直接 A/B v1 vs v3，**不用停服、不碰生产**，只占卡几秒。

| 项 | 值 |
|---|---|
| 靶心 | `hc read` **757 ms / 19.2%**（893 tok） |
| 手段 | `STRATA_GR_V3=1`（env，零构建） |
| 先验 | 41 block / 60 CU = 68% 占用；280 GB/s / 711 GB/s = 39% 带宽 |
| 验证 | **`fused_gr_bench` 微基准（零干扰）** → 通过后再谈停服 A/B |
| 风险 | 另一求和顺序 ⇒ 采纳须过提示侧 KL |

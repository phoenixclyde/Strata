# W969 · 600 / 800 / 500 不是三个结论，是**三个口径**：一个模型全部解释

- 日期：2026-11-04 21:2x–22:2x
- 起因：机主指出"一会 600 一会 800 一会又 500"。**质疑成立**：我此前每次换了一个 regime 就报一个新数，没把它们统一起来。
- 本件做三件事：**统一口径**、**逐条排除**（chunk / 引擎版本 / 上游 / 频率）、给出**一个能拟合全部数据的模型**。

**关键事实**：引擎打印的 tok/s = **实际读入 token / 时间**。所以 D 那一栏的"1400"里，1242/2468 有大量 token 是**前缀复用**跳过的
（`prompt 1915 tokens = 1910 reused + 5 read`），分母只算"读"的部分——**它不是冷读速率**。

## 2 一个模型拟合 A + B 全部冷读点

```
t ≈ 1.7 s  +  n / 822        （n = prompt tokens，冷读，serve）
```

| n | 预测 | 实测 |
|---:|---:|---:|
| 2,353 | 4.6 s | 4.41–4.58 s |
| 15,819 | 20.9 s | 22.24 s |
| 60,330 | 75.1 s | 75.03 s |
| 130,105 | 160.0 s | 164.8 s |

⇒ **每段冷读有约 1.7 s 的固定成本**（首层专家竞技场 bring-up / 首块 staging），
在 2.3K 时占 38%，在 60K 时只占 2%。**"短 prompt 只有 500、长 prompt 有 800"就是这个固定成本的摊薄**。

## 3 逐条排除：谁都不是原因

| 嫌疑 | 实验 | 结果 |
|---|---|---|
| `--prefill auto` vs `auto:16384` | 同二进制、同 2K prompt（`W968` + `W964`） | 524 vs 503（2K）、704 vs 775（9.7K）⇒ 只影响长档，且 16384 更好 |
| 引擎版本（0.1.56 vs 回滚 0.1.55w） | `W966` 同探针 | 503 vs 506 ⇒ **无差** |
| 上游 0.8.0 vs 0.4.1 | `W966` 同探针 + 内核反汇编 | 497 vs 503；**J=64 内核代码 23,164 vs 23,168 B、sgpr/vgpr/spill 全同** |
| GPU 降频 | 冷读时采 `sclk` | **1725 MHz**（MI10 上限 1746）⇒ 没有降频 |
| `--resident-budget-gib 76` 丢失 | 配置史（765 次启动） | 10-11 就去掉了，远早于 11-01 ⇒ 不是 11-01→今天的差 |

## 4 结论（回答"到底多少"）

1. **长 prompt 的 800 是真的，今天仍在**（804.1 @60,330，昨天 803.7 @61,246）。
2. **短 prompt 的 500 也是真的**（2,353 token 冷读 ≈525）。
3. **`W863` 的 946–1404 是 D 口径**（长度阶梯里带前缀复用，分母只算"读"），**不能当冷读速率**；
   我前几轮把这三栏混着报，才出现"600→800→500"的乱象，这个错在我。
4. **0.8.0 与 0.4.1 在代码级与实测上等价**，可以紧跟上游。

## 5 真正的优化靶心（比"换基线"更值钱）

模型的 1.7 s 固定成本 + 短档 525 tok/s ⇒ **首轮对话 TTFT 里约 1.7 s 是纯开销**。
这正是 `R88`（异步分阶段拷贝 / wait-copy 相位）要吃掉的部分，也和 `W853` 当年"wait copy 让 GPU 空转"的账一致。
⇒ 队列把 **R88** 放在前面是对的；它比继续在 0.4.1/0.8.0 之间比来比去更有价值。

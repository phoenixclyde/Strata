# W933 · R76 结项：`auto:16384` 的部分前缀代价只有 **0.04 s/请求**，保留

> 执行 2026-11-04 08:4x–09:1x，4 次重启，**生产保留 `auto:16384`**（config `fcf4df5b`）。

## 0 结论

| 项 | 结果 |
|---|---|
| 长文档追加式（真正的部分前缀）在负载中的占比 | **0.4%**（13/3000，其中约一半是本次测试自身） |

## 1 实测：复用的粒度确实是 chunk

构造 `DOC(30K) + Q_A` → `DOC + 追加段 + Q_B`（共同前缀 ≈ 30K，之后分叉）：

| 模式 | turn1 | **turn2 reused** | read | turn2 耗时 |
|---|---|---|---|---|
| **8192** | 25286 tok / 34.5 s | **24576**（3 chunk） | **728** | **2.63 s** |
| **16384** | 25286 tok / 32.1 s | **16384**（1 chunk） | **8920** | **12.56 s** |

两边都**精确对齐到 chunk 的整数倍** ⇒ **prompt cache 的复用粒度 = chunk 大小**，与推测一致。

（顺带：turn1 本身 16384 比 8192 快 **7.5%**（32.1 vs 34.5 s），与 W932 的 32K +5% 一致。）

---

## 2 一个必须先纠正的中间错误

我最初按「`0 < reused < t - 16`」统计，得出「部分复用占 **19.1%**」，并按最坏情况估出「切 16384 后平均每请求多读 6874 token ≈ 8.6 s」。**这个数字是错的。**

原因：**大部分「部分复用」其实是正常多轮**（turn2 = turn1 + 回答 + 问句，所以 `reused = turn1 长度 < t`），它们走的是**另一条路径**，与 chunk 无关。

### 两条复用路径（本轮实测确认）

| 路径 | 触发 | 粒度 | 受 chunk 影响 |
|---|---|---|---|
| **conversation cache**（整块快照） | turn2 的 prompt **完整包含** turn1 | 整块 | **否**（W922/W932 实测 99.68%） |
| **prompt cache** | 只有**部分前缀**重合 | **chunk 对齐** | **是** |

判据：`reused % 8192 == 0` 且 `t - reused > 64` ⇒ chunk 对齐的部分前缀。按这个口径重算：

```
chunk 对齐的部分前缀：13 / 3000 = 0.4%
  样本：t=51985 r=8192 / t=40586 r=8192 / t=103772 r=8192 / t=122938 r=24576 …
非对齐（多为多轮完整前缀）：521 / 3000 = 17.4%
```

**切 16384 后这批请求合计多读 90,112 token ⇒ 平均每个 6,931（8.7 s），但摊到全体 3000 个请求只有 30 token（0.04 s）。**

## 3 另一个意外发现：prompt cache 只缓存**完整 chunk**

短文档（6667 token）的同款测试，在 **8192 模式下也复用 0**：

```
[1] prompt=6667  reused=0     read=6667   耗时 9610 ms
[2] prompt=6685  reused=0     read=6685   耗时 9487 ms   ← 部分前缀，一点没复用
```

⇒ **不足一个 chunk 的 prompt 不进 prompt cache**。这解释了为什么「短 prompt 的部分复用」在两种 chunk 下都是 0 —— 也就**不存在「切 16384 会让短 prompt 失去复用」的问题**（本来就没有）。

而多轮（6580 token）能复用 99.68%，靠的是 conversation cache 那条路。

---

## 4 判决

**保留 `auto:16384`。**

- 收益：六长度全不劣，16K +2%、32K +5%、64K +6.2%、130K +8.1%（W932，全部 `0 reused`），按负载加权 **≈ +2.2% prefill**。
- 代价：0.4% 的请求各多花约 9 s，摊到全体 **0.04 s/请求**。
- 若将来出现**大量长文档反复追问**的用法（同一 30K 文档改几个字反复问），这条要重新评估 —— 那时 `auto`（8192）反而更好。

⚠️ **一个反直觉的地方值得记**：chunk 越大，单发 prefill 越快（GEMM 的 M 越大），但**部分前缀的复用损失也越大**（对齐粒度变粗）。这两件事是同一个原因的两面。

# W898 · 口径变更：本项目只做单流（2026-11-02 23:2x 机主定）

**一句话**：服务形态 = **单流**。凡以「多流聚合 / 多用户吞吐」为依据的条目、判据、收益预期，**全部作废或改写**；
decode 侧从此只守「不劣化」，收益只认 **prefill**。

---

## 1 撤了什么

| 对象 | 原表述 | 处置 |
|---|---|---|
| `R57` 多流聚合（`--batch N`） | 「聚合 ≥1.5× 单流、单流降 ≤5%」 | **撤除**：账本状态 `WITHDRAWN`、`count=0`，不进队列、不计入分母 |
| 方案 §0.2 第 3 条 | 「多流是未测轴…只在需要并发时启动」 | 改写为「只做单流；多流支持存在但不服务；外部多用户数字只作背景」 |
| 方案 §0.2 第 1 条验收句 | 「只认 prefill 或 **多流聚合**」 | 改为「只认 prefill；decode 条目只设 `|Δ| ≤ 1×CV` 的不劣化门」 |
| `R54` GDN megakernel | 以「decode 非 GPU 约 21%」立 | **挂起**（不是撤）：同模型把 GDN 融合做完后单用户 decode 62→62，期望值不足；只有 R52 审计证明存在**可见 launch 空窗**才重启 |
| `SESSION_STATE` 队列行 | 含 `R57` | 已移除；只留「已撤」说明 |
| `W895 §4` / `W897 §1` | 多用户 57→98 作为「增益存在」的论据 | 保留事实，**降级为背景**：不得引用为收益预期（两件已加口径注） |

## 2 重排后的唯一顺序

**R52 → R55 → R51 → R49 → R50 → R30′ → M3**（`R54` 挂起）

| 序 | 条目 | 为什么在这么前 |
|---|---|---|
| 1 | **R52** wave64 波口径审计 | 零停服；是 R55 的前置（先确认 64-lane 归约在哪几处、半波是否闭合） |
| 2 | **R55** 波内归约换 DPP | 影响所有内核、DPP 只换搬运方式（应逐位相同），零算法风险 |
| 3 | **R51** prefill MMQ 向量化 | **唯一还有大空间的面**：MMQ 已比 FP16 快 1.57×（8.975 vs 14.079 s @6.45K），继续优化 MMQ 本身 |
| 4 | **R49** per-file `-mllvm -amdgpu-sched-strategy=max-ilp` | 编译期、按文件；外部 dense +7–8%、全局套 MoE −2.2% |
| 5 | **R50** router BF16 GEMV | decode 侧，且 60 GB/s 尚未独立复现 ⇒ 先证伪再改 |
| 6 | **R30′** split-K | 会改求和序，需逐位门；优先级低于上面 |

## 3 单流下的 decode 现实

- 我们单卡短对话实测 **70.7 tok/s**（`bench_pair.py`，256 token）。
- 同模型同卡把「重打包 + DPP + QSA 融合 + 稀疏 decode + 并行 top-k」全做完：**62 → 62**。
- 跨卡才会涨（同为 MI50 引擎的 Castagna：4 卡两对 TP2 **pp 1,939 / tg 119.0（MTP，AR 79.5）**；
  层切分 pp 2,615 / tg 79.1）。**本项目单卡单流 ⇒ 跨卡不在范围内**，只作边界记录。
⇒ 结论：**decode 的剩余空间不来自项目内优化**；把精力放在 prefill 与「不劣化」上，才是与单流目标一致的策略。

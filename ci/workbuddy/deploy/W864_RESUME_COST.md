# W864 · 多轮续写的固定开销：R42 的「4KB 页」被证伪，靶心重定为「挂载固定成本」

> 2026-11-01 20:40–21:20，**零停服、零重启、零配置改动**。
> 口径：`[实测]` 本机跑出来的数 / `[源码]` 读过代码 / `[外证]` 上网核过 / `[推测]`。
> 上一轮（W863 §11）的结论「host KV pool 4KB 页 ⇒ 65000 映射项 ⇒ 830 ms」**本条撤回**。

---

## 0 三句结论

1. **PCIe 侧没有 830 ms 可挖**：256 MiB 主机↔显存单程 **20.3 ms（13.24 GB/s）**，
   4 KiB 页与 2 MiB 大页（实测 `AnonHugePages` 100%）**差 < 1%**，6 MiB 分块逐块 sync 也不掉速。`[实测]`
   ⇒ 「页粒度拖慢搬运」这条假设，在本机**物理上不成立**，原本准备的那次生产重启**取消了**。
2. **真正的钱在「挂载一个已停放会话」的固定开销上：约 380–400 ms**，而且**与 KV 大小无关**
   > **【AUDIT20 更正】** 这 380–400 ms 后来被 W866 切成 **145.6（读前）+ 23.7（挂载）+ 13.1（检查点）**，
   > W869 再证明其中 **147.3 ms 是上一次会话的停放**。所以本条里的「挂载」实际只对应 24 ms。
   > 本句保留原样只为追溯，**现行口径以 W869 为准**。
   （50 MB 的会话 375 ms，260 MB 的会话 414 ms，各自只读了 15 / 5 个新 token）。`[实测]`
3. 多轮第二段的 TTFT 因此可以拆成干净的直线：**TTFT ≈ 390 ms（固定）+ 2.3 ms × 新 token 数**，
   而冷启动读提示是 **1.6 ms/token**。也就是说被复用的那部分不是免费的——它换来了「每 token 贵 44%」加「一次性 390 ms」。

## 1 为什么先做探针（而不是先重启）

W863 §11.3 的推理链是：`kv_host_alloc` → pinned → 4 KB 页 → 65000 个映射项 → 830 ms。
链条里**每一环都可以单独测**，而最后一环（带宽）用一个不碰引擎的 HIP 程序就能测完。
先测，是因为它决定「要不要停服 5 分钟」。

新增探针：`ci/probe/pcie_probe.cpp`（四变体 × 四方向，见 §2）。

## 2 探针实测：256 MiB 主机↔显存 `[实测]`

```
device  AMD Radeon Graphics (hip 7.16)      buffer 256 MiB, chunk 6 MiB
host->host  cpu memcpy            26.4ms  10.17GB/s
hostmalloc   THP   0.0%  H2D 20.3ms 13.24GB/s | D2H 18.7ms 14.32GB/s | H2D/6M 20.8ms 12.93 | D2H/6M 19.7ms 13.65
thp_regged   THP 100.0%  H2D 20.1ms 13.33GB/s | D2H 18.8ms 14.26GB/s | H2D/6M 20.5ms 13.10 | D2H/6M 19.2ms 14.02
plain_regged THP   0.0%  H2D 20.2ms 13.32GB/s | D2H 18.8ms 14.26GB/s | H2D/6M 20.5ms 13.08 | D2H/6M 19.3ms 13.94
pageable     THP   0.0%  (单次大拷贝走同步回落, 计时不计) | H2D/6M 20.8ms 12.89 | D2H/6M 19.4ms 13.83
```

四个变体分别是：`hipHostMalloc(Mapped|Portable)`（**引擎今天用的就是这条**）、
`mmap + MADV_HUGEPAGE + 先触页 + hipHostRegister`（**提案的改法**）、同路径但不 `madvise`（对照）、
以及 `malloc` 未注册（下界）。

**读数**

| 结论 | 数 |
|---|---|
| 大页 vs 4 KB | **0.7%**（13.33 vs 13.32 GB/s），方向都对不上 830 ms 需要的那 40× |
| 分块 6 MiB 逐块 sync | 12.9–13.1 GB/s ⇒ **每块一次同步不是税**（0.48 ms/块，其中 0.46 ms 是纯搬运） |
| 大页是否真生效 | `thp_regged` 的 `AnonHugePages` **100.0%**（这次没有静默回落，所以「大页也没用」是硬结论） |
| 主机内 memcpy 260 MB | 26.4 ms ⇒ 就算恢复是纯 CPU 拷贝，也只有 26 ms |

⇒ **830 ms 里最多只有 20 ms 是搬运。** 剩下的必然是引擎逻辑，不是总线，不是页。

**链路事实** `[实测]`：`LnkCap/LnkSta` = **16 GT/s ×16（PCIe 4.0）** ⇒ 理论 31.5 GB/s，
本机实测 13.24 GB/s = 链路的 **42%**（hipHostMalloc/HIP 的常规水平）。这条只用来定位地板：
即便恢复真是纯搬运，地板也就是 20 ms —— 与 390 ms 差 20 倍。

## 3 生产实测：把 830 ms 拆成「固定 + 斜率」`[实测]`

口径：单用户、贪心、`max_tokens=24`，同一进程连续两轮。数据取自引擎自己打印的
`strata serve: prompt N tokens = R reused + F read in T ms`。

| KV 规模（token） | 复用 | 新读 F | prompt_ms | 备注 |
|---:|---:|---:|---:|---|
| 361 | 356 | 5 | **393** | 约 50 MB 的会话 |
| 371 | 356 | 15 | **375** | 同上，另一问 |
| 443 | 356 | 87 | 828 | |
| 1882 | 1877 | 5 | **414** | 约 260 MB 的会话 |
| 1899 | 1877 | 22 | 504 | |
| 2336 | 1867 | 469 | 1586 | 复现 W863 那条 |
| 2348 | 1877 | 471 | 1539 | |

线性拟合（按上表）：**截距 ≈ 390 ms，斜率 ≈ 2.3 ms/token**。

> **【AUDIT20 限定】** 这条直线**只对批路径成立**。表里 `443 tok / 87 新读 / 828 ms` 那一点按 390+2.3×87=590 算，实测 828，
> 偏 +238 ms —— 因为 87 个新 token 里有 64 个走了 **verify 窗口（13–16 ms/token）**，超过 `--short-read` 的部分才走批（3.4–4.0）。
> ⇒ 「2.3 ms/token」是两段拼接后的混合值；两条路各自的斜率见 `W867` §1。

> **口径诚实**：上表**每个点只有 1 次**（本机单用户、贪心、温度 0），没有重复，也没有算 CV。
> 「截距 390 ms」这个量级被两个极端点（50 MB / 260 MB 会话各 ~390-414 ms）**独立重复**过，可以信；
> 「斜率 2.3 ms/token」是粗估，**需要 ≥3 次重复才能当判据用**。

对照冷启动（`resume=0`）：2333 token / 3750 ms = **622 tok/s（1.6 ms/token）**；
1882 token / 3193 ms = 589 tok/s；361 token / 1507 ms = 239.6 tok/s（短提示本来就慢）。

**两个关键对照**

- **50 MB 与 260 MB 的会话，固定开销几乎一样（375 vs 414 ms）** ⇒ 不是按字节计费的任何东西。
- 同一会话「复用 + 5 个新 token」= 414 ms；「复用 + 471 个新 token」= 1539 ms
  ⇒ 增量 1125 ms / 466 token = 2.41 ms/token，**新 token 在复用态下比冷态贵 50%**。

⇒ W863 §10.3 那个「恢复 830 ms」应更正为：**≈ 390 ms 挂载固定成本 + ≈ 330 ms 的「每 token 变贵」**，
PCIe 只占其中约 20 ms。

## 4 顺带被证伪的三条（省掉三次瞎改）

| 假设 | 怎么测的 | 结果 |
|---|---|---|
| 主机内存回收 / swap（260 MB 镜像被换出，恢复时从盘读） | 读引擎 `/proc/PID/stat` 的 `majflt`、`status` 的 `VmSwap`，在请求前后取差 | **majflt +0、swap 0 KB**（两轮都是），不是缺页 I/O |
| 每次请求 mmap/munmap 一个大缓冲区（glibc ≥128 KiB 走 mmap，释放即归还，再分配就要重新缺页零填） | 50 ms 粒度轮询 `/proc/PID/maps`，比请求前/请求中/请求后的大匿名 VMA 集合 | **没有任何大匿名映射出现或消失**；进程是「73 GB 专家 arena + 模型 mmap + /dev/dri 显存映射 + 644 MB memfd」的稳定布局 |
| 4 KB 页 / IOMMU 映射项 | §2 的四变体探针 | 大页 100% 生效时带宽**不变** |

**仍然不知道的**：每请求 **+86187 次 minflt（≈336 MB）** 是什么。
它和 TTFT 的截距量级上撞（86187 × 4.5 µs ≈ 390 ms），但**这条只是巧合级别的证据**，
既没有证明它落在关键路径上，也没有定位到哪块内存——**先记账，不当结论**。

## 5 下一步：一次重启能回答的问题

固定 390 ms 到底花在哪，引擎已经有现成的拆解，只差一个环境变量：

```
STRATA_TRACE=1   →   strata trace: admission of slot N: drain X, prompt Y (read A, windows B,
                     K checkpoint(s) C = sync .. + save .. + evict .., rest D), ...
```
`[源码]` `src/program/generate.cpp:17471`（行号取自主线 `pr/strata-fork` @ `48b4866a`）；
`STRATA_TRACE` 在该处是**每请求** `getenv`（`:12185`），不是启动时缓存的静态。

四个数（read / windows / checkpoints / rest）直接决定改哪：

| 若大头在 | 说明 | 改法 | 预期 |
|---|---|---|---|
| `rest`（余额） | 挂载本身：逐层 restore + `refresh_residency` + `mtp.kv_restore` | 先看是「拷贝」还是「每层额外工作」——**同步次数已被 §2 排除**（43 次 6 MiB + 每次 sync 只花 20.8 ms，纯搬运 19.8 ms ⇒ 每次同步的税 ≤0.05 ms），所以若真是 rest 大，改法不是"合并同步"，而是查每层多做了什么（零填 / VMM 重映射 / 每个 state 的内核） | 待定 |

| `checkpoints` 的 `sync/save/evict` | 检查点搬运/驱逐 | 同上，或 `STRATA_CKPT_POOL` 类缓冲复用 | 至多省 100–200 ms |
| `windows` | 新 token 走了 verify 窗口（16 ms/token） | 调 `--short-read`（默认 64，交叉点约 33） | 小改，收益窄 |
| `read` | 确实是读提示本身慢 | 回到 prefill 主战场（专家流送） | 另立项 |

**注意**：如果只读源码会很想写「把逐层拷贝合并成一条流」——**探针已经证明那条不值钱**（38 次同步合计 ≤2 ms）。
这一条必须先记下来，否则下一轮又会照着"看起来对"的方向改一遍。


**成本**：一次重启（env 一行，不改二进制、不改 config 主体），起停各约 2–3 分钟，可 `deploy.sh rollback`。
**判据**：能拿到四段拆分即算成功；若 `rest ≥ 250 ms`，则「每层额外工作」方向值得查，预期收益 ≥ 350 ms。

### 5.1 为什么不能零停机拿到这四段（试过了）

`STRATA_TRACE` 在 `generate.cpp:12185` 是**每请求**读的（`const bool trace = std::getenv(...)`），
> **【AUDIT20 更正】** 这条**错**：`r18`（W866 §4）实测 `const bool trace` 位于 **serve 循环之前**，是**进程生命周期**的值——
> 21:11 建的标记文件，21:07 起飞的进程永远看不到。结论（须重建容器）仍成立，但第一环推理不成立。
所以理论上给活着的进程注入一个环境变量就够了。实测两条路都不通：

| 尝试 | 结果 |
|---|---|
| 宿主 `gdb -p <宿主PID>` 调 `setenv` | **失败**：`Target and debugger are in different PID namespaces`，且 `/proc/PID/exe` 读不了（EIO），没有符号表 |
| `nsenter -a` 后再调宿主 gdb | **失败**：进了容器的 mount namespace，宿主 `/usr/bin/gdb` 不在那儿（容器内没有 gdb） |

⇒ 剩下的路只有「重建容器」（env 在 create 时固化）。容器参数很简单（`--device=/dev/kfd --device=/dev/dri`、
`-v /models:ro -v ~/strata166/data:/data`、`--shm-size=64m`、`--restart unless-stopped`、`-p 8090:8090`），
重建可控，但**这是停服操作，需机主点头**，今晚没做。

## 2 机制：chunk 大小在抢 expert cache

日志逐字（三个臂启动时）：

```
chunk   8192 → the prompt path borrows 1578 CUDA0 cache slots ( 4.62 GiB)   21.1% of 7463
chunk  16384 → the prompt path borrows 2606 CUDA0 cache slots ( 7.62 GiB)   34.9%
chunk  32768 → the prompt path borrows 4667 CUDA0 cache slots (13.64 GiB)   62.5%
```

`--prefill auto` 的定义就是「**expert cache 能借到的最大 chunk**」（`generate.cpp:750`），所以 chunk 越大，借走的常驻专家槽越多：

- chunk 8192：cache 剩 5885 槽给常驻专家
- chunk 16384：剩 4857
- chunk 32768：剩 2796

**这解释了倒 U 的成因**：

- **短 prompt（16–32K）**：chunk 少、块数少 ⇒ 减少的 chunk 切换/启动开销 **大于** cache 变小的代价 ⇒ **大 chunk 赢**。
- **长 prompt（64K+）**：需要的专家总数本来就多，cache 又被借走 1/3 ⇒ 命中率下降、stream 增多 ⇒ **小 chunk 赢**。

32K 时 16384 最快、64K 时 8192 最快 —— 交叉点落在 32K–64K 之间，**不是单一最优值**。

## 3 为什么不采纳（净值核算）

用真实负载分布（6517 个 prompt 的长度直方图）：

| 区间 | 占比 | 16384 的效应 | 加权 |
|---|---|---|---|
| ≤8192（1 chunk，无差异） | **60.8%** | 0 | 0 |
| 8–16K | 2.2% | 0（变 1 chunk） | 0 |
| **16–32K** | **5.8%** | **−5.0%** | −0.29% |
| 32–48K | 1.6% | 未知（假设 −3%） | −0.05% |
| 48–64K | 4.7% | 未知 | — |
| **>64K** | **24.8%** | **+7.6%** | **+1.88%** |
| **合计** | | | **≈ +1.5%（变慢）** |

**>64K 占了 24.8%，是最大的一块**，而它正是 16384 变慢的地方 ⇒ 一刀切成 16384 是净亏。

（顺带纠正一个我自己的先验：我以为"主要场景是 6.4K"，那是**我的测试 prompt**；真实负载中位 4378、**p90 = 106301**、max 206226，39.2% 超过 8192。）

## 4 本轮真正值钱的东西：一条可组合的新假设（已立 R75）

borrows 从 1578 → 2606（+65%）是 16384 在长 prompt 上变慢的**直接原因**。而 **R66 的三条 opt-in 补丁正是减少 borrows 的**：

> `W921` 实测：`STRATA_PF_GROUP_SCRATCH` + `PF_HC_REGION` + `PREFILL_ROUTED_STREAM` 三开关全开 ⇒ **borrows 1578 → 1226（−22.3%，−1.03 GiB）**，但 prefill **−0.23%（噪声内）** ⇒ 当时判 DONE_NEG。

当时失效的原因是：chunk=8192 时 borrows 不是瓶颈。**而 chunk=16384 时它就是瓶颈**。

⇒ **假设**：R66 三条 + `auto:16384` 组合，borrows 从 2606 降到约 **2030**（−22%），可能让 16384 在 64K 上也不再变慢，从而拿到 16–32K 的 −5% 而不付 >64K 的 +7.6%。

这条组合**两条单独都不成立**（R66 单独 DONE_NEG、16384 单独净亏），但组合起来逻辑成立 —— 已立 **R75**。

## 5 产能边界（本轮踩到的）

`--prefill auto:32768` 借走 **62.5% 的 cache**（4667/7463），只剩 2796 槽给常驻专家。如果 prompt 更长或模型更大，这条路会先撞显存墙 —— **`auto:32768` 在 32K prompt 上已经比 16384 慢 1.9%**，不建议在任何长度上使用。

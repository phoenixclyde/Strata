# W890 · R38 结案（DONE_NEG）：占用率是真的，但它只值 **−19.5% 的一条路径**，整体反而是 +2.8%

**一句话**：`STRATA_TSUM=1`（fast 变体）在 T=3 把 HC down 的占用率从 12.5% 拉回 25%，实测 **down 2.62 → 2.11 ms（−19.5%）**——
**但同一次切换让 up 从 2.53 → 3.19 ms（+26.1%）**，HC 合计 **7.46 → 7.67（+2.8%）**，整窗口 **40.82 → 41.01 ms（+0.5%）**。
⇒ **「2.7×」不存在；占用率这条线索是真的，但它买到的是 1.2% 的窗口，不是 63%。**

---

## 1 实验设计（判别式，不是优化式）

上一轮（`W889`）算出的悬崖：HC down 在 **T=3 是 140 VGPR / 1 block/CU（12.5%）**，而 fast 变体是 **128 VGPR / 2 block/CU（25%）**。
两者**计算量相同、只差寄存器分配**，所以它天然是一个判别器：

- hc 明显变快 ⇒ 占用率是限制项；
- hc 不变 ⇒ 占用率不是限制项。

**A 臂**：`STRATA_VERIFY_PROFILE=1`（只为拿到 hc 六项），TSUM 关。
**B 臂**：再加 `STRATA_TSUM=1`。
两次都是 `docker restart`，各约 4.5 分钟；探针固定 `--prompt 600 --max 512`，每臂 1 发热身 + 3 发测量。

## 2 结果

| 项（ms/窗口） | A（TSUM 关） | B（TSUM=1） | Δ |
|---|---:|---:|---:|
| hc0 norm | 0.48 | 0.47 | −0.01 |
| **hc0 down** | **1.33** | **1.07** | **−19.5%** |
| **hc0 up** | **1.27** | **1.59** | **+25.2%** |
| hc1 norm | 0.06 | 0.06 | 0 |
| **hc1 down** | **1.29** | **1.04** | **−19.4%** |
| **hc1 up** | **1.26** | **1.60** | **+27.0%** |
| **HC 合计（GDN 层）** | **5.69** | **5.83** | **+2.5%** |
| HC 合计（QSA 层） | 1.77 | 1.84 | +4.0% |
| **HC 全部** | **7.46** | **7.67** | **+2.8%** |
| **窗口（GPU stages 的 total）** | **40.90 / 40.87 / 40.69** | **40.98 / 41.03** | **+0.5%** |
| 窗口（decode timing） | 44.96 / 44.60 / 44.28 | 45.02 / 44.60 / 44.40 | +0.1% |

**重复性异常好**：A 臂三发里 hc0 down 全是 1.33、hc1 down 全是 1.29 ⇒ 这六项不是 W863 那个 ±30% 噪声带，
`STRATA_VERIFY_PROFILE` 的相位计时是可用的（这也是本轮附带确认的一件事）。

## 3 怎么读这张表

1. **占用率确实是真的**：down 两条路径同步 −19.5%，与「12.5% → 25%」的方向一致，量级也合理
   （翻倍占用率买到 1/5 的时间，说明它原本受**延迟/并行度**限制，而不是纯带宽）。
2. **但同一个开关把 up 拖慢 26%**：`gr_up_q8_fast_kernel<T,false>` 在 T=3 的 VGPR 是 79（非 fast 是 73），
   **占用率同为 37.5%** ⇒ up 的变慢不是占用率，是它换了归约形状（`tsum<P>` 的 P=false）。
3. **净效果是负的**：HC +2.8%、窗口 +0.5%。**这个开关不能采纳。**
4. **上限也被测出来了**：down 全部只占窗口 **2.62 / 40.82 = 6.4%**。
   就算把 down 直接抹零，也只有 6.4%；占用率这条杠杆实际买到 **1.2%**（0.51 ms / 40.82）。
   ⇒ R38 原来写的「2.7×」**在物理上就不可能**：HC 全部才 18.3% 的窗口。

## 4 顺手纠正的一个数

`W863` 说 HC 占窗口 **15.3%**；本轮同一相位表实测 **7.46 / 40.82 = 18.3%**。
差 3pp 的原因：T 从当时的 3.08（`W873`）到现在 3.23，而 **HC 的 VGPR/占用率随 T 走**（§2 的机制）。
⇒ 「HC 占比」不是一个常数，**报它必须带 T**。

## 5 结论与处置

| 项 | 处置 |
|---|---|
| R38 | **DONE_NEG**（原前提作废 + 唯一可用的杠杆实测为负） |
| `STRATA_TSUM` | **REJECTED**（`P253`）：净 −0.5%；且它改求和顺序，连 KL 门都不必再花 |
| 「HC 还有 2.7×」 | **删掉**。可挖上限：down 全抹零 = 6.4%；现实杠杆 = 1.2% |
| 后续若要碰 HC | 只剩**只对 down 用 fast**（拆分开关）这条 1.2% 的路，性价比低于队列里任何一条 |

## 7 方法学（本轮最值钱的一条）

`W889` 我给自己的结论打了折（「up 占用率 37.5–50% 却只有 80 GB/s ⇒ 占用率不解释这条带」）——**这个折打对了**。
本轮实测把两条路径分开：**down 受占用率影响（−19.5%），up 不受（且被同一个开关拖慢）**。
⇒ 「把一条机制按 family 统一处理」是这个项目反复踩的坑（`P245` 的 async+move 合并也是同一个形态）。
**下一个开关若要动 HC，只能按 down/up 分开。**

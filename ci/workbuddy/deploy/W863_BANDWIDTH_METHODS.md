# W863 · decode 带宽利用率：方法清单（外部证据）+ 受控实测

> 起因：机主要「上网找找能提高 decode 期间显存带宽利用率的方法」。查完后我把最相关的两条
> 做成受控实验（`ci/probe/read_probe.cpp`），结果**推翻了我上一轮给 R31 排的优先级**。

## 0 三句结论

1. **split-K 有效，但有膝盖**：HC down 形状（10240→320）从 553 → **621 GB/s（+12%）** 在 S=4，
   S=8 就掉回去。外部文献在别的卡上给的是 +2×，我们这里只有 +12%，差别在于我们的块本身太小。
2. **宽读（16 B）有效**：同形状同 S 下 **+11%…+35%**（826 vs 621 在 S=4）。但**它解释不了 8×**。
3. **生产 HC 只有 98 GB/s，而这个探针把同样的读做到 553–826 GB/s** ⇒ 读模式最多只能解释 **1.5×**，
   剩下的**5.6× 在别处**（融合内核里的 dequant/归一化/LDS/occupancy）。⇒ **R31 的优先级必须下调**。

## 1 外部证据：文献里能提带宽的八种做法

| # | 方法 | 证据（带出处） | 我们的情况 |
|---|---|---|---|
| **1** | **split-K**：输出维太短时，把归约维切 S 份，块数翻 S 倍 | Graphsignal 实测：5120 行形状只到 **82–88%** 带宽，而 15520 行的 lm_head 到 **98.6%**；「行组少 ⇒ 独立内存流少 ⇒ 变成延迟受限而非带宽受限」。Intel Arc 实测：N=5120 的 int4 GEMV，**S=1 是 259 GB/s（43%），S=16 是 533 GB/s（89%）** | **已验证有效**，见 §2：+12%（S=4 最优） |
| **2** | **宽访存**（每 lane 16 B） | gfx906 实测（skyne98 wiki）：`global_load_dwordx4` **867–873 GB/s** vs scalar **814 GB/s** | **已验证有效**，+11…+35%；但 34 B 布局不齐，要走 LDS 中转 |
| **3** | **global→LDS 直通**（`buffer_load_to_lds`，数据不进寄存器） | AMD 官方性能指南称该族指令让一个参考 GEMM 提升 **60%** | **未用**；这是 R31 的正解形态（比"先读寄存器再写 LDS"省寄存器） |
| **4** | **LDS 宽访问 + bank padding** | gfx906 实测：`ds_read/write_b128` **9.5–11.2 TB/s**，b64 4.3–8.8，b32 1.9–3.9；列式访问 ld=32 时 **1865 GB/s**，加一个 vec4 填充（ld=33）回到 **3974 GB/s** | 未用；若走 LDS 中转必须按 b128 + 填充 |
| **5** | **内联 dequant，不做独立 pass / 不落中间 buffer** | Intel Arc 文档：「never a separate pass, never a temporary buffer; that would double the traffic that is the entire budget」 | **已是**（MMQ 内联反量化） |
| **6** | **权重驻留 + 激活广播**（weights 是流量，activation 几乎免费） | 同上文档的 design rule | 部分：HC 是 weight-stationary，但激活要走 LDS 广播 |
| **7** | **ILP/占用率算术**（VMEM 队列、s_waitcnt 时机、VGPR 粒度 16） | gfx906 无 `s_clause`/`s_waitcnt_depctr`/`s_delay_alu` ⇒ 延迟隐藏只能靠 ILP 与占用率；AMD 占用率公式：**170 寄存器 → 取整 176 → 2 waves；压到 168 → 3 waves（+50% 延迟隐藏）** | **未查**；这是"8× 在别处"的头号嫌疑 |
| **8** | 减少字节（更低比特、KV 量化、批处理摊销） | 通用；批处理对单流无效（机主明确单流） | 不做：改 pack 格式 / 与单流冲突 |

**明确不适用**：批处理摊销（用户单流）、改量化格式（改 pack = 大工程且破坏逐位等价）、
tensor-core 路线（gfx906 无矩阵指令）。

## 2 受控实测：同样的字节，只改一个变量

`ci/probe/read_probe.cpp`（容器内 hipcc 编译，≤360 MiB，与生产同驻留）。
两个模式**读完全相同的字节数**：

- `mode0`：每个 34 B 的 Q8_0 块发 **17 条 2 B load**（生产内核今天的样子）
- `mode1`：同样的字节用 **16 B 流式 load**（若 LDS 中转可行，这是它的天花板）

`S` = split-K 因子（同样的字节切成 S 倍多的块）。

| 形状 | S | mode0 GB/s | mode1 GB/s | 宽读收益 |
|---|---:|---:|---:|---:|
| **HC down 10240→320** | 1 | 553 | 613 | +11% |
| | 2 | 592 | 678 | +15% |
| | **4** | **621** | **826** | **+33%** |
| | 8 | 494 | 493 | —（发射受限） |
| | 16 | 278 | 289 | — |
| **GDN qkv 2560→10240** | 1 | 566 | 763 | **+35%** |
| **big 10240→8192（85 MiB）** | 4 | 627 | 839 | +34% |
| **HC up 320→10240** | 1 | **125** | 不可（行 340 B 非 16 的倍数） | — |
| | 4 | 36 | — | — |

三条读数：

1. **split-K 的膝盖在 S=4**（1280 blocks ≈ 21 blocks/CU），再往上被**块发射开销**吃掉
   （S=8 起两个模式的数字重合 ⇒ 已不读受限，而是发射受限）。
2. **HC up 是病态形状**：行只有 340 B（10 个 Q8 块），一个 block 一行时每线程只读 5 字节，
   S=1 就跌到 125 GB/s，加 S 更差（块更多、每块更空）。生产用的是 **160 blocks 打包多行**，
   所以生产比我这个模型好；但这个形状本身没有 K 向并行度可用。
3. **宽读（+33%）与 split-K（+12%）可以叠加**，HC down 从 553 → 826 GB/s。

## 3 最关键的一条：读模式解释不了生产的那 8×

| 口径 | HC 读的有效带宽 |
|---|---:|
| 生产实测（相位表，644 MiB / 6.89 ms） | **98 GB/s** |
| 本探针 mode0、S=1（最朴素的 2 B 读） | **553 GB/s** |
| 本探针 mode0、S=4 | 621 GB/s |
| 本探针 mode1、S=4（宽读天花板） | **826 GB/s** |

⇒ **连最朴素的 2 B 读都能到 553，生产只有 98。读模式最多解释 1.5×，剩下的 5.6× 不在读上。**

那 5.6× 只可能来自融合内核里**每个字节要做的其它事**（`gr_down_q8_kernel` 里除了读还要
norm、跨 lane 归约、LDS 往返、up 投影），或者来自**占用率/寄存器**（AMD 的占用率是能算的：
170 寄存器 → 2 waves，168 → 3 waves）。

**这条直接改了 R31 的排位**：把"改 load 宽度"当成 HC 的主攻方向是错的——它顶天值 1.5×，
而真正的大头（5.6×）还没人量过。

## 4 修正后的动作顺序

| 序 | 条目 | 为什么 | 判据 |
|---|---|---|---|
| **1** | **R32 · 量清融合内核的 5.6×**：同形状、同字节，把"只读"探针逐步加回生产内核的每一件事（norm → 归约 → LDS → up），每一步量一次带宽 | 这是唯一能定位 5.6× 位置的办法；纯微基准，零停服 | 每加一步，带宽掉多少 |
| **2** | **R33 · 占用率/寄存器审计**：`--save-temps` 取出 VGPR/占用率，按 AMD 公式算 waves/SIMD | 若 VGPR 落在 169–176 之间，压到 168 就是 +50% 延迟隐藏，改动极小 | 每 SIMD waves 数 |
| 3 | R30' · split-K **按形状**上线（HC down S=4） | 已实测 +12%，但要在真实内核里验证，且 S 必须按形状选（文献：S 不随 N 单调） | 相位 + 逐位门（split-K 会改求和序） |
| 4 | R31 · 宽读 + LDS 中转 | 天花板 +33%，但要在 R32 之后：若 5.6× 来自 LDS 往返，加 LDS 反而更糟 | 微基准 |
| — | 文献方法 5/6（内联 dequant、权重驻留） | 已经是现状 | — |

**一句话给方案**：不要再把"带宽利用率低"当成"读得不够宽"。这轮数据说明**读得够宽了**（553 GB/s
的朴素读 vs 98 的生产），**是每个字节的其它开销把带宽吃掉了**——这才是该打的地方。

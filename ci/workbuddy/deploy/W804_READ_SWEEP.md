## 0 结论（先行）

1. **`STRATA_PREFILL_CPU_SHARE_MAX` 钉 1024 是在漏水。** 同一个 bench，把 MAX 放到 3072：
   read 1,095 / 1,203 / 1,406 / 1,820 / 1,866 / 2,196 分别 **-31.7% / -27.3% / -25.6% / -15.6% / -14.7% / -14.2%**；
   而现役 MAX=1024 在这一段是 **-0.3% / -0.0% / -7.0% / -0.6% / -0.1% / -1.0%**（等于没动）。
2. **一半功劳不是 CPU 的。** 加一条隔离臂 D = `share=0` + `STRATA_PREFILL_STREAM_MIN=3072`（只改 staged 阈值、完全不用 CPU）：
   它在同一段拿到 **-20.2% / -13.7% / -14.3% / -4.2% / -4.3% / -5.2%**。
   ⇒ 1.1-1.4K 是「staging + CPU」两件事叠加，1.8K 以上 CPU 才是主力。
3. **MAX=4096 没有额外收益**（E 臂与 B 臂逐档在 ±1.5% 内）⇒ 3072 就是拐点，正好等于上游缺省。
4. **`W800`/`P128` 的「STREAM_MIN 否决」只对「往小调」成立。** 往大调是赢的（D 臂）——
   这条要写进 register，否则以后有人再看到 P128 就会把这条路一起封掉。
5. 采纳动作**暂缓一项**：MAX=3072 会同时把 CPU 份额带进 1024-3072 段，这一段的质量门本轮正在跑（§4）。

## 1 为什么必须重做这个账

`W803` 把 `STRATA_PREFILL_CPU_SHARE` 改成 `auto` 之后，`W800` 那张「`wait copy` 754 ms（23.5%）」的相位图
**描述的是 `share=0` 的旧世界**。而 `W803` 为了保守，把 `MAX` 钉在 1024 —— 那段代码里 `cpu_share_max()`
同时被当成 `g_stream_min_share` 用（`prefill.cpp:211` `if (applies && cpu_share_on()) g_stream_min_share = cpu_share_max();`），
所以钉 1024 意味着 **1,024 以上的 chunk 仍然走「把每个专家都从 PCIe 拉一遍」**。

上游对 3072 的态度是负面的：`docs/DETAILS.md:1821` 逐字「`STRATA_PREFILL_CPU_SHARE_MAX=3072` … also stays opt-in:
it **lost 2% at 2,048 tokens** on the 5070」。所以这一轮是去验这句话在本卡成不成立。

### 2.1 三条读法

- **< 1024：只有 CPU 份额有用。** D 在 315-700 档是 -0.1% ~ +0.6%，而 A/B/E 都是 -19% ~ -27%。
  ⇒ 这一段的收益确实来自「把专家交给空闲 CPU」，不是来自 staging。
- **1,024-3,072：两件事叠加，且比例随 read 变化。**
  1,095 档：staging 贡献 -20.2，CPU 再加 -11.5（合 -31.7）；
  1,406 档：staging -14.3，CPU 再加 -11.3；
  2,196 档：staging 只剩 -5.2，CPU 再加 -9.0。
  ⇒ **read 越大，staging 越不值钱（专家被更多 token 摊薄），CPU 的价值越稳定。**
- **4,096 = 3,072。** E 与 B 逐档差 <=1.5%（最大 1,095 档 -32.6 vs -31.7），在臂间噪声内 ⇒ **拐点在 3,072**。

### 2.2 相位证据（read 1,866 档，单 chunk）

| 臂 | GPU timeline | 前四相位 |
|---|---|---|
| C（基线） | 4,115 ms | gemm gate/up 26% · **dequant 14%** · gemm down 12% · ple 12% |
| D（只 staging） | 4,027 ms | gemm gate/up 26% · gemm down 12% · ple 12% · **dequant 9%** · `wait copy` 4% |
| A（MAX1024，等于 C） | 4,126 ms | 与 C 同形（这一段 share 不参与） |
| B（MAX3072） | 3,493 ms | gemm gate/up 24% · ple 14% · gemm down 11% · **dequant 6%** |

`dequant` 从 14% → 9%（staging）→ 6%（+CPU）**两次下降**，与两条机制一一对应：
staging 让拷贝按路由来（少搬），CPU 直接把一部分反量化搬走。

## 3 与上游的分歧，以及为什么

上游说 3072 在 2,048 token 上「lost 2%」（RTX 5070）；本卡在 1,820-2,196 上是 **-15% ~ -14%**。**符号相反。**

能对上的是 `#1282` 里作者自己的话：「the gain grows with the **experts' size**. UD-Q4_K_XL's larger experts make a
small chunk PCIe-bound. Q2_0's and IQ2_XS's ~1.2 MB experts mostly do not, so they move less.」
本包是 **IQ4_XS，专家 blob 约 4 MB**（`W800` 由 `wait copy` 反推：每个短 chunk 搬 2.3-4.5 GB / 580-1,100 个专家），
是 IQ2_XS 的三倍多 ⇒ **本卡这一段是 PCIe 受限**，所以「少搬」和「别人算」都直接变成时间。
5070 的专家小、PCIe 快，2,048 token 已经摊薄，再看不出收益。**这不是谁对谁错，是包的形状不同。**

## 4 质量门（1-3K 段）：本段此前从未测过

`MAX=3072` 不只是改 staging，它同时把 **CPU 份额带进 1,024-3,072 段**。按规则 X（`W803`），
任何动分布的改动都要过同一套 teacher-forced KL 门。做法与 `W803` 相同，只把 shape 轮放大：

| 项 | `W803`（<1024 段） | 本轮 `kl_corpus2`（1-3K 段） |
|---|---|---|
| shape 轮 fresh | 551-617 | **1,483 / 1,531 / 1,599**（落在 1024-3072） |
| probe 轮 fresh | 141-187 | 136-183 |
| `--short-read` | 300 | 300 |
| 配对评分位置 | 1,348 | **653** |
| 臂 | A/C = off，B/D/E/F = on | **A = MAX1024；B、C = MAX3072（同一配置两遍）** |
| CPU 真的动了（`cpu gate -> share` 行数） | 0 / 326 | **A 45**（只有 t0 那个 576-token chunk）**/ B、C 各 185**（四个 chunk 全动） |

`cpu gate` 的 45 对 185 就是隔离证据：A 臂只有第一个 576-token chunk 进 share，后面三个 1.5K chunk 全部没进。

### 4.1 KL 结果

| 对 | KL 均值 | KL 中位 | p90 | p99 | argmax 一致 | KL=0 占比 |
|---|---|---|---|---|---|---|
| **A∥B**（改 MAX） | **0.02132** | 0.00357 | 0.0671 | 0.354 | 89.43% | **0.0%** |
| **A∥C**（改 MAX，第二份样本） | **0.02966** | 0.00474 | 0.0968 | 0.379 | 88.51% | 0.0% |
| **B∥C**（**同一配置两遍 = 底噪**） | **0.02715** | 0.00243 | 0.0861 | 0.467 | 88.97% | 0.0% |

**判读**：变更的两份样本（0.0213、0.0297）**把底噪 0.0271 夹在中间** ⇒ 均值上「改 vs 不改」与「同一配置两遍」
不可区分。中位是 0.0036 / 0.0047 对底噪 0.0024（约 1.5-2 倍）—— 但同一统计量在 `W803` 里的两次抽样也差 27%
（A∥B 0.0165 对 A∥D 0.0210），所以这 1.5-2 倍不足以判成系统性偏移。

**两条必须写下来的限制**：
1. **本段没有任何逐位相同的位置**（`KL=0` 占 **0.0%**，而 `W803` 的 <1024 段约一半位置逐位相同）。
   原因：t0 的 576-token chunk 在**所有臂**里都进了 share，所以 A 不是确定性基线，整条序列从第一个 chunk 起就带 share 的计时噪声。
   ⇒ **本门的检验力比 `W803` 弱**，它只能回答「有没有超过自身噪声」，回答不了「有没有更小的确定性偏移」。
2. 本段的底噪（0.027）是 `W803` 的 <1024 段（0.008-0.011）的 **约 3 倍**：chunk 从 600 涨到 1,500，
   share 的切分差异要摊到更多专家上。**底噪越大，越难分辨真信号，也越难误判** —— 两个方向都要记住。

### 4.2 处置

**采纳 `MAX=3072`**（与上游缺省一致），回滚位 `data/strata-huihui-ud-iq4_xs.json.bak_w804_max3072`。
理由：(1)均值判据（规则 X）通过；(2)中位落在 0.003-0.01 的采纳带内；(3)收益 14-32% 是本月最大的一笔余量；
(4)该值就是上游对显式 `auto` 的缺省，我们此前钉 1024 是**无数据时的保守**。

**不做 `MAX=4096`**：E 臂与 B 臂逐档差 <=1.5%，没有收益。

## 7 任务级门：36 题、三臂 —— 唯一的分歧出现在「同一配置的两次运行」之间

分布层（§4）只能证明「没系统性移动」，回答不了「有没有变笨」。这一层补上。

### 7.1 语料与协议

| 项 | 设定 | 为什么 |
|---|---|---|
| 题目 | **36 题**，4 类各 9 题（某 SKU 的总件数 / 件数最多的订单号 / 含某 SKU 的订单数 / 最早发货的订单号） | 答案由生成器自己从同一份日志算出，**不需要人工核对**；必须真读日志，不能靠常识 |

| 输出 | 强制一行 `ANSWER: <value>`（结尾另加禁枚举/禁解释的指令） | 不做这条，默认思考会把 300 token 全花在枚举记录上（实测 `finish=length`，见 §7.4） |

### 7.3 分辨率与判读

- 本题集的**分辨率是 1/36 = 2.8 pp**。上游对自己那套（HumanEval 取偶数题 82 + 30 道生成推理题）
  的口径是逐字「**a change of 3 reasoning tasks is noise**」（3/30 = 10 pp，`DETAILS.md:1896`）。
  ⇒ 我们这套的粒度比上游自认的噪声阈**细 3.5 倍**，而实测分歧 **<=1 题（2.8 pp）**。
- 格式面有一条真实差异：t28 在 B、C 里答成裸 `16`（值对、前缀丢了），A 带了前缀。
  ⇒ **严格口径下 B 少 1 题**。但 B 和 C 是同一配置，两遍都丢前缀 ⇒ 这同样是开关自身的抖动，不是系统性退化。
- **不能说的**：这套题覆盖的是「短日志 + 单步查/加」这一类；工具调用格式、长链推理、代码生成**没覆盖**。
  上游用 HumanEval 覆盖代码面（其 `157/164` 与本卡无关，是别的机器与包的读数）。

### 7.4 过程中的两次返工（写下来防复发）

1. **默认思考吃光预算**：不加 `reasoning_effort: none` 时，模型会把 300 token 全用来逐条枚举日志，
   8 题里有 1 题 `finish=length` 且没有任何 `ANSWER:` 行 ⇒ 那不是「答错」，是「没答」。加了之后答案 6-9 token、0.3-1.9 s。
2. **`mt_task.py` 的 `SUFFIX` 没定义**：我用字符串替换插常量，锚点没匹配上就静默跳过，运行时 `NameError`。
   **驱动器的新守卫抓到了它**（`!! ABORT no JSON`），但脚本当时**没有 trap**，于是把生产留在了臂 A（`share=0`）的配置上。
   已补 `trap restore_cfg EXIT`：任何路径退出（含 ABORT）都恢复生产并重启。
   ⇒ 教训：**臂脚本的恢复必须走 trap，不能靠顺序执行到最后一行**；**改代码不许用字符串替换，改完要 `ast.parse`**。

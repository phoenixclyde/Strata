## 1 P28 `STRATA_GR_SPLIT=1` -> REJECTED

**先修一处引证错**：register 原写 `AMD_HIP.md:461` / `fused_gr.cu:1722`，实测是
**`docs/AMD_HIP.md:482`** / **`src/kernels/cuda/fused_gr.cu:1750、1754、1771`**。

**文档原文**（`docs/AMD_HIP.md:482`）：

> `gr_down_multi`, opt-in | split along K (8 rows x 5 slices of 2048), **~3% per window; sums in another order
> than the single-token read, so off by default** | `STRATA_GR_SPLIT=1`

**源码原文**（`fused_gr.cu`）：

```
1750:  // gfx906, opt-in STRATA_GR_SPLIT=1: the latency-hidden norm/up (STRATA_GR_FAST) with the K-split down (~3% faster
1754:  static const bool split_on = std::getenv("STRATA_GR_SPLIT") && std::string(std::getenv("STRATA_GR_SPLIT")) == "1";
1771:  return false;   // the gfx906 STRATA_GR_SPLIT read: no q8_1 (the caller quantizes), like the v3 path above
```

**三条判据，任一即够**：

1. **预期收益 ~3%/verify window 远低于本机解码分辨力 9.5~15%** => 按项目"低于分辨力不可判"的规矩，**发车也测不出**；
2. **"sums in another order than the single-token read" = 破坏位一致**（浮点求和顺序不同 => 结果位不同）
   => 与本项目"不改答案 / 保位一致"的保守基线原则冲突（同 P10 对 `--prefill` 的处置）；
3. **默认关**（off by default）。

## 2 P32 `--kv-grow` -> REJECTED

**help 原文**（`generate.cpp:677-679`）：

> `--kv-grow` the K/V takes VRAM only for the cells the requests reach and the expert cache holds the rest,
> giving slots back as the context grows (**one GPU, with `--expert-profile`**; `STRATA_KV_GROW=1/0` also).
> Default: the whole `--max-context` allocated at start

**生效条件**（`generate.cpp:3788-3803`）：**单 GPU + 不 streaming（未用 `--kv-resident`）+ 有 profile**
---- 我机三条**都满足**（无 `--layer-split`、无 `--kv-resident`、有 `--expert-profile`）。

**收益算账**：

| 项 | 值 |
|---|---|
| `--kv k8v4` 单 cell | 816 B |
| `--max-context` | 262,144 cells |
| KV 总量（整上下文） | 262144 x 816 B = 213,909,504 B = **213.9 MB = 204.0 MiB**（**W735 更正**：原文把十进制 MB 当 MiB 用） |
| expert cache | **21.98 GiB / 9757 槽** => **2.30 MiB/槽** |
| **全省下来换到的槽** | 204.0 MiB / 2.30 MiB = **约 89 槽（+0.91%）**（**W735 更正**：原写 93 / 0.95% 系单位混用） |

而且这 93 槽是**上限**：省下的量随请求实际用到的上下文**减少**（用满 262K 时为零）。
=> **收益 <=1%，远低于分辨力** => 不采纳。

## 3 P29 `STRATA_SPEC_GUMBEL=1` -> 保持 CANDIDATE（口径勘定）

register 原 note：`AMD +5.7~9%；**贪心时是空操作**`。本波把"我们到底是不是贪心"查清了：

- 我机 config（`strata-huihui-ud-iq4_xs.json`）**无 `sampling` 段**；
- `serve/server.py:576-577` 原文：
  > An absent temperature keeps the engine's default, **which is greedy**; `temperature=0` means the same thing,
  > so it is not forwarded.

=> **不显式传 `temperature` 的请求一律贪心** => 该开关在**默认口径下是空操作**。
仅当**客户端显式带 `temperature > 0`** 时才可能有 note 里的 +5.7~9%（那属客户端用法，须单独实测）。

**判定**：**保持 CANDIDATE**（并 不 是"不适用"---- 它是客户端行为相关的条件开关，不像 P30 那样在引擎层恒 false）。

## 5 教训（复发项）

**register 里的引证行号也会错**：本条 P28 的 `AMD_HIP.md:461` / `fused_gr.cu:1722` 都是错的
（实际 482 / 1750+1754）。这与 W716 审计发现的"引证行号逐字取不到"是**同一类问题再次出现**
（见 `W716_AUDIT.md` 发现 #1）。=> **凡在 register 里写行号，必须现场 `sed -n` 取原文后再落笔**；
引用前的复核成本很低（一条 `sed`），而错误行号的代价是"可复核性打折"。

## 0 三句结论

1. **生产容器就是「一条流」**，不是「支持几条、多了排队」——没有 `--batch/--slots` 时引擎走 solo 路径，
   server 侧只有**一轮控制线（the single turn）**，第二个请求必然等前一个读完提示并让出控制权。
   `[源码]` 这不是显存不够，是**设计如此**；而且上游的并行栈在 **HIP 上根本不启用**。
2. **草稿链长度已经到顶了**：`--spec-min-p` 0.70 → 0.40 把草稿/窗口从 0.78 拉到 1.43、接受率 86%→66%，
   **tok/s 打平（48.9 vs 49.0）**。`[实测]` 与 vLLM 在 MI300 上的实测曲线同形（N=5 峰值 1.18×，N=7 回落）。`[外证]`
3. **带宽真正浪费在两处，不在 GEMV 主体**：HC 只有 **14%**（6.89 ms 搬 675 MB），专家读占窗口 **32%** 但效率没测过。
   主体大矩阵 GEMV 是 52–60%，head 55% —— 都还算正常。`[实测]`

## 1 并发流的真相（回答「生产容器支持几个流」）

### 1.1 机制

| 层 | 事实 | 出处 |
|---|---|---|
| 槽位数 | `parallel_slots(cfg)` = args 里的 `--batch/--slots`，否则 config 的 `parallel`（>1 才算）。**生产两者都没有 ⇒ 0 个批槽** | `serve/server.py:3684-3696` |
| 没有批槽时 | 引擎走 **solo 路径**（GEN + MTP 草稿），server 侧所有请求排在**一轮控制线**后面（"the single turn"，`QUEUE_BEAT_S` 每 10 s 发 keep-alive，`waiting`/`_admit_next` 决定谁拿到） | `server.py:284`、`:1753-1798`、`:1861` |
| 就算开了 `--batch N` | 控制线（读提示、准入）**仍是一次一个请求**；只有计算进槽 | `server.py:1861` 起的 `generate_batched` 注释 |
| 单请求时 | 即使有批槽，某请求「独占且无人等」时会 `_may_go_solo()` **回到 solo 路径**（"with drafts: the fastest stream"） | `server.py:1881-1895` |
| **HIP 的额外限制** | `parallel_stack_env()` 在 `backend == "hip"` 时**直接 return**：0.2.9 那套并行栈（CKPT_POOL / BATCH_* / QSA_SLOTS 等 9 个开关）**只在 Linux CUDA 上被验过**，HIP 一个都不自动开 | `server.py:3701-3706` |

### 1.2 实测（两个请求，第二个晚 1 s 发出）`[实测]`

```
A: 发出 +0.00s，3.62s 完成 96 tok
B: 发出 +1.00s，4.49s 完成 96 tok   ← 比 A 晚 1.87s 结束，不是并行
```

⇒ B 基本是在等 A 让出控制线后重跑。**结论：并发度 = 1**。

### 1.3 该不该改

**不该**，而且和机主用法一致：

- 上游自己把「单请求」定义为最快路径（`_may_go_solo` 的注释逐字写明）；
- 多流要靠 `--batch`，而 HIP 上的并行栈没有测量支撑（上游注释直说 "HIP got no measurement without replicas"）；
- 一开批槽就要额外 KV + checkpoint pool，而本机 VRAM 只剩 **920 MiB**（`[实测]` 启动横幅）。
- 真要多流，正确的做法是**换一条路线**（多实例/多卡），不是在这张卡上硬开。

- dense 合计 **16.99 ms / 4263 MiB = 263 GB/s = 29.8%**（旧记 37%）—— 这才是「带宽利用率」的真身。
- **最好的单个 kernel 也只有 53%**（`native_mmvq` 2560×10240 ncols=2：27.9 MB / 59.5 µs = 469 GB/s）
  ⇒ 问题不是"某一条读特别烂"，而是**整条 decode 路径都在屋顶的一半以下**。
- **HC 是最刺眼的**：675 MB 用了 6.89 ms；同样的字节量 head 只用 1.73 ms。
  **根因（W863 H1，源码核实）**：HC 读走的是 `launch_q8()`（`fused_gr.cu:2229` 的 **"S23 experiment"** 分支），
  而**同样这两个矩阵**用普通 `native_mmvq` 只要 **14.7 + 13.7 µs/组 = 245 GB/s**（R 表微基准，ncols=2），
  生产实测是 **71.8 µs/组 = 97 GB/s** ⇒ **实验级 Q8 内核只有普通 mmvq 的 40%**。
  另有两条路被门挡住：`STRATA_GR_V3` 在 `s_down != nullptr`（即 HC_Q8 开）时**不适用**（`fused_gr.cu:2272`）；
  staged 分裂读同样要求 `s_down == nullptr`（`:2308`）。
  ⇒ 两条互斥的走法：(a) 改这个 Q8 内核（重编 + 逐位门）；(b) **`STRATA_HC_Q8=0` 走 bf16 staged 读**——
  字节翻倍到 1.28 GiB，但按 245 GB/s 只需 **5.6 ms**，比现在的 6.89 ms 还快；代价是答案有极微小变化（rounding-level）。
  微基准里同样的两个矩阵（ncols=2）只要 14.7 + 13.7 µs/层 ×48 ≈ **2.7 ms** ⇒ 生产比孤立微基准慢 **2.5×**，
  说明开销在**发射/同步/分步**上，不在 kernel 本身。`[实测+推论]`
- **专家读 32% 却没有字节数**：`VRAM hits` 只给时间。要算利用率必须从路由轨迹 × expert-profile 逐层枚举
  （R22 那套方法可以复用），这是下一步**最该补的测量**。

## 6 HC 探测结果（2026-11-01 17:2x，一次重启，已恢复）

### 做了什么

`STRATA_HC_Q8=0` + `STRATA_DECODE_TIMING=1` → 重启 → 三个请求 → 取相位表 → 恢复原配置 → 重启。
两个开关都不改算式（前者换读完路径，后者只打印），所以是单变量。

### 结果：**没有信号**

| 表 | 条件 | total (ms/窗口) | hc 合计 | 窗口数 |
|---|---|---:|---:|---:|
| #112 | Q8=1（历史） | 41.51 | 6.30 | 111 |
| #113 | Q8=1（历史） | 53.05 | 8.09 | 83 |
| #118 | Q8=1（历史） | 33.19 | 5.34 | 166 |
| #119 | Q8=1（历史） | 40.98 | 6.67 | 54 |
| **#120** | **Q8=0** | **44.98** | **7.46** | 100 |
| #121 | Q8=0（冷） | 52.62 | 10.15 | 60 |
| **#122** | **Q8=0** | **43.43** | **7.69** | 11 |

**同配置下的 hc 在 5.34–8.61 之间跳**（±30%）。Q8=0 的 7.46/7.69 完全落在这个噪声带里。
⇒ 这次探测**没有分辨力**，不能用来判"关掉 HC_Q8 更快还是更慢"。

**方法学修正（重要）**：之前我把「hc 6.89 ms」当精确值去推"97 GB/s、慢 2.5 倍"，那是**用一个噪声 ±30% 的量算出来的比值**。
字节数是准的（644 MiB，R22 逐张量枚举），带宽比值不可当结论用——要判就必须交错多轮取配对。

### 但探测给了一条更硬的线索

**字节翻倍（Q8 644 MiB → bf16 1.28 GiB）几乎不改变 hc 的时间** ⇒ 这条读**不是带宽受限**。
配合源码，瓶颈指向**并行度**：

| kernel | grid | threads | blocks/CU（60 CU） | 占用率（2048 thr/CU） |
|---|---|---:|---:|---:|
| HC `down`（`gr_down_q8_kernel`） | `dim3(Q8_RG+1, Q8_NKC)` = **11×16 = 176** | 256 | 2.93 | **≈37%** |
| HC `up`（`gr_up_q8_kernel`） | `UPM_BLOCKS` = **160** | 256 | 2.67 | **≈33%** |
| 对照 `native_mmvq` wave | 按行切，几千个 block | 256 | 远高于此 | 接近饱和（245 GB/s 的来源） |

（`Q8_RG = LR/(WARPS*Q8_RPW)`，`Q8_KC = 640`、`Q8_NKC = D/640 = 16`。）

### AUDIT19 把这个判断改了

上面「瓶颈指向并行度」的推理**在 STREAM 实测后站不住了**：

| 事实 | 数值 | 来源 |
|---|---|---|
| 纯流式读在 1 block/CU（256 thr/CU） | 549 GB/s = 53.7% 屋顶 | AUDIT19 §1 实测 |
| 纯流式读在 4 blocks/CU（1024 thr/CU） | **884 GB/s = 86.3%** | 同上 |
| HC 现在 176 blocks = 2.93 blocks/CU | 按插值应能到 ~78% ≈ 690 GB/s | 外推 |
| HC 实测 | **98 GB/s = 11%**（噪声上界也只有 14%） | 相位表 |

⇒ **并行度只能解释 ~8% 的差距，剩下的 7 倍在别处**。源码给出了答案：`gr_down_q8_kernel` 里取一个
Q8_0 block 的 32 字节负载要发 **32 条 2 字节 `q8_ld16`**（`q = q8_ld16(...) | q8_ld16(...) << 16`，16 个 q），
而宽读只需 2 条 `uint4`——**这是指令发射率受限，不是带宽、也不是占用率**。

同时 **R27 的「block 越少越快」被降级**：它是 rows/block 与 block 数一起变的混淆实验，
不能外推成「占用率不是杠杆」（AUDIT19 §3.2）。

### 下一步（改过的）候选顺序

1. **R30 · 受控并行度实验**（零停服）：`native_mmvq` 只改 grid、不动 rows/block，看 469 GB/s 能否上移。
   这是唯一能判定「53% 屋顶还有没有上限」的实验，也决定 HC 要不要跟着改 grid。
2. **R31 · HC 的 load 指令吞吐**：按 16 B 对齐的块先把数据搬进 LDS，再从 LDS 取 2 B 片段。
   **求和顺序不变 ⇒ 可要求 `diff=0`**，不必过 KL 门。这是把「32 条 2 B load」降到「2 条 16 B load + LDS」。
3. 原 `Q8_KC 640→320` 方案**暂缓**：它改的是 chunk 粒度（求和序会变），应在 R30 定方向之后再动。

**先做微基准再重编**：`q8_wave_lab.cu` 那类秒级编译的小程序能先验证"blocks 翻倍 → 时间是否下降"，
不必每次花 8–10 分钟重编整个 TU。

## 7 受控实测（W863 §2，`ci/probe/read_probe.cpp`）：R31 被降级

外部文献查完之后我把最相关的两条做成了单变量实验（同字节，只改块数 / 只改访存宽度）：

| 形状 | S | 2 B 读 | 16 B 读 | 宽读收益 |
|---|---:|---:|---:|---:|
| HC down 10240→320 | 1 | 553 | 613 | +11% |
| | **4** | **621** | **826** | **+33%** |
| | 8 | 494 | 493 | —（发射受限） |
| GDN qkv 2560→10240 | 1 | 566 | 763 | +35% |
| HC up 320→10240 | 1 | **125** | 不可（行 340 B 不是 16 的倍数） | — |

**结论一**：split-K 有效但膝盖在 S=4（~21 blocks/CU），给 +12%；
**结论二**：宽读给 +11…+35%；
**结论三（最重要）**：**生产 98 GB/s，而最朴素的 2 B 读都有 553 GB/s ⇒ 读模式最多解释 1.5×，
剩下的 5.6× 在融合内核的其它工作里**（norm / 跨 lane 归约 / LDS 往返 / up 投影），或占用率。

⇒ 因此本文件 §6 里"HC 的 load 指令吞吐"那条**降级**，新的第一靶心是
**R32：量清那 5.6×**。完整方法与外部证据见 `deploy/W863_BANDWIDTH_METHODS.md`。

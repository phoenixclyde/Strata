## 2 `rest` 是什么：四段打点把它切成 145 + 24 + 13（r19/r20 实测）

一条续写请求的完整时间线（trace 时间戳同一条日志内，单位 ms）：

```
r0                    8640.2        ← 请求进入
previous commit joined 8640.3       ← 等上一请求的 verifier commit：0.1
kv ensured             8640.3       ← 弹性 KV 增长（池子够大 ⇒ no-op）：0.0
cache lookup done      8785.9       ← ★ 145.6  ← 这 145 ms 落在 14186–14318 这段代码里
mounted                8809.6       ← 快照挂载 +23.7（与它自己打的 "restored … in 24.7 ms" 对上）
checkpointed           8822.7       ← 检查点挂载 +13.1
request                8822.7       ← 读开始（rest 结束）
prompt start           8822.8 → read 46.3 → prompt done (slots refilled) 8869.1
```

**结论**：`rest = 145.6 + 23.7 + 13.1 = 182.4`，其中**挂载只占 24 ms**、检查点 13 ms；
> **【AUDIT20：差 50 ms 无点】** 本节这条时间线的 rest 合计 **182.4**，而 §1 表里同形状请求（1882 tok / 复 1877 / 读 5）的 rest 是 **232.6**，
> 差 **50.2 ms** 没有打点覆盖。两者不是同一条请求，但也没解释差在哪一段 —— **下一个打点要先补这 50 ms**。
**最大的一块 145 ms 在"读之前、挂载之前"** —— 即 `kvg_ensure` 之后到 `conversations.best()` 判定之间那 130 行。
这段时间**没有**AI 计算、没有 PCIe、没有大拷贝（`conversations.best` 是 O(停泊数×检查点数×前缀比较)，微秒级；
`bs` 在单流下为空）。**下一个打点就放在 `conversations.best()` 之前，即可二分。**

**为什么不是借槽回填**：`prompt done (slots refilled)` 在 8869.1，而 `request + read = 8822.7 + 46.3 = 8869.0`
⇒ **回填耗时 ≈ 0.1 ms**。本机 `--prefill auto` 单卡、请求只有 100–2000 token，`Prefill::relayout`
按请求实际需要借槽（源码原话：*"A request lends only what its own prompt needs"*），所以回填本来就不该贵。
#340 的 37% 代价是**长 chunk（2K–8K 一次读）**的场景，不适用于这一轮。

**顺带排除的其它候选**：检查点保存 0.0 ms（每请求都是）、PCIe 搬运 ≤25 ms、swap/缺页 0、
`majflt +0`、大缓冲区 mmap 抖动无。

## 3 `--short-read` 的交叉点实测（另一条独立收益）

> **【AUDIT20：本节结论已被 W867 判否】** 下表按「批路径 3.4–4.7 ms/tok 更快」推出「省 100–450 ms」，
> 但 W867 同进程 A/B 实测：5 新 token 走窗口 **262–269 ms**，强制批路径 **475–563 ms** ⇒ **窗口本来就快一倍**。
> 失败原因是批路径在极小输入上有一笔 **~250 ms 的固定成本**（W867 测得 read=256 ms/5 token）。
> 下表**只保留为当时的推理记录**，不要再照它改 `--short-read`。

| 追问新 token | 走的路 | `windows` | 若强制走批路径（按 3.4–4.7 ms/tok 估） | 收益 |
|---:|---|---:|---:|---:|
| 15 | 窗口 | 160 ms | ~60 ms | **省 ~100 ms** |
| 22 | 窗口 | 349 ms | ~90 ms | **省 ~260 ms** |
| 60（推测） | 窗口 | ~700 ms | ~250 ms | 省 ~450 ms |
| 102 | 批 | 45 ms | — | 已在批路径 |

默认 `short_read = 64`（`generate.cpp:889`）是按「批路径有 ~300 ms 固定成本」定的；
但实测两条路径**都要付同一个 `rest`**（221 vs 270 ms），所以那个 300 ms 的理由不成立，
交叉点其实在 **≈0–10 token**。`--short-read 0` 值得 A/B（配置一行，一次重启）。

   比其它任何单项都大；定位之后才知道是 CPU 循环、驻留/映射、还是某个设备查询。

   且实测回填 ≈0 ms ⇒ 本机大概率没有收益（除非换成长 chunk 场景再测）。

## 1 机理：先把「16 行 × 4 KiB」这件事说清

`include/strata/ngram/ple_reader.hpp:1-14` 逐字：

```
// The table is 320,001,536 rows of 90 bytes (IQ4_NL, 26.8 GiB) or 160 (FP8 E4M3, 51.2 GB) and is never held in
// RAM: every row comes from an unbuffered 4 KiB read (platform::DirectFile). A token needs 16 rows on 16
// different pages, and all 16 depend on the token itself, so the only time to hide them is the embedding plus
// layer 0.
```

本机实测表规模（启动日志）：`PLE on, table 320001536 rows of ...-00002-of-00003.gguf`。
`grep` 到的分片：**49,835,229,856 B**，表本体 = 320,001,536 × 90 = **26.8 GiB**。

相位口径（`src/prefill/prefill.cpp:2500-2504`）逐字：

> Events are recorded on the compute stream in order; the time between two consecutive marks is charged to the
> phase of the first, so **a gap where the GPU waits (for the host's expert grouping, or for an expert's copy)
> lands on the phase that was waiting**.

⇒ `ple` 这一项就是**这一段 GPU 空转**。本轮所有臂都同时印出主机侧累计值
（`prefill timing: host: ... PLE N ms`），两者相减在 10-40 ms，说明**主机侧 PLE 工作几乎没有和 GPU 重叠**。

`PleReader` 的流水线（同文件:5-14）：
- `issue`：token id 一确定就发；
- `collect`：layer 1 读之前收；
- prefill 把一整块的 16×N 行一次发出去，按页去重、按偏移排序，`max_inflight`（默认 256）深，
  **"a chunk's reads can run while the previous chunk computes"**。

这一句是本轮第二个实验（chunk 重叠）的全部依据。

### 2.2 判定

- **B `mmap`**：六格 TTFT **全对**（-3.4% / -1.8% / -1.8% / -0.25% / -2.1% / -0.7%，均值 **-1.7%**），
  `ple` 降 5-8%。但 A 与 A2 之间的地板就有 0.2-1.4%，这个量级**按规则（引擎级 A/B 只判 ≥5%）不采纳**。
- **C `ram`**：均值 **+0.03%**，即**没动**。原因见 §2.3。
- **D `row-cache 4M`**：0%。1M 行（95 MB）已经过拐点。
- **E `row-cache 0`**：`ple` 普涨 10-20%（如 2777：793 对 691），说明**行缓存本身值 15-20% 的 PLE**，
  但把容量翻 4 倍一点不加分 ⇒ 命中率受「一个提示内部 20-34% 的重复」限制，与容量无关。

### 2.3 关键异常：C 臂只有第 1 个请求是快的

C 臂：第 1 个请求 `ple=8 ms`、主机 PLE **23 ms**（`direct` 是 294 ms），第 2 个请求起回到 647/1168 ms。

跑完 C 臂时进程的 `RssFile` 只剩 **986,984 kB**（≈1 GB）——
**26.8 GiB 的表页被页缓存回收了，而这个映射还挂着**。同一时刻宿主 `Cached` 从 78.6 GB 掉到 43.8 GB。

机理：`--ple-io ram` 的 POSIX 路径是
`madvise(MADV_WILLNEED)` → **16 线程逐页 touch** → 整段 `mlock`
（`src/kernels/ngram.cpp:386-410`）。本容器 `ulimit -l = 8192 KB`，`mlock` 必然失败：

```
strata: PLE table mlock failed (Cannot allocate memory; raise `ulimit -l`): its pages stay faulted in but may be reclaimed
strata generate: PLE table loaded (not locked) (--ple-io ram) in 84.2 s
```

`locked=false` ⇒ 这些页只是**普通文件页缓存**，和引擎自己那 59.7 GB anon（专家竞技场 31.6 GB + 会话缓存等）
一起挤 128.7 GB。启动顺序是「touch 表（→ 78.6 GB cached）→ 载权重（→ anon 59.7 GB）」，
后期分配把**刚 touch 进来的表页挤出去**。

### 3.1 H-A：把 chunk 调小，让 PLE 藏到前一块的计算里 —— 机理成立，净效应是负的

- **PLE 那一列完全按预期掉**：2048 的 chunk 把 4568 的 `ple` 从 14.7% 打到 **6.8%**（绝对 1186 → 597 ms），
  4840 从 12.9% 打到 **6.1%**。机理被证实：**只有第一个 chunk 付钱，后面的都被前一块的计算藏住了**。

- 与上游一致：0.2.5 的发布说明逐字「NVIDIA cards under 16 GB now read prompts in chunks of 4096 …
  **a cold 8K prompt is 9% slower**」。

⇒ **P139 否**。这也把「小 chunk」这条路彻底封了：它省 PLE，但更贵。

## 4 门槛与代价：要采纳 `--ple-io ram` 得付什么

1. **RAM**：引擎稳态 anon **59.7 GB** + 表 **26.8 GiB（= 28.8 GB）** = **88.5 GB**，机器 128.7 GB。
   （**AUDIT11**：原文写 86.5 GB，是把 GiB 当 GB 相加；差额 2 GB 在"能不能放下"的判断里不影响结论，但数错了。）
   *够，但只在页缓存干净时够*——启动前不清理，26.8 GiB 会被挤掉（C 臂）。
2. **启动**：+216 s（表 touch 85 s + 之后载权重更慢）。上游 #4104 在同一件事上量到
   **310 s（~90 MB/s）**，并指出这是**用户态逐页缺页**的软件成本，而不是盘的带宽
   （同一块盘顺序读 979 MB/s）；#4105 给了修法（4 MiB O_DIRECT × 8 worker 读进 page-locked RAM，
   **23.7 s / 1215 MB/s**），但**两条都还是 open**。
   补充（W815）：本机启动本身分两档——**pack 在页缓存时 42-46 s 就绪**，**冷启 201-280 s**
   （55.43 GiB 竞技场按 0.27-0.40 GiB/s 读）；`+85 s` 就是 26.8 GiB ÷ 0.35 GiB/s，**换 NVMe 才压得下去**。
   而且这里有个绕不开的取舍：128.7 GB 里 59.7 GB 是引擎 anon，26.8 GiB 给表之后，
   **pack 的 55.4 GiB 页缓存就留不全** ⇒ 「启动快」与「提示快」二者只能选一个。
3. **mlock 拿不到**：容器 `ulimit -l=8 MB`，所以「lock」名不副实，任何别的进程要内存都可能把它挤走。
   上游 INTEL.md:723 对同一现象的建议是「**不要**给容器 `memlock=-1`，锁住的表和竞技场会一起挤爆 RAM」。
4. **解码侧**：稳态无代价（§5：槽位 9873 不变、解码 -1.1% 噪声内）。
   只有「表被换出」的非稳态才会掉 10-14%（W810 的 C 臂 42.44）。

⇒ 归纳成一句可执行的：**`--ple-io ram` 值 -14% 提示时间，但它买的是一个「必须每次冷启都先清页缓存、
并且长期占着 26.8 GiB」的运行态**。这不是一个能悄悄开着的开关。

### 6.1 逐字指纹查出一件比 PLE 更要紧的事：**这个构建的贪心输出不可复现**

`mt_hash.py`：同一 prompt、`temperature 0`、`top_p 1`、`max_tokens 200`，取 `content` 的 sha256。

| 臂 | H0 | H1 | H2 |
|---|---|---|---|
| PA（生产） | `6fbf2586…` n=1171 | `e6b05862…` n=1210 | `e46c4fd3…` n=1169 |
| RA（ram） | `bb9b9c0a…` n=1157 | `73e2ea71…` n=1140 | `d72b2a7d…` n=1164 |
| PB（生产） | `d78fe6ea…` n=1140 | `a354d5a9…` n=1132 | `fb81d68c…` n=1183 |

「The same prompt always takes the same path. The engine now picks the prompt path from the prompt's length
(96 tokens and more go through the chunked pass). **The old timing guess changed answers between runs.**」

两个直接后果：
1. **`--ple-io ram` 的答案是否等价，用"逐字指纹"这种方法在本构建上判不了**（基线自己就不稳）。
   要判只能走统计口径（36 题 / KL / 多次采样的分布），或者先升到 0.2.5 让路径确定。
2. **以前各轮凡是"跨重启比答案"的质量门，都带了一个此前没登记的方差源**——
   这是本轮在 PLE 之外挖到的、影响面更大的东西（登记为待办）。

## 7 污染审计与"显存能不能归零"

被问到了，逐项查（`albus/r5/audit_env.sh`）：

| 面 | 结论 | 证据 |
|---|---|---|
| 进程 | **干净**。全机只有我这一条 `ab_p44.sh` + 引擎 + `serve/server.py` + `strata-vision`（容器正常启动的一部分） | `pgrep -af`；`rocm-smi --showpids` 全程只有 `strata` 一个 KFD 持有者 |
| 配置 | **= 生产**：`env_n=12 / args_n=33 / 无任何 ple 参数 / --prefill auto / 无 TIMING|TRACE` | 每臂的 `CFGCHECK` 行 + 末次 `final env_n=12 args_n=33 ple_io=False` |
| 固化 | `verify_config` **PASS=36 FAIL=0**（六个数面） | `deploy/params/verify_config.py` |
| 注册表 | `gen_config --live` **（无差异）** | 同上 |
| 显存 | **能归零**：引擎在跑 33.72 GB → `docker stop` 5 s 后 **10.85 MB**（GTT 14.9 MB，驱动基线）→ 重启后又回到 **33.719 GB**，且进程占用逐字节相同（33,703,591,936） | `albus/r5/vram_zero.sh` |
| 页缓存 | 64.6 GB（含 ram 臂读过的 PLE 分片页），**可回收、不是污染**；`direct` 走 O_DIRECT，不受它影响 | `/proc/meminfo` |

**一个我自己造成的、必须登记的手工干预**：跑 D 臂（row-cache 4M）时我为了查另一件事执行了
`drop_caches`，那时 D 正在跑。影响评估 —— **AUDIT11 更正了两处**：

1. **`direct` 的只是 PLE 走 O_DIRECT；专家竞技场不走。** W815 用启动日志 + `src/core/pinned.cu:827` 证明
   Linux 上竞技场是 **buffered 经页缓存**（`read through the file cache (buffered (not Windows))` 是标签不是失败）。
   所以 `drop_caches` **会**让专家重读盘，原文"专家读也是 O_DIRECT"是错的。
2. **「D 的 `ple` 与 A 逐格差 <1%」不实。** 逐格实算：**+2.4 / −10.2 / 0.0 / −1.4 / +4.0 / −0.2%**；
   而同配置 **A vs A2 的地板本身是 0.3-8.3%**（1448 格 A=265 / A2=287）。

⇒ **D 的结论（`--ple-row-cache 4M` 无收益）仍然成立**，但依据必须换成"落在 A/A2 地板内"，
不能再用"差 <1%"。D 也不锚墙钟，只用 `ple` 相位，这一点原文是对的。
此后所有需要"页缓存干净"的臂（RD）都改成**显式、在启动前**做，并逐次记录 `DROPCACHES done` 与 `PLEMAP`。

## 8 登记与处置

| 编号 | 参数 | 结论 |
|---|---|---|
| **P138** | `--ple-io mmap` / `ram` | **REJECTED**（裸用）。`mmap` -1.7%（噪声内）；`ram` 0%（表被回收）。机理见 §2.3 |
| **P139** | `--prefill 4096` / `2048` | **REJECTED**。PLE 减半成立（14.6%→6.8%），但总时间 +5~9% |
| **P140** | `--ple-row-cache 4194304` | **REJECTED**。0%；1M 已过拐点（0 → −15~20% 才是它的价值） |
| **P141** | `--ple-io ram` + 启动前 `drop_caches` | **CANDIDATE（待解码门槛）**。-14% 提示；代价 +216 s 启动、26.8 GiB 常驻、mlock 拿不到 |
| **P142** | `--no-ple-prefetch` | **REJECTED**。+1.4%（噪声内），ext4 上无收益 |

**关闭 P138 这一族的依据**：表是 26.8 GiB 的随机 4 KiB 块，本机是 **SATA SSD（Fanxiang S100Pro）**，
实测持续 **≈68k rows/s = 68k IOPS**，已经压在 SATA 队列上限。参数面里没有任何东西能把它变快
（mmap/ram/row-cache/chunk/no-prefetch 五条路全试过）。

**真正能解的三条（都不是参数）**：
1. **换 NVMe**：4K QD256 随机读从 ~68k IOPS 到 400-700k IOPS ⇒ `ple` 从 250 ms/1k 降到 ~30 ms/1k，
   即 2.5-5K 的提示**再快 11-12%**（估算，按 IOPS 线性外推；上行 #2040 的 SATA/NVMe 对比方向一致）。
   这是本轮唯一一条「花钱就能拿到两位数」的结论。
2. **把 PLE 分片放到第二块盘**：现在专家流和 PLE 行共用一个 SATA 队列。本机只有一块盘（`sda`），
   没有第二块 ⇒ 与 1 等价。
3. **上游 #4105 移植**（O_DIRECT 读进 page-locked RAM，23.7 s）：只解启动，不解稳态。
   要它有意义还得先解 `ulimit -l`。

## 0 三句结论

1. **第 1 项在本机做不了，原因不是代码**：异步停放要一块 stage，
   `conversation_park_async_begin()` 的门是 `cudaMemGetInfo(fr) >= want + 3 GiB`
   （`want` = `need` 向上取整到 64 MiB ≈ **320 MiB**）。本机空闲 **0.8 GB** ⇒ 条件永假 ⇒ 直接 `return false`。`[源码]+[实测]`
2. **那 92 ms 的真实来源是另一条分支**（同一个 env 打开的）：`park_drops` 把本次要丢弃的**检查点搬进停放镜像而不是复制**
   （`generate.cpp:10738-10749`，`conversation_snapshot_save(..., &moved)`）。一个 1900-token 会话的检查点 KV ≈ 260 MB，
   省两次复制 ≈ 50–90 ms，与实测同量级。**W869 的「异步省一半」归因作废，已加更正横幅。**
3. **decode 基线立起来了**（零风险，从引擎自己的日志算，5799 条请求）：中位 **52.3 tok/s**（p10 42.9 / p90 61.4）、
   **19.08 ms/token**、草稿接受率中位 **0.87**。这是第 2 项的起点，任何 decode 改动都要对着它比。

## 1 为什么第 1 项被挡（三个数）

| 量 | 值 | 出处 |
|---|---|---|
| stage 需要的容量 | `want = 320 MiB`（260 MB ∧ 64 MiB 对齐） | `conversation_park_async_begin` |
| 代码要求的空闲 | `fr >= want + 3 GiB` ≈ **3.3 GiB** | 同上，逐字 |
| 本机空闲 | **0.8 GB**（`--vram-reserve-mib 832`） | 启动横幅 / `rocm-smi` |

⇒ 把这条门放宽（比如改成 `want + 512 MiB`）能让异步路径在本机跑起来，但那是**改上游的一条显存安全规则**：
0.8 GB 的余量里放 320 MiB 的临时缓冲，一旦同时还要分配别的东西就是 OOM，而 OOM 在引擎里是致命错误（不是回退）。
**不做**——收益（再省 ~75 ms 的 TTFT）与风险（整机 OOM）不成比例。

**另一条更干净的路**（留给以后）：不用 stage，直接 D2H 进**pinned 主机缓冲**（每个 part 一份），
再把 stage→镜像那一步省掉。但那要给 `ConversationBuffer` 加 pinned 形态，属于引擎内部改造。

## 2 顺带说明：现在的生产其实跑的是「move-only」

`STRATA_PARK_ASYNC=1` 在本机同时打开两件事，其中异步那件**因为显存不足是惰性的**，
所以实际生效的只有 `park_drops` 的 move。这个组合对本机是最优的（拿到 92 ms，且没引入未验证的 HIP 异步路径），
但它**不稳固**：哪天显存变宽（例如换小 context、减 expert cache），异步路径会突然真的跑起来，而它在 HIP 上从未被验证过。

⇒ **已在 r26 做掉**：新增 `STRATA_CKPT_MOVE_PARK`（env 或 `/data/strata-ckpt-move` 文件），`park_drops` 改由它驱动；
`STRATA_PARK_ASYNC` 回退为「只管异步停放」。config 已换成 `STRATA_CKPT_MOVE_PARK=1` 并撤掉 `STRATA_PARK_ASYNC`，
`/data/strata-park-async` 标记也删了。

**验证（r26，第九→第十次部署后实测）**：

| 形态 | `rest`（续写 5 新 token） |
|---|---:|
| 同步（基线） | 226.3 / 196.5 ms |
| async 臂（实际只跑到了 move） | 159.5 / 104.8 ms |
| **move-only（r26 现在的形态）** | **156.0 / 122.9 / 106.0 ms** |

浸泡 8 请求 **0 错误**（`ERR |non-finite |discard invalid` 全 0）。⇒ **-70…-90 ms 保留，且不再依赖一条本机永不执行的路径。**

## 3 decode 基线（第 2 项的起点）

从 `/data/strata-huihui-ud-iq4_xs.log` 直接算（5799 条请求，取最近 200 条）：

| 指标 | 值 |
|---|---|
| decode 中位 | **52.3 tok/s** |
| p10 / p90 | 42.9 / 61.4 |
| min / max | 24.1 / 66.9 |
| 每 token | **19.08 ms/token** |
| 草稿接受率（中位） | **0.87** |

按接受率分档：

| 接受率 | n | 中位 tok/s |
|---|---:|---:|
| 0.50–0.70 | 12 | 43.7 |
| 0.70–0.85 | 52 | 51.1 |
| 0.85–2.00 | 136 | **52.8** |

**读数**：接受率从 0.87 往上加已经没有多少空间（136/200 已在最高档且只有 52.8）；
而 p10 到 p90 有 18 tok/s 的散布，说明**变异性比均值更值得看**——这一点与 W863 的相位表结论一致（相位会迁移）。

⇒ 第 2 项的正确打法是**先解释那 18 tok/s 的散布**，而不是继续追单点峰值：
如果散布来自相位/热状态，那么「抬峰值」的改法在真实使用里会被摊薄；如果来自路由/命中率抖动，那才是可修的。

# W867 · `--short-read` 判否（实测窗口路径更快），并修掉一个自己的仪器 bug

> 2026-11-01 21:5x–22:1x。第六次部署后（`0.1.55o`，tag `mi50-0.2.9-r22`）。
> 本轮只有一条代码修复、一条判否、一条自纠。

---

## 0 三句结论

1. **`--short-read 0` 判否**：5 个新 token 的追问，走 verify 窗口 **262–269 ms**，强制走批路径 **475–563 ms**
   ⇒ 窗口快一倍，默认值是对的。`[实测]`
2. **我上一轮的「22 token 走窗口 349 ms，所以门槛 64 太高」也是错的用法**：349 ms 是 22 token 那次一起测的，
   而 5 token 只要 45 ms；窗口的每 token 成本随长度上升，交叉点大约在 **20–30 token**，把门槛压到 0 是把常见情形变慢。
3. **修掉一个自己造的仪器 bug**：`(win ? windows_ms : read_ms) += ms` 写在 `if (trace)` 里面，而 `trace` 是
   **进程生命周期**的（serve 循环之前求值）⇒ 启动时没有标记文件的进程，摘要会打 `read 0.0, windows 0.0, rest=全部`。
   r21 那一批数据因此**整批作废**（我已按 r22 重测）。`[实测]`

## 1 `--short-read` A/B（同一进程内，靠文件切换，零重启）

做法：`/data/strata-short-read` 里写一个数字就覆盖 `--short-read`（r21 加的，逐请求读；删文件即恢复）。

| 臂 | 文件内容 | 5 个新 token 的追问 | read | windows | rest | 合计 |
|---|---|---|---:|---:|---:|---:|
| A（默认） | 无 = 64 | 走窗口 | 0 | **46.3** | 215.8 | **262 ms** |
| B | `0` | 强制批路径 | **256.3** | 0 | 218.1 | **475 ms** |

另一组重复 A/B 同向：A 46.7/222.4 = 269 ms，B 274.7/287.7 = 562 ms。
⇒ **B 臂慢 213–293 ms（约 2×）**，`--short-read 0` 直接判否，保持默认 64。

**顺带得到的曲线**（A 臂，`--turn1 1200` 固定前缀）：

| 新 token | read（批） | windows | rest | 说明 |
|---:|---:|---:|---:|---|
| 5 | 0 | 45 | 222–228 | 全窗口 |
| 22 | 0 | 349（**r18 测，见 AUDIT20 A16**） | 235 | 全窗口，≈16 ms/token |
| 117 | 500 | 45 | 288 | 批为主，末尾一个窗口 |
| 163 | 611 | 45 | 295 | 同上 |
| 198 | 674 | 47 | 277 | 同上 |

（**AUDIT20 A16**：本表混了两个版本 —— 22 token 那行是 r18，其余是 r22 之后；r22 修过累加器的仪器 bug（见 §2），
r18 时标记文件在场所以那一行有效，但**同一张表混版本**会让复算者对不上。）

⇒ 窗口≈13–16 ms/token，批≈3.4–4.0 ms/token，但**批在极小输入上有一笔 ~250 ms 的固定成本**（B 臂 5 token 的 read=256）。
交叉点落在 **20–30 token**，与默认 64 相比，改成 24 可能再省 50–100 ms —— **收益不够大、方向不确定，先不动**。

## 2 仪器 bug（这条要记住，是第 11 次「先验证工具再信数据」）

```cpp
if (trace) {                                   // trace: 进程启动时求值一次
    const double ms = ...;
    (win ? req_times.windows_ms : req_times.read_ms) += ms;   // ← 累加器被关在门里
    ...
}
```

后果：22:00 那次部署时标记文件不存在 ⇒ `trace=false` ⇒ 累加器不动 ⇒ 摘要打出
`read 0.0, windows 0.0, rest 3590.3`（连冷启动 3590 ms 全算进 rest），而**同一请求上一行**还写着
`strata trace: read 4 tokens (windows) in 46.9 ms`。**两条日志自相矛盾**——这就是发现它的方式。

修法（r22）：把两行时钟读数移到门外，只有打印留在门内。

## 3 现在的账（r22 实测，单流、贪心）

一段多轮追问的 TTFT 组成：

| 段 | ms | 状态 |
|---|---:|---|
| `rest` 里的「读之前空白」 | **145** | 已二分到 r0→cache lookup 之间，尚未命名 |
| 快照挂载 | 24 | 与引擎自打 24.7 ms 互证 |
| 检查点挂载 | 13 | |
| 读（5 token，窗口） | 46 | 窗口路径，已判否改进方向 |
| 读（120–200 token，批） | 500–674 | 3.4–4.0 ms/token |
| 检查点保存 | 0 | 每请求都是 |
| 借槽回填 | ≈0.1 | 上一轮判否 |

⇒ **145 ms 是眼下唯一还没有名字的大项**（占 5-token 追问 TTFT 的 55%）。
r21 已经在 `conversations.best()` 之前放了一个打点，但它只在 `tr()` 打开时输出，而 `tr()` 又被
进程生命周期标志锁着 ⇒ **下次重启时要同时把 `tr()` 也改成逐请求判定**，那 145 ms 就能一次切开。

| **中位** | performance **47.03** / schedutil **45.94** | | **-2.3%**（中位的中位） | -3.1% | -2.0% | -2.6% |

**三对全部同向（schedutil 更低），四个指标一起动，量级一致。** 所以这不是噪声，也不是我先前猜测的"performance 更好"。

> **【AUDIT8 更正 2026-10-25 18:3x】** 上表末行的 **-2.3% 是"两个臂各自取中位再相除"**；按**逐对差值**算是
> 47.28/46.72 = **-1.18%**、46.04/45.68 = **-0.78%**、47.03/45.94 = **-2.32%** ⇒ **中位 -1.2%（区间 -0.8 ~ -2.3%）**。
> 方向与"三对同向"不变，**幅度按 -1.2% 用**。（AUDIT8 P1-3）

**这有三个后果：**

1. **`P97` 的疑问关闭**：governor 差异约 **1-2%**（逐对中位 -1.2%，区间 -0.8~-2.3%，见上方更正），方向是 `schedutil` 更优。把 W776 遗留的 `performance` 改回 `schedutil` **不是回归，而是小幅改善**。
2. **现存"performance 时代"基线偏悲观约 1.2%**（`P91` 的 46.35、`W788` 的 51.58、R5 的 53.17/53.02 都属于那一批）。
3. **R5 当初那个"+3% 回归"被解释掉了**：53.17 对 51.58 的 3%，与 governor 偏差（2%）和预热偏差（3%，见 §3）同量级，**本来就不该判成回归** —— 这与 `AUDIT7 P1-2` 的结论（5 runs 判不了 3%）互相印证，但这次给了机制。

## 3 协议新事实：重启后前几个请求偏高约 3%

同一套配置（`HC_Q8=1`、`schedutil`）在两次会话里：

| 时刻 | 该进程内的第几个请求 | total |
|---|---|---|
| R0 | 第 2、3 个 | 47.51 / 47.19 |
| R0b（先丢弃 2 个） | 第 4-9 个 | 46.72 / 45.68 / 45.94（schedutil 臂） |

差约 **3%**，与专家流从 `17.44` 回落到 `10.3` 同源：`--expert-cache auto` 是**按请求逐步填充**的。

=> **基线协议必须丢弃重启后的前 2 个请求**；之前所有"3 runs"（含 `P91`）都可能含 1 个偏冷样本。
这是一条比数字更重要的修正，已写进 `W776 §12.4`。

## 4 R5a：`HC_Q8` 复核（zero-code 单臂）

动机：读源码发现 `up` 的 fast 路径被 `!q8w` 挡住 ——

```
fused_gr.cu:33   // the latency-hidden norm/up (gr_norm_fast_kernel / gr_up_fast_kernel, STRATA_GR_FAST):
                 //   gfx906's, built for CUDA too
fused_gr.cu:1321 if (fast && !q8w) gr_up_fast_kernel<<<UPM_BLOCKS, THREADS, 0, st>>>(m);
fused_gr.cu:2189 gr_fast():  #if defined(__HIPCC__) return true;   // HIP 下默认开
```

也就是说：`HC_Q8=1`（我们现役）会把 `up` 切到 `gr_up_multi_kernel<...,true>`，拿不到那个"消掉依赖链"的实现。

做法：`arm_run.sh`（同 R0 的自恢复骨架）把 `STRATA_HC_Q8` 改成 `0`，丢弃 2 个请求后测 M×3。

| 指标 | `HC_Q8=1`（R0b schedutil） | `HC_Q8=0` | Δ |
|---|---|---|---|
| **total** | **45.94** | **47.45** | **+3.3%（更差）** |
| hc_down | 3.47 | 3.47 | **0%** |
| hc_up | 3.44 | **2.96** | **-14.0%（更快）** |
| hc_norm | ~0.58 | **1.54** | **+165%（更差）** |
| gemv | 5.92 | 6.13 | +3.5% |
| 专家槽 | **9901** | 9732 | -169 |

原始行已核对，`norm` 不是解析假象（`0.85 + 0.41 + 0.14 + 0.14 = 1.54`）。

**三条结论：**

1. **`P78`（采纳 `HC_Q8=1`）成立，而且比原来记的更硬**：它同时拿到 **-3.2% 墙钟**和 **+169 槽**。之前在 `P78` 里被标为"未定"的 decode 部分，现在有了机制性解释 —— `HC_Q8=1` 让 norm 快了 2.7 倍（0.58 对 1.54）。
2. **`hc_down` 对表示法完全不敏感**（int8 与 bf16 都是 3.47）。所以 `down` 那 9 倍差距**不是带宽/精度问题，是内核效率问题**，换表示法不解决 —— 这也否掉了"用更小的量化喂 down"这条路。
3. **`up` 有 14% 的已测结构余量**（2.96 可达，现役 3.44）。它来自 `gr_up_fast_kernel`，而该内核在 `HC_Q8=1` 下被 `!q8w` 排除。把 Q8 支持补进去，理论收益 **-0.48 ms（约 -1.0% 墙钟）**。

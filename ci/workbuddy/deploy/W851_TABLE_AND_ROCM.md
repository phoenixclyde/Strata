## 1 做了什么

用上游工具 `tools/hip/tune_rocblas.cpp`（引擎同款 tuner：逐形状枚举 rocBLAS 的全部 solution，
每个计时 + 对拍输出 + 检查「拒绝更小 T」），在**两个 ROCm 上各跑一遍同一份形状集**：

| 臂 | 镜像 | rocBLAS | tuner 构建 | 结果表 |
|---|---|---|---|---|
| 5.7 | `strata-gfx906:0.2.9r1`（ROCm 10.1.0 / HIP 7.16） | `5.7.0.962d0059` | `~/strata166/tuner-build-r101/tune_rocblas` | `~/strata166/data/gfx906-rocblas-5.7.0.txt` |
| 5.5 | `strata-gfx906:0.2.9t2`（生产，ROCm 7.14） | `5.5.0.cd957402309` | `~/strata166/tuner-build-r714/tune_rocblas` | `~/strata166/data/gfx906-rocblas-5.5.0-6b.txt` |

形状集 = 引擎的 **14 个 dense FP16 投影** × **6 个 token 桶**（256/512/1024/2048/4096/8192）= **84 case**。
（旧表只有 1024/2048/4096/8192 四桶，所以只有 56 行 —— 这是本轮的第二个发现。）

跑法：镜像内 `--device /dev/kfd --device /dev/dri`，**带生产同款 `HSA_OVERRIDE_GFX_VERSION=9.0.6`**；
两次都记录 `/metrics` 的 `totals.requests` 增量，**都是 0**（tune 期间没有请求进来，计时干净）。
单次全量 **4 分 50 秒**（84 case，比按单 case 外推的 2.4 h 快得多 —— 小形状的 solution 数很少）。

## 2 两张表逐行比对：**84 行判定完全一致**

```
版本: 5.7新=5.7.0.962d0059   5.5新=5.5.0.cd957402309   5.5旧=5.5.0.cd957402309
行数: 5.7新=84               5.5新=84                    5.5旧=56

== 5.7新 vs 5.5新 ==  共同行 84
   两边都 default : 9     两边都有解 : 75     判定相反 : 0

== 5.5新(6桶) vs 5.5旧(4桶) ==  共同行 56
   两边都 default : 9     两边都有解 : 47     判定相反 : 0
```

平均 gain：5.5 是 **3.13×**（75 个有解 case），5.7 是 **3.04×**。

⇒ **两代 rocBLAS 对这 84 个形状的内核选择完全一致**（0 个判定相反）。
解索引不同（-605557634 vs -605559119）是因为索引是 build-specific，但**「哪个更快」的结论一样**。

## 3 由此推翻 W850 的归因

W850 测到「10.1 的 read 比 7.14 慢 3.4–11.5%」，当时的归因是「10.1 + 没有可用表」。
现在可以更进一步：**那不是「10.1 的引擎/驱动更慢」，而是「表被版本检查整份挡掉」**：

```
prefill gemm: rocBLAS version mismatch: file=5.5.0.cd957402309 runtime=5.7.0.962d0059
```

而 §2 证明：只要把表重做成 5.7 版，**每个形状的最优解与 5.5 逐行相同**（连 default/有解的判定都一致）。

⇒ **切 10.1 的净收益 = 0**。它不退步（前提是重做表），但也不前进。
W850 那个 −3.4~−11.5% 全部由「表失效」解释，与 ROCm 版本无关。

## 4 真正的增量：256 / 512 两个桶（旧表完全没有）

按桶汇总 14 个形状的 GEMM 时间（5.5 的实测值）：

| 桶 | 形状数 | 库里默认选核合计 | 表里最优解合计 | 节省 |
|---|---:|---:|---:|---:|
| **T=256** | 14 | 10.50 ms | **4.58 ms** | **56.4%** |
| **T=512** | 14 | 15.78 ms | **7.82 ms** | **50.4%** |
| T=1024 | 13 | 16.43 ms | 9.79 ms | 40.4%（旧表已在吃） |
| T=2048 | 13 | 26.88 ms | 17.97 ms | 33.1%（旧表已在吃） |
| T=4096 | 11 | 31.90 ms | 25.11 ms | 21.3%（旧表已在吃） |
| T=8192 | 10 | 32.31 ms | 27.44 ms | 15.1%（旧表已在吃） |

前两行是**净增量**（旧表在这些 T 上没有行，`rocblas_tuning::Table::closest()` 会退回「最近的桶」，
即用为 T=1024 选的内核去跑 T=256）。后四行是旧表**已经在吃**的收益，重测只是复现。

**这解释了为什么「补小桶」比「换 ROCm」值钱**：小 chunk 正是 prefill 最贵的一段
（W804：1–3K 是 staging+CPU），而表在那里是空白。

## 6 为什么不可见（算术能闭合）

tuner 说的是真的 —— T=256 桶的 14 个形状合计 **10.50 ms → 4.58 ms**。
但要看分母：331 token 的 `read` 是 **1550–2100 ms**。

```
10.50 ms / 1550 ms = 0.68%      ← 这 14 个 GEMM 在一次 331-token prefill 里的占比
5.92 ms / 1550 ms = 0.38%       ← 把它们全换成最优解，能省下的比例
```

实测 −0.7%（n=7，且方向混乱）与 0.38% 是同一个量级。**这条闭合了：不是表没生效，
而是「小 T 时这 14 个 dense GEMM 本来就只有 10 ms 级」，改成最优也只能省 6 ms。**

这也反过来说明历史数据的合理性：W850 里「表被版本挡掉」能让长 prompt 慢 3.4–11.5%，
是因为 4096/8192 桶的 GEMM 合计是 **32 ms 级**、而长 prompt 的 read 分母大但 GEMM 增速更快；
小 prompt 恰好吃不到这个杠杆。

与 W804 的记录一致：**1–3K 的瓶颈是 staging + CPU，不是 GEMM**。表补到 256/512 桶，
等于在占比 0.7% 的地方省一半。

## 7 判词

| 问题 | 答案 |

| hipBLASLt 表能做出吗 | **不能**（`W851_HIPBLASLT_VERDICT.md`：白名单无 gfx906 + 实测 algos=0 + 构建不编） |

## 8 附带确认的两件事

1. **`STRATA_HIP_PROMPT_F16=1` 是开着的**（`STRATA_GFX906_TUNED=1` 配方里的 `HIP_PROMPT_F16` 带出来），
   日志横幅在：`STRATA_HIP_PROMPT_F16=1: the prompt's 16-bit GEMMs run FP16 in and out`。
   ⇒ 表所作用的 f16_inplace 路径在生产上是活的。
2. **prompt chunk 是 8192**（`strata serve: prompt chunk auto: 8192 tokens, a 384-slot ring`）⇒
   一次 prefill 的 T 通常就是 8192，**256/512 桶只服务「短 prompt」与「长 prompt 的尾 chunk」**。
   这是判读收益时要带上的量纲：它不改善长 prompt 的稳态 prefill，只改善短请求与尾巴。

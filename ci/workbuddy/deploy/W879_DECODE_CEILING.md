## 0 三句结论

1. **3 MB 这个尺寸不是墙**：纯读（无算术）能跑 **608.7 GB/s**（5.2 μs），是 GEMV 的 5.5 倍。`[实测]`
2. **墙是 M（每窗口 token 数）**：同一份 3 MB，**M=1 → 238 GB/s（13.2 μs），M=4 → 110 GB/s（28.6 μs）**。
   而 `M=3.11`（生产实测）正好落在 110 附近 —— **生产的 22 μs/专家与独立探针的 28.6 μs 同一量级**。`[实测]`
   ~~没有实现缺陷~~ —— **【C4 · AUDIT21】这一步跨大了**：两者是**不同精度**（4-bit vs fp16），同量级说明「跨精度比较不亏」，
   不等于「同精度下没有缺口」。`R37` 实测的 295 vs 487 GB/s（1.65×）正是同精度的缺口，本文没触及。
3. **「合并专家 kernel」的收益只有 1.1×，不是 1.25–1.7×**：每 block 行数 1→4→8，GB/s 只从 110.0 → 116.4 → 120.9。
   ~~⇒ 按 `W878` 自己定的判据（≥600 GB/s 就收口），decode 的 kernel 线到此为止。~~
   **【A4 · AUDIT21】这条已撤回**：探针是 fp16，生产是 4-bit grouped GEMM，不是同一个 kernel；
   生产 kernel 的 1.65× 缺口（`R37`）本文没触及。见顶部横幅与 `W832` §6.5。`[实测]`

## 1 纯读：尺寸 → 带宽（上限曲线）

`--mode read`，100 次重复，3 MB / 12 / 48 / 96 MB：

| 数据量 | grid=1024 | grid=4096 |
|---:|---:|---:|
| 3 MB | **608.7 GB/s**（5.2 μs） | 204.5（15.4 μs） |
| 12 MB | 204.8（61.4 μs） | 712.4（17.7 μs） |
| 48 MB | 646.0（77.9 μs） | **808.8**（62.2 μs） |
| 96 MB | **806.4**（124.8 μs） | 774.2（130.0 μs） |

两个读数：

- **3 MB 能到 609 GB/s**（网格 1024）⇒ 早前「3 MB 太小、跑不满」的判断**不成立**，那是 v1 探针每 block 只读 8 KB 的产物。
- **网格必须与数据量匹配**：3 MB 用 4096 个 block 反而只有 204 GB/s（每线程读不到 1 个 float4）；48 MB 则需要 4096 个 block 才到 809。

## 2 GEMV：M 是主因，线程组织只值 10%

`--mode gemv`，3 MB（1 个专家），fp16，K=4096：

| M | rows/block | 时间 | GB/s | μs |
|---:|---:|---:|---:|---:|
| 1 | 1 | 13.22 μs | **238.0** | 13.22 |
| 1 | 4 | 13.34 μs | 235.9 | 13.34 |
| 1 | 8 | 14.60 μs | 215.5 | 14.60 |
| 4 | 1 | 28.59 μs | **110.0** | 28.59 |
| 4 | 4 | 27.03 μs | 116.4 | 27.03 |
| 4 | 8 | 26.02 μs | **120.9** | 26.02 |

- **M 从 1 到 4，带宽掉 54%**（238 → 110）。这不是带宽不足，是**每字节要做的 MAC 变成 4 倍**：
  M=4/110 GB/s ⇒ 110 GB/s ÷ 2 B × 4 = **220 GMAC/s**；而 M=1 的 238 GB/s ⇒ 119 GMAC/s。
  **M 越大，单位时间做的 MAC 越多** —— 符合「算术受限」而不是「带宽受限」。
- **rows/block 1→8 只给 +10%**（110.0 → 120.9）⇒ 这就是「合并一层 31 个专家」能拿到的全部，**1.1×**。
  `W875` 的 1.25–1.7× 来自 v1 探针的 3 MB vs 96 MB 对比，那个对比混了「网格不足」与「合并」两件事，**不成立**。

## 3 与生产对上了，而且生产不亏

| 项 | 值 | 口径 |
|---|---:|---|
| 生产每专家 | **22 μs**（31.42×48 专家 ÷ 33.11 ms GPU） | 引擎自报 |
| 探针 M=4 fp16 | 28.6 μs | 本探针 |
| 探针 M=1 fp16 | 13.2 μs | 本探针 |
| 生产每专家 MAC 数 | 6 M 权重 × 3.11 = **18.7 M** | 4-bit，3.135 MB（**W891 更正：2.99 是算错的，`21.79 GiB ÷ 7463 = 3.135 MB`**） |
| 探针 M=4 每专家 MAC | 1.5 M × 4 = **6.0 M** | fp16，3 MB |
| ⇒ 生产吞吐 | **850 GMAC/s** | 18.7 M ÷ 22 μs |
| ⇒ 探针吞吐 | **536 GMAC/s** | 6.0 M ÷ 11.2 μs（v1 的最佳形态） |

**生产在单位时间内做的 MAC 比 fp16 探针多 58%** —— 4-bit 的价值（同样字节做 4 倍乘加）**已经吃满**。
「22 μs vs 11 μs」看起来像生产慢一倍，换成 MAC 就是生产快 1.6 倍。

> **【B3 限定 · AUDIT21】比较对象不同，不能据此说「没有可挖」。** 这里比的是 **4-bit 生产 vs fp16 探针**（两种精度）；
> 而 `R37` 比的是 **同一精度下生产 vs 理想形态**：生产 **295 GB/s** vs 同算术 **487 GB/s** = **1.65×**，
> 那部分字节效率的缺口与精度无关，本文**没有触及**。原来的「没有 2.5× 可以挖」只对**跨精度**成立，已删。

## 4 一条被顺手排除的开关：`STRATA_MMVQ_IL` 在 HIP 上是空壳

`verify.cpp:175` 有 `STRATA_MMVQ_IL`（默认开，2–4 列时走 interleaved 变体，注释说 bitwise 相同）。
它看起来像「n=3.11 专属优化」，值得 A/B —— **但 `native_mmvq.cu:4015` 逐字**：

```
#else  // HIP: no interleaved path
bool native_mmvq_il_supported(int, int, int) { return false; }
int  native_mmvq_il_rows_for(int, int, int, int) { return 0; }
void native_mmvq_il(...) { native_mmvq(...); }
```

⇒ 在 gfx906 上这个开关**完全惰性**（和 P245 的 async park 是同一类陷阱：**开关存在 ≠ 路径存在**）。
**不要拿它做 A/B。**

## 5 ~~结论：decode 线收口~~ —— **已撤回（AUDIT21 / W882）**

`W878` 定的判据是「3 MB / M=4 若 ≥600 GB/s ⇒ 合并无利可图、decode 收口」。实测：

- 纯读 3 MB = **608.7 GB/s** ≥ 600 ✓
- GEMV M=4 = 110，合并后 121（+10%）

⇒ **判据命中，收口。** decode 的 `13.2 ms/token / 75.8 tok/s` 不是「浪费了带宽」，而是：

```
每 window 41.1 ms = 8.3 ms 固定（draft 3.4 + host 2.1 + 发射）
                 + 10.6 ms × T（T=3.11，由 min-p 决定，动不了）
其中专家 GEMV 33.1 ms 是「3 MB × 31.42 专家/层 × 48 层」在 M=3.11 下的算术成本，
不是带宽浪费（带宽只用到形状上限的 110/238 = 46%，而形状上限本身由 M 决定）。
```

**要再往上，只有三条路，都不在「调参」范围内**：

1. **改量化**（4-bit → 3-bit）：直接减字节，但质量代价大，且模型是给定的；
2. **改模型**（更少的每 token 专家数）：路由决定，top-k=10；
3. **改硬件**（更高 fp16/INT8 吞吐或更大 L2）：L2 只有 4 MB，一个专家 3.135 MB。

## 0 三句话

1. **R75 的假设被证伪**：R66 三补丁把 borrows 从 2606 压到 **1904（−27%）**，但 64K 的 TTFT **一点没变**（76.557 → 76.451）。"borrows 是长 prompt 变慢的原因"判错了。
2. **但发现了一个测量方法的系统缺陷**：`bench_pair.py` 的 `text_of(words, seed)` 让**短 prompt 成为长 prompt 的前缀**（同 seed 前 N 词相同），导致 `reused > 0` 的污染数据。**W931 的"64K 上 16384 慢 7.6%"就是被这个污染的，真相是 16384 快 6.2%。**
3. **`--prefill auto:16384` 已采纳**：六个长度全部不劣，越长优势越大（16K +2%、32K +5%、64K +6.2%、130K **+8.1%**），decode 与多轮复用都不受影响。

## 2 测量方法的系统缺陷（本轮最重要，影响所有历史 prefill 数据）

`ci/bench_pair.py`：

```python
def text_of(words, seed):
    rnd = random.Random(seed)
    return " ".join(rnd.choice(VOCAB) for _ in range(words))     # 50 词的词表
```

每次用 `seed + i`。**同一个 seed、不同 words ⇒ 短的是长的前缀**（`Random(11)` 前 N 个词完全相同）。

服务端日志把这个暴露得很清楚（64K 请求，同一实例，连续 8 条）：

```
61246 tokens = 8192 reused + 53054 read in 70807 ms (749.3 tok/s)   ← 污染
61246 tokens = 8192 reused + 53054 read in 71230 ms (744.8 tok/s)   ← 污染
61246 tokens =     0 reused + 61246 read in 76206 ms (803.7 tok/s)  ← 干净
61246 tokens =     0 reused + 61246 read in 81442 ms (752.0 tok/s)  ← 干净
```

**W931 的 A2 臂 71.130 s 属于第一组**（含 8192 token 复用），而不是纯 prefill。

还有一个更隐蔽的表现：同一参数连跑两次 `bench_pair`（不重启），第二次**全部命中 prompt cache** —— 实测 32K 的 rep1–3 TTFT 是 **0.199 / 0.177 / 0.169 s**，而 rep4–5 才是真的（40.272 / 40.487 s），于是 median 被拉成 30.174 s、CV **16.2%**。

### 修法（已进纪律）

**只采信服务端日志里 `0 reused` 的记录**。日志格式固定：`prompt N tokens = R reused + (N-R) read in T ms`。

`bench_pair` 本身也要改：seed 应按长度区分（如 `seed * 100003 + words`），使不同长度不共享前缀。

## 4 `auto:16384` 的完整账（全部 `0 reused`）

### 4.1 prefill：六个长度全不劣

| 长度 | 8192 | **16384** | Δ |
|---|---|---|---|
| 6.4K（1 chunk，不变） | ~8.8 s / ~716 tok/s | 8.790 s / ~722 | ≈0 |
| 16K | 20.56–20.78 s / 738–760 | 20.233 s / 759 | **+1~3%** |
| 32K | 40.27–40.55 s / 755–762 | 38.542 s / 794 | **+5%** |
| 64K | 81.0–81.5 s / 752–756 | **76.2–76.5 s / 801–803** | **+6.2%** |
| 130K | 177.9 s / 729.6（129783 tok） | **165.1 s / 788.7**（130225 tok） | **+8.1%** |

**越长优势越大** —— 与"chunk 越大，GEMM 的 M 越大、权重复用越好"一致。

### 4.2 decode：不受影响

`n=9`，256 tokens：**median 80.58 tok/s，CV 2.2%**（去冷启 78.3–82.1）。
对照 8192 的 79.05 ⇒ **+1.9%，噪声内**。

（第一轮 n=4 只得 71.69 是**预热不足**，W920 的老教训复现；n=9 后才稳定。）

### 4.3 多轮复用：不受影响

`multiturn.py` 4 段 × 2 轮，prompt ~6580 token：

```
conv1–4 的 turn2 复用率：99.68 / 99.68 / 99.68 / 99.69%
```

对照 8192 的 **99.72%** ⇒ **−0.04pp**。

原因：多轮 prompt 只有 ~6.6K，在 16384 chunk 下是 **1 个 chunk**，复用是整块级别，与 chunk 上限无关。

⚠️ **仍有一个未验证的角落**：**部分前缀复用**（例如长文档多轮，第二次只加了几句话）。64K 请求在 8192 模式下能复用恰好 8192，在 16384 模式下复用 0 —— 说明**复用粒度是 chunk 大小**。这类场景本次没测，列为 R76 的候选。

### 4.4 显存：无净代价

| 项 | 8192 | 16384 |
|---|---|---|
| expert cache | 7463 slots / 21.79 GiB | **7463 slots / 21.79 GiB（不变）** |
| VRAM free | 920 MiB | **920 MiB（不变）** |
| prefill 期间 borrows | 1578（4.62 GiB） | **2606（7.62 GiB）** |

borrows 只在 prefill 期间生效，decode 时归还，所以常驻布局一点没变。

### 4.5 按负载加权的预期收益

| 区间 | 占比 | Δ | 加权 |
|---|---|---|---|
| ≤8192（1 chunk） | 60.8% | 0 | 0 |
| 8–16K | 2.2% | ~0 | 0 |
| 16–32K | 5.8% | +2% | +0.12% |
| 32–48K | 1.6% | +5% | +0.08% |
| 48–64K | 4.7% | +5% | +0.24% |
| **>64K** | **24.8%** | **+7%** | **+1.74%** |
| **合计** | | | **≈ +2.2% prefill** |

而长 prompt 的 prefill 占端到端比例更高，所以**端到端收益大于 2.2%**。

**`auto:32768` 仍不采纳**：借 62.5% cache（4667 槽），32K 上已比 16384 慢 1.9%。

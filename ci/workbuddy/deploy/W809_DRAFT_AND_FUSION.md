## 1 为什么先做这三件事

`W808` 把解码相位拆开之后（GPU-reach wait 31.85 ms = **72.1%**，draft 3.82 = 8.6%，commit/emit 0.04 = 0.1%），
剩下的可动项只有三类。逐条上网核对上游读数，三条都有现成的先验：

| 项 | 上游读数（逐字） | 出处 |
|---|---|---|
| `--spec` 深度 | `--spec 3` 1.145 / `--spec 4` **1.122** / `5` 1.079 / `6` 1.060 / `8` 1.027（story/code/document，3 对） | `DETAILS.md:2492` |
| `--spec-min-p` | `0.0` = 10.4（接受 52%）/ `0.5` = **12.2/12.0/11.7**（68%）/ `0.7` = 11.8/11.4/11.6（**93%**） | `A770_SPEED_SPEC.md:243-248` |
| `STRATA_B6_MMVQ_ROWS=1` | 「exact multi-column MMVQ reusing the activation fragment across rows (K-quants, IQ4_XS)」，**bit-exact**，**+0.2..1% / +0.5..2%** | `DETAILS.md:2514` |
| 七开关融合整套（sm_60） | P100：decode **36.56 → 41.76 tok/s（+14.2%，8/8 对）**，identity gate 相同 | `OLDER_GPUS.md:100-110` |
| 六开关融合整套（sm_86） | 整套 **+9.6% / +14.6%（8/8 各）** | `DETAILS.md:2435` |

我们的现状：`--spec 4`、`--spec-min-p 0.70`（`P06`，早期 `calibrate` 扫出来的 0.33/0.5/0.7 = 33.74/35.72/**36.96** tok/s），
而 `src/core/nv_defaults.cpp:22-46` 的默认表**只给 sm_86 与 sm_60**、`arch_defaults.cpp` 只给 gfx12/gfx1151
⇒ **gfx906 两套默认表都是空的，这些融合一个都没开**。

**`W808` 的扫描器抓不到这一类**：它找的是 `#if defined(STRATA_USE_HIP) … opt-in … #else … default on …` 的宏形态，
而这类是**运行时 `setenv` 的架构默认表**。方法论的补丁：扫默认表，不只扫宏。

## 2 仪器先升级，否则测不动

第一轮（`w809_spec`）每臂只跑 3 个 prompt，`A` 与 `A2`（同配置两遍）差 **5.2%**，而待测效应只有 2-3% ⇒ 判不了。

改成：每臂 **6 个 prompt × 200 token**、**丢掉前 2 条**（重启后前两个请求是冷的，`P98`），取后 4 条的
`ms/token = ms/window ÷ tokens/window`（引擎内部测，不含客户端；`generate.cpp:15050` 的字段定义）。
第二轮 `P` 与 `P2` 同配置只差 **0.1%** ⇒ 分辨率进到亚百分点。

**但第三轮又坏了**：`P` 与 `P2` 差 **6.9%**，因为 `P` 臂的 `per-layer host` 是 **3.00 ms** 而其余臂 1.67-2.15 ms
——主机侧被别的负载干扰（per-layer host 含 plan/actq/jobs/CPU experts）。**教训：这台机器上，host 抖动比 GPU 大一个量级，
凡是 ±1% 级的旋钮，A/B 都判不了**，必须换仪器（§5）。

## 3 结果一：`--spec-min-p 0.50` 是中性，`0.70` 站得住（`P06` 复核通过）

`W809b`，臂 `P`(0.70) / `S`(融合整套) / `Q`(0.50) / `S2` / `P2`，每臂 6 prompt 丢前 2：

| 臂 | avg T | tok/win | ms/win | **ms/tok** | GPU-reach | 接受率 | 相对 P |
|---|---|---|---|---|---|---|---|
| **P**（0.70，生产） | 2.25 | 1.86 | 37.05 | **19.82** | 29.38 | 68.7% | — |
| **Q**（0.50） | 2.83 | 2.05 | 40.80 | **19.89** | 32.18 | 59.6% | **+0.4%（中性）** |
| S（融合整套） | 2.26 | 1.79 | 38.61 | 21.40 | 28.18 | 64.8% | +8.0% |
| S2（整套重复） | 2.27 | 1.84 | 39.03 | 20.89 | 28.00 | 67.7% | +5.4% |
| **P2**（0.70 重复） | 2.35 | 1.92 | 37.90 | **19.79** | 30.06 | 68.0% | **−0.1%** |

**读法**：把 `min_p` 从 0.70 降到 0.50，`avg T` 从 2.25 涨到 2.83、`tokens/window` 从 1.86 涨到 2.05（+10%），
但 `ms/window` 也涨了 10%（37.05 → 40.80，GPU-reach +9.5%）⇒ **两边正好抵掉**，`ms/token` 差 0.4%，
而同配置两遍的差是 0.1% ⇒ **中性，不是改进**。

**这同时推翻了我第一轮的读法**：第一轮（3 prompt、不丢冷启）给出 `0.50` 比 `0.70` 快 2.8%，且「4/4 配对都更快」。
换成 4 条稳态样本后是 +0.4%。第一轮那个 4/4 是**把冷启当成了信号**。

**`--spec 6` 不用再测**：第一轮已有（`E` 臂，`avg T` 3.9）**+11.4%**，接受率从 63.8% 掉到 47.3% —— 更深的窗口把
低概率草稿也拖进来，每窗口成本涨得比产出快。上游 `DETAILS.md:2492` 的 spec 扫描也是 `4` 最好。

⇒ **`P06` 维持 `--spec-min-p 0.70`**，`P05` 维持 `--spec 4`。**没有采纳任何参数。**

## 4 结果二：九开关融合整套在 gfx906 上是负的（−5.4~−8.0%），而它在 P100 上是 +14.2%

臂 `S`/`S2` 把 `src/core/nv_defaults.cpp` 里 sm_86 那张表的九项全部显式打开：

```
STRATA_SIDE_MIXER=2  STRATA_ATTN_DAILY=1  STRATA_GR_UP75=1  STRATA_GU_SWIGLU=1
STRATA_QSA_ROWS=1  STRATA_B6_MMVQ_ROWS=1  STRATA_ADAPT_NOWAIT=1  STRATA_ADAPT_LAG=2
STRATA_CPU_IQ_ALL_EXACT1=1
```

自证：`FUSECHECK engine_env_hits=0`（P 臂）对 **`9`**（S 臂），从容器内 `/proc/<pid>/environ` 数出来的，
所以差异确实来自这些开关。

| | 相对生产 | 备注 |
|---|---|---|
| `S`（第一次） | **+8.0%** | 逐条 20.6/21.3/21.5/22.6 |
| `S2`（重复） | **+5.4%** | 逐条 20.2/21.6/20.1/22.2 |
| 上游 sm_86 | **−9.6% / −14.6%** | 8/8 对 |
| 上游 P100（七开关） | **−14.2%**（36.56→41.76 tok/s） | 8/8 对 |

**机理**：这些融合的前提是「launch 开销占比大、SM 多、波形切换便宜」。gfx906 的占用率只有 **6.8%**（`P96`），
且 decode 的瓶颈是 `GPU-reach wait`（纯等待 GEMV 算完），把两个 launch 合成一个并不能让 GEMV 变快；
`SIDE_MIXER=2` / `ATTN_DAILY=1` 这类「换布局」在 8.x 上是按 8.x 的 warp 宽度与 L1 行为量的。

⇒ **这一族在 gfx906 上整体关闭**（`P135`）。这也是一条更普遍的结论：
**「上游在别的架构上 bitwise + 两位数收益」不能作为本卡采纳的依据** —— 与 `W797` 的「相位会迁移」同构，
只是这次发生在**架构之间**，而不是同一次运行之内。

## 5 结果三：`B6_MMVQ_ROWS` 用微基准判死（这是本轮方法上最重要的一步）

既然 `B6` 的上游读数只有 **+0.2..1%**，而我们的 A/B 分辨率是 ±5%（host 抖动）——用引擎级 A/B 判它**注定失败**。
第三轮实测也确实是：`B6` −5.7% / `B64` −7.2% / `G` −5.6%，而 `P2` 是 −6.9% ⇒ **全在基线漂移内**。

正确工具是源码自带的 `src/kernels/b6_mmvq_bench.cpp`：**GPU 事件计时、每格 50 次取中位、
「immune to the host」**、并且逐格 memcmp 验证 bitwise。它在镜像里没编译，`ninja b6_mmvq_bench mmvq_multi_parity`
增量构建即可（约 2 分钟，不动 `strata` 二进制；构建后 `md5sum` 仍是 `184f8ade…`）。

结果（**90 个形状 × 4 种 rows 模式 = 360 个组合**）：

| 量 | 值 |
|---|---|
| 与默认布局的中位偏差 | **+0.00%** |
| \|偏差\| > 2% 的组合 | **76 / 360** |
| 最大收益 | **−12.0%**（`qsa q Q6_K` cols=1） |
| 最大损失 | **+12.7%**（`shexp down IQ4_NL` cols=2） |
| **bitwise 失败** | **0**（每格三列 `ok ok ok`：B=A、A=1col、B=1col） |

我们真正在用的格子（cols 2-4、IQ4_XS / Q6_K）示例：

| 形状 | cols | A (ms) | m1 | m2 | m4 | m8 |
|---|---|---|---|---|---|---|
| gdn gate Q6_K | 2 | 0.0427 | **−11.5%** | −11.5% | −11.5% | −11.5% |
| gdn out IQ4_XS | 2 | 0.0286 | −5.6% | −4.9% | −5.6% | −5.6% |
| gdn qkv Q6_K | 4 | 0.0813 | **+6.3%** | +6.5% | +6.5% | +0.0% |
| gdn qkv IQ4_XS | 3 | 0.0650 | +0.2% | +0.2% | +0.0% | +0.0% |
| qsa q IQ4_XS | 2-4 | — | ±0.2% | ±0.2% | ±0.2% | ±0.4% |

**读法**：它是**逐形状的洗牌**（有的格子真快 11%，有的真慢 12%），而一个窗口要跑 47 层 × 十几次投影，
正负混在一起就摊平到 0（中位 0.00%）。上游那 +0.2..1% 是它的净结果，我们量不到，也不该在这里赌。

⇒ **`P136` REJECTED**（bitwise 所以无质量风险；但也没有可判的收益，且存在逐形状 −12% 的格子）。

### 5.1 顺带钉死一个结构性事实：本卡报 **compute capability 9.0**

基准自己的 banner 逐字：

```
=== device 0: AMD Radeon Graphics (sm_90, L2 8192 KB), 50 reps, median ms per call, B = rows mode 1 ===
```

`il_cc()` / `il_arch_ok()` / 各处 `cudaDeviceGetAttribute(cudaDevAttrComputeCapabilityMajor)` 走的是同一个 shim，
所以 **gfx906 在这套构建里被当作 9.0 卡**。这解释了：

- `W806` 的 `P127`（`decode_defaults_arch_ok()` 走 CUDA 分支）—— 不是偶然，是**系统性的**；
- `il_arch_ok()` 的 `major >= 8` 恒真 ⇒ 所有「sm_80+ 才用」的分支都会放行；
- `nv_default_env(9, 0)` 返回空表 ⇒ 融合开关一个都不开（`§4` 的原因）。

⇒ 以后凡是看到「上游按 compute capability 分支」的默认值，都默认「本卡会走 **major=9** 那一支」，先用这个判。

## 6 三条死路，本轮一次性登记（省掉以后的 GPU 时间）

| 项 | 为什么是死路 | 证据 |
|---|---|---|
| **`STRATA_MMVQ_IL_ROWS`**（2..4 列交错布局） | `native_mmvq.cu` 里整块实现的外层是 `#if !defined(__HIPCC__)`（2941 行），HIP 构建走 `#else // HIP: no interleaved path` 的 stub ⇒ `native_mmvq_il_supported()` 恒 false，连解析器都不编译 | `native_mmvq.cu:2941 / 3262` |
| **`STRATA_MMVQ_IL_WIDE`**（5..8 列） | 同上，且 `kIl58Arch` 只有 `{120, 1201}` 两张卡的表 | `native_mmvq.cu:3072-3075` |
| **suffix draft / `--lookup-chain` 调参** | suffix drafter 每请求只开 **1-2 个窗口**（全请求约 100 窗口），接受 0-4/3-6；lookup chain 在日志里 **0 行**（未启用） | `grep -c "suffix drafts:" = 2443` 行，每行 `1-2 windows` |

**顺带纠正一个我先前的假设**：我看到 `kIlRowsShared` 里 IQ4_XS 的 `ncols=3 → {0,0,2,4,4}`，
一度以为「T=3 是唯一拿到 rows=4 的列数，所以 min_p 0.5（avg T≈3）最快」。
**这条机理不成立** —— IL 根本没编译进来（上面第一行），`min_p` 的收益（若存在）只能来自
「专家读取按窗口摊销」，而 `§3` 的实测已经证明它是中性的。

## 7 方法论（这轮真正的产出）

1. **仪器分辨率必须小于效应量，否则换仪器**。待测 +1%，A/B 噪声 ±5% ⇒ 任何结果都是噪声的形状。
   本轮的正解是**用上游自带的微基准**（GPU 事件计时、50 次中位、bitwise 断言），成本 2 分钟构建。
2. **同配置两遍是唯一的价格标签**。第二轮 `P` vs `P2` = 0.1% 让「+0.4% 是中性」成立；
   第三轮 `P` vs `P2` = 6.9% 让那一整轮作废。**先看这个数，再看结论**。
3. **host 侧抖动比 GPU 大一个量级**（`per-layer host` 3.00 vs 1.67）。解码相位账里 host 只占 9.4%，
   但它能在两次相同配置之间漂 80%，所以凡是要判 ±1% 的，必须让 host 安静或绕开 host。
4. **架构默认表要逐个扫**：`nv_defaults.cpp`（sm_86/sm_60）、`arch_defaults.cpp`（gfx12/gfx1151）、
   `decode_defaults_arch_ok()`（宏）、`il_arch_ok()`（cc >= 8）。本卡在四张表里全是「不在名单」，
   而 shim 又把它报成 9.0 —— 两者叠加就是这一串「默认值错位」的总根源。

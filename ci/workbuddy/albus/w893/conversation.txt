===== 002 assistant =====
这个思路**完全可行，而且是你目前拿到 4 人 DeepSeek 并发最务实的方案**——原因在于：vLLM 跑不了 Strata 这套 2.25bpw 的 GSQ-RCO GGUF（它是 llama.cpp/Strata 专用量化，vLLM 要的是官方 FP8/BF16 那 510GB，4×48G=192GB 装不下）。所以"每卡一个 Strata 实例 + 前置路由"反而是让 4 个人各享单用户质量的正解。

## 原理

每个容器 = 1 张卡 = 1 个单序列引擎 = 同时服务 1 人。4 个容器 + 路由，≤4 人并发时每人都落在一个空闲实例上，**互不排队、各自满速**（单卡 48G 约 25–40 tok/s）。第 5 个人才会排队。

## 但瓶颈从显存转移了——三件事你必须先确认

| 约束 | 说明 |
|---|---|
| **系统内存（最关键的）** | 每个实例仍要把装不进显存的专家 + 运行时放在 RAM。单卡 48G 比 12G 卡省 RAM，但 4 个实例叠加，**总 RAM 预算 256GB 起步、384–512GB 才从容**。注意：把**同一个模型目录 bind-mount 进 4 个容器**，OS 页缓存只缓存一份（同文件同页），4 实例共享，能大幅压低总 RAM。 |
| **NVMe（共享、需高速）** | 只存**一份** 274GB 模型（含 111GB Engram），4 实例并发随机读同一块盘。用 PCIe 4.0 高速盘（≥5GB/s），慢盘会被 4 倍读放大拖死。 |
| **CPU 核心** | 溢出的专家在 CPU 算，4 实例需足够核心（建议 32–64 核总量，或每实例 8–16 核）。 |

> 验证办法：先在宿主机或一个容器里跑 `strata launch --family deepseek41 --model ist-das-2.25bpw --plan`，看单实例的 VRAM/RAM 分配，再把 RAM 需求 ×4 核对总内存。

## 一、2026 最值得注意的新引擎

**1. DeepInfer（DeepSeek 官方开源，2026-10-20，Apache 2.0）**
这是今年和 DeepSeek V4.1 Flash 最相关的新引擎——它就是 DeepSeek 自家生产环境跑 V4.1-Flash 的栈，自带 DSpark 投机解码、EP+EPLB 专家并行、确定性采样。但有个**致命限制**：

> DeepInfer 只支持 **NVIDIA SM100（Blackwell，如 B200/GB200）和华为 Ascend 950**。官方 README 明确**不列 Hopper/Ampere**，你的 4090 是 Ada Lovelace（SM89），**不在支持范围**。

所以它对你目前**用不了**——除非你换 Blackwell 卡。先记着，未来换卡再考虑。

**2. llama.cpp（b11870+，2026-10-25 起原生支持 V4.1 Flash）**
这是和你 4 容器方案**直接竞争**的新进展：llama.cpp 现在原生跑 DeepSeek V4.1 Flash（含图），而且它的 `llama-server` 自带 **`-np` 并行槽位**。这意味着你可以**不拆 4 容器 + nginx**，而是跑**一个 llama.cpp 实例**、`--tensor-split 48,48,48,48` 把模型摊到 4 卡、`-np 4` 直接服务 4 人并发，单端点更简单。代价：Strata 官方宣称其引擎比通用 llama.cpp 快 ~3×（针对 Engram 卸载和 DSpark 调过），所以同硬件下 Strata 单用户更快，但 llama.cpp 胜在"一个进程搞定多人"。

**3. SGLang / vLLM（仍是多用户生产的双雄）**
- vLLM 已到 **0.23.0**（P-EAGLE 投机解码、Model Runner V2）；SGLang **0.5.13** 带 RadixAttention（多轮 agent / 前缀复用绝佳）。
- 两者都有 V4.1-Flash 的预览镜像（`vllm/vllm-openai:deepseekv41-flash-0909`、`lmsysorg/sglang:dev-dsv41`），但**全量 510GB 需要 8×H100/H200**，你的 4×48G=192GB 装不下——所以它们**跑不了 763B 的 DeepSeek**，但**能轻松跑 Qwen3-Coder-Next（FP8 ~87GB，TP=4 富余）**。

**4. TensorRT-LLM（NVIDIA 官方，最快但最重）**
数据中心的 A100/H100/Blackwell 上比 vLLM 快 30–50%，但编译模型要一两天、NVIDIA-only。4090 能跑，但对你这种"消费卡 + 超大模型"场景收益有限；若想榨 Qwen3-Coder-Next 的极致速度可考虑。

**5. Omlx（2025 末新兴轻量引擎）**
代码干净、易改，性能接近 llama.cpp 但仍落后于 vLLM/TRT-LLM，目前小众，暂不必上。

## NInfer 是什么

一个从零手写的 **C++20 / CUDA 推理引擎**（Apache 2.0，2026-06-26 首发），设计哲学和 vLLM/llama.cpp 相反：**不追求通用，只为一两张特定显卡 + 少数几个模型做极限优化**，所以跑得极快。上游 `Neroued/ninfer` 锁死在 **RTX 5090（sm_120a, Blackwell）**，编译系统直接拒绝其他架构。

但社区迅速做了**各架构分支**，其中就有你的卡：

| 分支 / fork | 目标架构 | 显卡 |
|---|---|---|
| `Neroued/ninfer`（上游） | sm_120a | RTX 5090 |
| `ruwwww/ninfer-5060ti` | — | RTX 5060 Ti |
| `ashalliants/ninfer-3090` | sm_86 | RTX 3090 |
| **`T-Crypt/ninfer-4090`（Linux, sm_89）** | **sm_89** | **你的 RTX 4090** ✅ |
| `UDPSendToFailed/ninfer-4090`（Windows） | sm_89 | RTX 4090 |
| `JGamboa/ninfer-4090-windows`（int8-prefill 版） | sm_89 | RTX 4090 |

> 关键点：**4090 和 4080 都是 Ada Lovelace / sm_89**，所以这些 sm_89 分支能直接在你魔改 4090 上编译运行。

## 这对你的 4×48GB 方案意味着什么

**它直接替换/强化了之前"vLLM + Qwen3-Coder-Next 给多人编码"那条路线**，而且更贴合你的卡：

2. **你 48GB 是纯红利**：同一模型只吃 ~17GiB 权重，剩下 30GB 全砸进 KV——**262K 上下文毫无压力，甚至冲 350K**；或空出来的显存可以试 **Qwen3.6-35B-A3B（MoE，~21GiB 制品）**（4090 分支"继承但未充分测试"，你 48GB 正好有空间验证）。

## 但它救不了你 DeepSeek 那条线（限制要说清）

## 对你部署 LLM 真正有意义的几点

**1. 带宽近乎打平——这是 MI50 唯一的"牌"**
LLM 的 decode（逐 token 生成）是**显存带宽瓶颈**，而两边都是 ~1 TB/s。所以**纯 decode 的理论上限接近**；但 4090 还有更高的算力去跑投机解码（NInfer 的 MTP 能把 4090 推到 130–150 tok/s），MI50 算力太弱撑不起同等投机深度。

**2. 算力差 6–12 倍——prefill 和量化内核全靠它**
Prefill（读长上下文）、MoE 路由、INT8/FP8 量化 GEMM 都是**算力瓶颈**。4090 的 330 TFLOPS Tensor + 660 TOPS INT8 让它在这些环节碾压 MI50 的 26.5 / 53。这也是为什么 NInfer 能在 4090 上把 Qwen3.8-27B 跑到 130+ tok/s，而 MI50 跑同模型会慢一个量级。

**3. 容量 48G > 32G，且 4090 有 FP8**
你 48G 能整装 Qwen3.8-27B 还留 ~30G 给 KV（冲 350K 上下文）；MI50 32G 更紧。而且 4090 原生 FP8 让 KV cache 量化（vLLM fp8_kv、NInfer rk4v4）翻倍扩容——**MI50 没 FP8，长上下文劣势明显**。

**4. 软件生态是决定性差距**
这正好接回咱们第一个话题：gfx906/MI50 在 ROCm 里已被弱化（社区报告需 ROCm 7.14 镜像、无 hipBLASLt 内核、Strata 仅 community-tested、Wave64 无 matrix core）。而你的 4090 是 **sm_89，NInfer/vLLM/SGLang/llama.cpp 全原生支持**。MI50 想跑同样的引擎，移植成本和坑远高于 4090。

**5. MI50 仅有的两个真实优势**
- **ECC 全芯片**：7×24 长时间跑、数据完整性要求高时比无 ECC 的 4090 稳。
- **Infinity Fabric 互联**：多卡 P2P 比 4090 的"纯 PCIe、无 NVLink"强。但对你这种本地 4 卡、靠路由分流（每卡独立实例）的玩法，**互联几乎用不上**——你根本不做跨卡 all-reduce。

## 一句话总结

**4090 48G 在算力（6–12×）、显存容量（1.5×）、FP8、软件生态上全面压过 MI50 32G，唯一打平的是带宽、唯一落后的是 ECC 和原生多卡互联；而对你"每卡独立实例 + 路由"的部署形态，MI50 的互联优势也发挥不出来。** 所以你手里 4 张 4090 48G 远强于 4 张 MI50——除非你极度看重 ECC 和二手白菜价，否则 MI50 不值得换。

## GSQ-RCO 到底是什么

这套 2-bit 量化是两个方法拼起来的：

| 缩写 | 全称 | 干什么 |
|---|---|---|
| **GSQ** | Gumbel-Softmax Quantization | 训练后**标量量化**：用 Gumbel-Softmax 松弛去学习"每个权重值取哪个网格点 + 每组缩放因子"。在 2–3 bit 区间把**标量量化**和更贵的**矢量量化（QTIP/AQLM）**之间的精度差距基本抹平，同时仍兼容标准 GGUF 格式 |
| **RCO** | Riemannian Constrained Optimization | **在总比特预算下给每个张量分配格式**：敏感的层多留比特、皮实的层狠压，用黎曼流形上的梯度优化**精确卡死总体积**，不用手调超参 |

一句话：**GSQ 负责把每个张量压到指定精度，RCO 负责在"总大小不超预算"的前提下智能分配（哪层该保、哪层可压）**。这就是为什么 2-bit 还能几乎不掉分。

| 张量类型 | 量化格式 |

## 二、KV 量化：这条数据里**没明说具体 `--kv`**，但有两层要分清

这是关键，容易混：

**1. 模型自带的架构级 KV 压缩（始终开启，与 Strata 无关）**
DeepSeek V4.1 Flash 原生用 **CSA2（Compressed Sparse Attention 2）** + **FP4 主 KV 缓存**，把全局 KV 压到 **890 bytes/token**（上一代的 1/4）。它分两支：
- **global 分支**（随序列长度线性增长，长上下文大头）：main KV（FP4 压缩）+ indexer K，常驻 HBM；
- **SWA 分支**（滑动窗口 128 token，固定大小）：未压缩 KV。

这套是模型架构决定的，**只要你跑 V4.1-Flash 就在用**，不是 Strata 的开关。

**2. Strata 的 `--kv` 开关（可选进一步压缩）**
Strata 另外提供 `--kv` 档位：`fp16` / `int8` / `q4_0` / `k8v4`（K 用 INT8、V 用 4bit 混合）。但 toolmintx 那篇和 Strata 官方测速表**都没有标注这个 2.00bpw 测速用了哪个 `--kv`**，只说了 "**The KV cache lives in graphics memory**"（KV 在显存里）。

考虑到：
- 该测量在 **4.6K 上下文**（默认 8K 窗口内），KV 体量很小，本来就不需要激进量化；
- 官方默认 `--context 8192` 是"校验过"的档，大概率走**默认 KV（未额外量化 / 即原生 FP4 CSA2）**。

> 所以严谨地说：**这个 40.2/615 的例子，KV 用的是模型原生 FP4 CSA2（890 bytes/token），Strata 侧没开额外 `--kv` 量化**。要更激进省显存（比如冲 256K+ 上下文），才需要显式加 `--kv q4_0` 或 `k8v4`，但那会牺牲一点质量且超出官方校验范围。

## 一、为什么利用率满了功率还在大幅摆

1. **decode 负载天生是"脉冲式"的**：单序列每生成一个 token，要跑一堆小 kernel（每层：attention → 路由选专家 → 专家 GEMM → 反量化），kernel 之间还要等 CPU 做专家选择、等 RAM/SSD 取专家。于是 GPU 在"密集计算脉冲"和"等 CPU/内存的空窗"之间来回切换——功率自然跟着锯齿状上下跳。
2. **Vega 20 的 DVFS 很激进**：负载一冲高就 boost 时钟、功率跟着冲；一进空窗或撞到 power cap，时钟又被压下来、功率回落。这个 boost↔drop 的来回 thrash 会把功率画出大波浪，**也顺带吃掉一点性能**（每次变频都有开销，空窗降频后下次又得重新 boost）。

所以：你看到"算力到顶但功率乱跳"，说明 GPU 在**高时钟脉冲**和**降频空窗**之间振荡，而不是在稳态高负载。

## 二、先确诊：是撞 power cap 还是纯 DVFS 抖动

```bash
rocm-smi --showpower      # 看当前功率是否贴着 cap（撞 cap 会触发降频振荡）
rocm-smi --showtemp       # 看 hotspot / edge 温度，热节流也会造成功率摆
rocm-smi --showclocks     # 看 sclk 是否在 max 和低位之间反复跳
```

- 如果 **power 一直顶在 cap 上、clock 在 max↔中档之间跳** → 是 power-cap 振荡，抬 cap / UPP 能解。
- 如果 **power 没顶 cap、但 clock 仍乱跳** → 纯 DVFS 反应过度，锁频即可。
- 如果 **温度高且伴随降频** → 散热/热点问题（Vega 20 的 VRM/热点温度是个老毛病）。

## 三、最对症的一招：锁频，消除振荡

Vega 20 上直接锁住时钟，让 DVFS 别再 thrash——这是消除功率摆动、并把"真实稳态天花板"逼出来的标准做法：

```bash
# 锁定到一个固定高时钟（去掉 boost/drop 抖动），单位是 MHz，取 showclocks 里的 sclk max
rocm-smi --setperfdeterminism 1600     # 例如锁 1600MHz，按你卡的 sclk 上限填

# 或手动固定 performance level（更硬）：
echo manual | sudo tee /sys/class/drm/card0/device/power_dpm_force_performance_level
rocm-smi --setsclk 0 1 2 3 4 5 6 7     # 允许到最高档（再配合 --setperfdeterminism 更稳）
```

锁频后你会看到：**功率不再锯齿、稳定在一条线附近，tok/s 通常会略涨 5–15%**（少了变频开销，且不再掉进低时钟空窗）。同时它也能告诉你"在这个频率下到底能跑多少"——排除了 DVFS 干扰后的真值。

## 一、Strata 有没有专门给 gfx906 写的内核？——没有

Strata **没有为 gfx906 手写专门的 dp4a / v_dot4 / v_dot8 MMQ 内核**。证据来自它的构建系统和 issue：

- gfx906 构建开关是 `-DSTRATA_HIP_GFX906=ON`，在 CMake 里，gfx906 分支给 `strata_mmq` 这个库打上 **`GGML_USE_HIP`** 宏（issue #2459 原文：`target_compile_definitions(strata_mmq PRIVATE GGML_USE_HIP)`）。
- 那个 MMQ 库里有文件直接 `include llama.cpp's common.cuh`（#2459 确认：`mmq_nvfp4_w4a4.cu includes llama.cpp's common.cuh`）。
- 它的 CUDA 内核（`native_moe.cu`、`native_qsa.cu`、`router_top10.cu` 等）是 `.cu` 文件，**gfx906 上就是同一套 .cu 经 HIP 重编译**，没有另写 `.hip` 或 gfx906 专用文件。所谓 gfx1151 的专用 barrier 是给 gfx1151 的，跟 gfx906 无关。

所以：**gfx906 上的量化矩阵乘，走的是 llama.cpp 的 ggml MMQ 内核，以 HIP 后端编译**。dp4a（`v_dot4`）确实在用——但它是 **llama.cpp 的 dp4a，不是 Strata 原创**。NVFP4 的 w4a4/w4a8 那条路是 RTX-50 专属，gfx906 根本不参与（#2459、#1691 都确认）。

## 二、那 Strata 拿 llama.cpp 来干嘛？（你的疑惑点）

一句话：**Strata 是个"调度 + 内存分层 + 服务"引擎，真正的矩阵乘算力是借 llama.cpp 的 ggml 后端跑的。** llama.cpp 在 Strata 里干三件事：

| 角色 | 说明 | 证据 |
|---|---|---|
| **① GGUF 容器与加载** | 模型以 GGUF 格式发布（llama.cpp 定义的格式），Strata 的 `src/artifact/gguf_reader.cpp` 解析它 | 模型以 GGUF 发布；`gguf_reader.cpp` 读容器 |
| **② MMQ（反量化 + 量化矩阵乘）内核** | 实际在 GPU 上算量化权重的就是 llama.cpp 的 ggml-cuda MMQ（HIP 后端）。这是"矩阵乘"的全部算力来源 | 发布说明 v0.2.2 明写"a faster dp4a in **llama.cpp's MMQ kernels**" |
| **③ ggml 的张量/量化类型支持** | IQ3_XXS 这类量化格式的 unpack 与运算来自 ggml | 量化类型在 ggml 里定义 |

而 **Strata 自己原创的部分**是：`session.cpp` 的会话循环、48 层图捕获、`expert_cache.cpp` 的专家三级缓存（VRAM↔RAM↔SSD）、`cpu/pool.cpp` 的 AVX-512 CPU 专家池、`core/mtp.cpp` 的投机解码、`ngram/ple_reader.cpp` 的 SSD 查表层。也就是**"模型怎么存、怎么调度、怎么路由专家、怎么分三层"是 Strata 的；"矩阵怎么乘"是 llama.cpp 的**。

## 三、这跟你 45 tok/s + 带宽十几% 完全对得上

因为 gfx906 的 MMQ 就是 **llama.cpp 的 HIP 版 dp4a 内核**，而上游/旧版 llama.cpp 的 gfx906 MMQ 正是 hipfire 测过的那种**行并行（row-parallel）变体**——无 LDS、无数据复用、GPU/wall 比 1.04×、VALUBusy 卡在 ~48% 的发射率墙。这正是你看到的"算力到顶、带宽饿着"。

而那个**能破墙的优化**（tiled + LDS + 异步复用、`v_dot8_i32_i4` 把 int4 权重指令数减半）只存在于 **iacopPBK/llama.cpp-gfx906** 这种社区 fork 里，**不在 Strata 引用的 llama.cpp 版本里**。

**2. 窗口①：又一次"改到死代码"（`P446`）**

三臂 ctl / pa3+`ATTN_DP4A` / pa3+`DPP`+`LDS_PAD`+`ROUTE_DPP`，每臂 2.5K×2 + 8K×2 + 16K×2。`qsa attn` 8K **2238 → 2235 / 2232 ms**、16K **4731 → 4718 / 4750 ms**，整条 prefill 偏差 ≤0.15%（2×CV 0.19%）——逐毫秒不动。

**4. 深挖：为什么"照理会快"却慢了（`P449` / `P450`）**

常数 `CHUNK=64`、`THREADS=256`、`G=12`、`HD=256`、`NSC=4`、`top_k=2048` ⇒ **每 query 64 个块**。

- 量化段（`qsa_decode_attn.cu:234-247`）：`if (t < G*NSC)` 只有 **48/256 线程**，每线程串行 64 次 amax + 64 次 div/cvt ≈ **448 条**，其余 208 线程等 `__syncthreads`，且**每 query 重复 64 次**；
- 分数段确实省：每 cell 每 lane 基线 ≈130 条（12×8 FMA + 反量化 + reduce12），dp4a ≈85 条 —— 但每 8 个 MAC 只省 3 条（2 `v_dot4` + cvt + 2 mul 收尾 vs 8 `fma`），4× 密度被吃回 1.6×。

**对照项目**：iacop `fattn-q8.cuh` 的 `quantize_Q_to_shared` **全线程参与**、一块摊 `nbatch_K`(128–256) 个 key、KV 原生 Q8_0 不需反量化。
**外证**（skyne98，同代 MI50 实测）：热循环 QDQ 的 int8-dot4 **2.00 TOPS vs fp32 5.95（0.34×）**；摊薄复用后 dot4 21.7 vs 13.0（1.67×）。同站 dot 吞吐 sdot4 21.7–22.3 TOPS ⇒ **硬件没打折**。

**5. 窗口③：warp-per-group 把 DP4A 救回来（`P451` / `P452`）**

只改一处：48 个组 ÷ 8 warp（每 warp 6 组）、**每 lane 2 个值**、5 级 `__shfl_xor` 求 amax、各转自己那 2 个值 —— 形状抄 llama.cpp `quantize_q8_1`。

| 形状 | ctl `qsa attn` | pa5+DP4A | Δ | ctl 整条 | pa5+DP4A | Δ | 2×CV |
|---|---|---|---|---|---|---|---|
| 2.5K | 575 ms | **510** | **−11.22%** | 1584.4 µs/tok | 1573.9 | −0.66% | 5.07%（不显著） |
| 8K | 2234 ms | **1982** | **−11.29%** | 1253.6 | **1231.2** | **−1.78%** | 0.50% |
| 16K | 4714 ms | **4212** | **−10.65%** | 1278.7 | **1258.1** | **−1.61%** | 0.11% |

decode 59.00 → 61.45 tok/s（CV 8–10%，不可分）。

**位相同**：`amax = max(|x|)` 与顺序无关，`d = amax/127`、`round(x/d)` 逐元素同一表达式 ⇒ 码字逐字节不变，−11% 全部来自调度（旧 48/256 线程、448 条/线程；新 256/256 线程、≈84 条）。

**6. 顺带修掉一个静默正确性洞（`P448`）**

`STRATA_ATTN_OPT_DISPATCH`（`qsa_decode_attn.cu:1077`）只有 `case 1/2/4`，`default: break;` 之后直接 `return` ⇒ 同时开两个开关（如 `DPP|LDS_PAD` = 5）会**一个内核都不发就返回**，调用方照常 merge，输出是残留数据、**不报错**。已扩到 `case 1..7`。窗口①恰好被 swizzle 挡住，否则那臂会测出"零成本"的假象。

**7. 数值门：判否（`P453`）**

工具 `tools/quant_quality.py`（`run` / `compare`），5 段 × 999 位 = **4995 个配对点**，三臂：

| 臂 | 内容 | top-1 | KL | KL p99 | PPL（run / ref） |
|---|---|---|---|---|---|
| A vs Ab | pa5 + `ATTN_DP4A=0`，同 argv 两容器（**自一致地板**） | **100.00%** | **0.00000** | 0.0000 | 4.048 / 4.048 |
| A vs B | pa5 + `ATTN_DP4A=1`（开关） | **93.55%** | **0.04130** | 0.6109 | 4.057 / 4.048 |

- **地板是 0**（100% / 0.00000）⇒ 环境完全确定，0.0413 不是噪声，是开关本身；
- 两条判据**都破线**：KL 0.0413 是阈值 0.0139 的 **3.0 倍**，top-1 93.55% 差 99% 线 **6.45 个点**；
- 归因干净（技能 §6）：A 与 B **同 exe、只差一个 env** ⇒ 这一门归因到 `ATTN_DP4A` 一个开关，不是整栈。

**⇒ 判决：pa5 不装机。** 它用 1.78% 的 prefill 换掉 6.45 个百分点的 top-1 与 3 倍的 KL——按项目标尺这是负优化，
`P451` 从 OPEN 改 **DONE_NEG**，`deploy_gate` D4 保持红。代码留在 `gfx906/port-all`、开关默认关。

**偏差（必须写，否则会被当生产值）**：工具 FIXED 强制 `--expert-cache 1500` / `--pcie-frac 0` / `--adapt-every 100000` /
`STRATA_PREFILL_CPU_SHARE=0` / `STRATA_ROUTE_TAIL_SKIP=0`；**`--kv` 从工具默认 fp16 改为 `k8v4`** ——
否则 `kv_mode=0`、dp4a 派发条件（`kv_mode==3||kv_mode==1`，`qsa_decode_attn.cu:1146`）永不成立，这一门会测出「零差异」的假通过。
它测的是 **GPU MMQ 内核的 prefill 数值**，不含主机侧 CPU share。

**8. 为什么"大幅提升"却过不了数值门：误差正好落在 0.19 nat 的判决边上（`P454`）**

把两臂的 4995 个位置逐点对齐（`margin_analysis.py`）后，答案很硬：

| 量 | 值 |
|---|---|
| argmax 变了的位置 | **322 / 4995 = 6.45%** |
| 其中 A 的第一名在 B 里掉到**第 2 位** | **234（72.7%）** |
| 参考侧 top1−top2 间隔（nats） | p10 0.025 · **p50 0.191** · p90 1.055 · p99 3.96 |
| 间隔 < 0.1 nats 的改动 | 103（占改动 32%，占全体 2.06%） |
| 间隔 < 0.5 nats 的改动 | 242（占改动 75%） |
| |Δlogp(target)| | 中位 **0.018** · p90 0.402 · max 10.1 |

**这不是"答案错了 6.45%"，是"在 0.19 nat 的分岔口上换了边"**——四分之三是和亚军互换了名次。
而 int8 查询的量化步长恰好就是这个量级：

- q 的 int8 步长 = 组内 amax/127 ⇒ RMS 误差 ≈ 0.45% × amax ≈ **1.3% × σ_q**；
- 分数 = 256 维点积 ⇒ 相对误差 ≈ 1.3% ⇒ 对一个 O(1–10) 的分数就是 **0.01–0.13 nat**；
- 观察到的中位间隔 0.191 nat、中位 Δlogp 0.018 nat —— **同一个数量级**。

**⇒ 结论不是"实现写错了"，而是"8 bit 的步长正好压在模型做决定的间隔上"。**
项目标尺要 KL ≤0.0139，等于要求噪声再小 3 倍；单档 int8 做不到（步长与位宽是指数关系）。

**9. 能救的路子：把这一层从 int8 换成 fp16 点积（`P455`，未实施）**

同一条分数段，换一种指令：

| 方案 | 每 8 个 MAC 的指令 | q 的相对误差 | 预计 attn | 预计 KL |
|---|---|---|---|---|
| 基线 fp32 fma | 8 `fma` | 0 | — | 0 |
| int8 `v_dot4`（已判否） | 2 dot4 + cvt + 2 mul = **5** | **1.3%** | −11% | **0.0413** |
| **fp16 `v_dot2_f32_f16`** | 4 dot2 + 1 mul = **5** | **0.03%** | 预计 **−8~−11%** | 预计 **<0.001** |

关键：`v_dot2_f32_f16` 是 **2 MAC/指令**，8 个 MAC 只要 4 条，而且**没有 int8 那套 cvt+2mul 的收尾**（k 侧 int8 转 f16 是精确的，scale 放到最后乘），
所以每头的指令数与 int8 路径相同（5 条），但 q 的精度从 1.3% 回到 0.03%——**快的一样快，误差小 40 倍**。
外证：同代卡上 `__builtin_amdgcn_fdot2 -> v_dot2_f32_f16`，摊薄复用后 21.9 TOPS vs fp32 13.0（skyne98 实测）。
工具链侧本轮已验证：`__builtin_amdgcn_fdot2(a, b, acc, false)` 在 `--offload-arch=gfx906` 下**编译通过**（`t_fdot2.cu`，CLANG=0，7,768 B 目标文件）。

**为什么还没有直接上**：它要新增一条 OPT 分支（共享 half 查询 tile + k 侧 i8→f16 打包 + 两个 score 分支各一份），
改错一处就是一次白烧的窗口。所以这一步按项目纪律走：**先编、再数值门、最后才测速度**；顺序不跳。

**10. 先看「误差长什么样」：不是位宽，是共模（`P458`）**

fp16 那臂的 KL（0.03798）几乎等于 int8 那臂（0.04130），这本身就不该发生——fp16 的查询误差是 0.03%，
int8 是 1.3%，差一个数量级。所以先不猜机理，把四份已有 tsv 拿来做误差结构分析（零窗口）：

| 量 | int8 臂 | fp16 臂 |
|---|---|---|
| argmax 变化 | 322 / 4995 = **6.45%** | 285 / 4995 = **5.71%** |
| \|Δlogp(target)\| 中位 | **0.01769** | **0.01930** |
| \|Δlogp\| > 0.01 的比例 | **54.41%** | **55.22%** |
| \|Δlogp\| > 0.5 的比例 | 7.13% | 7.75% |

**21. 根因：这七组 KL 是同一个数——度量测的是模型的混沌，不是内核的精度（`P468`）**

把已落盘的五只臂（基线 + 四个开关）**两两**比，不看「谁离基线近」：

| 对比 | 两者的扰动差 | KL |
|---|---|---|
| ctl vs `CTLREAD` | **1e-7** | 0.04111 |
| ctl vs `F16Q` | 1e-5 | 0.04479 |
| ctl vs `F16D` | 1e-5 | 0.03798 |
| ctl vs `DP4A` | **1e-2** | 0.04130 |
| **`CTLREAD` vs `F16Q`** | 1e-7 vs 1e-5 | **0.04221** |
| **`DP4A` vs `F16D`** | 1e-2 vs 1e-5 | **0.03544** |
| `CTLREAD` vs `DP4A` | 1e-7 vs 1e-2 | 0.04650 |

**决定性的是 `CTLREAD` vs `F16Q` = 0.04221。** 两者都只差 1e-7~1e-5，如果这个度量反映**精度**，它们彼此应该 ≈0；
实测却和「差 1e-2 的 `DP4A` vs 基线」**一样大**。七个数挤在 [0.0354, 0.0465]、跨度 1.31× ——
**任意两臂等距**，这是混沌映射的统计距离，不是精度排序。

**机制**：1e-7 的扰动经 48 层残差放大到 O(1e-2)，在 softmax 上把近 ties 翻边；于是**任何非零扰动都落到同一个宏观距离**。
而 `REDUCE12` / `DPP` 两臂**逐位不变**（零扰动），地板才恰好是 0.00000。

**外部核实（不是猜）**：Yuan 等 2025《Understanding and Mitigating Numerical Sources of Nondeterminism in LLM Inference》
实测仅改 batch / GPU 就让**准确率波动最多 9%、响应长度差 9,000 token**，根因是浮点非结合性；
Thinking Machines《Defeating Nondeterminism in LLM Inference》把批次相关内核行为列为主因；
多方一致：**80 层模型每层几个 ULP，足以在相当比例的 prompt 上翻转 argmax**。

**⇒ 旧数值门（对逐位相同的基线求 KL ≤ 0.0139 / top-1 ≥ 99%）对任何算术改动都不可能通过。**
`P453`/`P456` 的 FAIL 是**这道门的性质**，不是 DP4A / F16D 的质量。

**22. 撤回一条，并把门改造掉（`P469` / `P470` / `P471`）**

- **撤回**：第 16 条那个「`<..,16>` 被展平成 7087 条 / 408 个载入点」**是错的**。时间戳说明了原因：
  `.o` 是 **12:24**（pa7 重编），`fat.bin` 是 **12:23** —— dump 在重编之前，装的是 **pa8 的 printf 版**
  （`global_atomic_cmpswap_x2` 150 与 `buffer_wbinvl1_vol` 100 就是 printf 缓冲，我当时没认出来）。
  用 pa7 的真实 `.o` 重解：基线 **886** 条、`<..,16>` **890** 条；`v_fmac_f32` **120 vs 87+33 = 120**；
  `ds_read_b128` 都是 24；分数环都是 `v_mul_f32 + 7×v_fmac_f32`，只差末尾一条 `v_mul_f32`。**同一段算术。**
- **新门（`P470`）**：① 地板臂（同二进制同 argv 两容器）必须 **0.00000**；② **同噪控制臂**——一个可证等价的算术重排
  （本轮的 `CTLREAD`，ISA 与探针都证明只差 1e-7）给出**噪声地板 0.0411**；③ 候选 **≤ 地板 ⇒ 不可判**，
  **≥ 2× 地板才算有害**。按此，`DP4A` 0.0413 / `F16D` 0.0380 / `F16Q` 0.0448 **全在地板带内、彼此不可区分**。

**26. CPU 与 PCIe 的单件成本只差 5%——所以那条路不是杠杆（`P484`/`P485`）**

上一节说 CPU 段占 11.7%，自然会问：把 miss 改走 PCIe 会不会更便宜？**两个价都用本机实测，不估**：

| 来源 | 数 |
|---|---|
| 引擎自己的模型行（日志） | `the CPU pool takes 81 us per missed expert (38.6 GB/s of expert bytes), the link 13.2 GB/s -> pcie_frac 0.15` |
| 我们的窗口账（`P482`） | CPU 段 **4.64 ms/窗** ÷ `0.45–0.51 per layer-window × 48` = 21.6–24.5 个 ⇒ **190–215 µs/个** |
| PCIe 一侧算出来 | 一个专家 blob = 槽均价 **2.99 MiB**，链路 **13.2 GB/s** ⇒ **225 µs/个** |

**⇒ CPU 只比链路便宜 1.05–1.2×，不是模型假设的 2.9×。** 也就是说 `--pcie-frac` 往哪边调都不会改变 11.7% 这个数；引擎自适应出的 `0.15` 方向也没错。

**这条顺带把 `P416` 接上了**：那次判定「decode 不稳的主因是专家缓存命中率（corr 0.49），不是线程数」，当时只有相关性；现在有了机制和量级——命中率掉的就是这 11.7%（p90 17.11 ms 的窗口），而 `--pool-workers` 那条路 `P265` 早已判过无差。

**一个 2.3× 的缺口，我记成「未解释」而不是「已解释」**（`P485`）：模型说 81 µs、实测 190–215 µs。我试过用「10 worker × 24.5 个 ⇒ 2.45 轮/窗 ⇒ 199 µs」解释，但实测是 4.64 ms，差 23 倍——**轮数解释不成立**，除非中位样本里大量窗口的 CPU 段接近 0（p90 是 17.11 ms，分布确实双峰）。现有日志只有两个边缘分布、**没有「每窗口 CPU 专家数 × CPU 段」的联合分布**，所以拆不动。要拆得在窗口里抓逐请求行，而 `--pool-workers` 已判无差 ⇒ 不再投入。

**落成一句话给后续所有 R**：decode 的 CPU 段只能靠「少 miss」压，也就是**加槽**（`R104`）；这不是换路径的问题，是容量问题。

**27. 顺手抓到一个比目标更值钱的东西：`pass2` 比 `pass1` 快 3.7%，和重启无关（`P486`）**

|---|---|---|---|
| 2.5K | **−3.70%** | −3.44% | −4.43% |
| 8K | −0.56% | **−6.65%** | −0.31% |
| 16K | +0.03% | +0.09% | −0.31% |

**第一件事：2.5K 的系统性 3.7% 是「热身」，不是「重启」。** `ctl` 那一对中间根本没有重启，照样 −3.70%。所以**A/B 两臂的 pass 位置必须对称**：单 pass 窗口里每臂都是 pass1（像 A0 窗口的 ctl/b/c），偏差抵消；若一臂 1 pass、另一臂 2 pass，2.5K 上会凭空长出 3.7% 的假差异。**新窗口改成每臂 2 pass，正是为这个**——这条要写进所有后续窗口的协议里。

**第二件事：8K 那个 6.65% 是偶发双峰。** 同臂、同二进制，只差一次重跑，8K 就从 1339.1 掉到 1250.1，而中位只有 −0.31% ⇒ 约 1/6 概率命中的双峰事件，和 `generate.cpp` 注释里 R9700 的「queue placement 双峰」（一半启动把两条忙队列排到同一 pipe，4K 提示慢 13%）**同形**。

⇒ 我把 `STRATA_HIP_QUEUE_PRIME` 的判决**改判**：不是「无现象，关掉」，而是「**罕见但 5–7% 的双峰**，等窗口搭车时用 `=nn` 测」（候选 `hipk` 已备，默认不变）。

**这也回头解释了以前那些 +2% 的怪数**：它们大多出现在「某臂的第 1 pass 对上另一臂的第 2 pass」这种不对称里，而当时我们把 2.5K 的 +2% 一律写成「首条冷启动」。现在有数了：**3.7%**，而且它跟重启无关。

**28. 上一节那个「2.3× 缺口」是我的错，逐请求拟合把它结清了：95 µs/个，R² = 1.000（`P487`）**

上一节我用「CPU 段中位数 4.64 ms ÷ 每层窗专家中位数 0.45×48」算出 190–215 µs/个，并说这与引擎的 81 µs 差 2.3×。**这是把两个中位数相除——两个数来自不同请求，中位数不可除。** 正确做法是把两个量**在同一条请求上配对**，而 `decode timing` 那一行里正好两个都有（`CPU %.2f` 是 `d1.run/w`，源头是 `expert_source.cpp:5302 d.ms_run += ms(c3, c4)` 的真实墙钟；`CPU experts %.2f` 是 misses/(w×L)）。

对 342 个「至少 1 个 CPU 专家」的请求做最小二乘：

```
cpu_ms = 0.0954 × missed_experts + 2.69 ms      R² = 1.000
        (95 µs/个)                  (2.7 ms/请求的固定开销)
```

R² 这么高不奇怪：每个专家 blob 形状相同（gu 1280×2560、down 2560×640），CPU 侧成本几乎恒定。对照拟合 GPU 命中：**33 µs/件**，CPU/GPU = **2.9×**，与引擎注释里 38.6 GB/s 的口径一致。

**三条后果：**

1. **9 成数字对上**：模型 81 µs vs 实测 95 µs，差 17% ⇒ 引擎的 `pcie_frac` 自适应可信，**CPU 比 PCIe（225 µs/blob）便宜 2.4×**，「把 miss 改走 PCIe」这条不但不是杠杆，**方向还是错的**。`P484` 的结论方向对、数字错，已在原行里更正。
2. **`P485` 改判 DONE_NEG**：所谓「2.3× 未解释缺口」不存在，它是我的算术错。保留该行只为一件事——**方法教训：比率必须来自同一样本的配对，不能拿两个边缘分布的中位数相除。** 这一条今天已经在 `P482`（decode 分解）和 `P486`（pass 位置）上各犯过一次同类错误。
3. **miss 数是重尾**：每请求 p10 **0**、p50 **222**、p90 **7,102**、max **109,738**（58/400 请求为 0）。所以「CPU 段 11.7%」是中位数口径，**少数请求会被它吃掉几秒**；`R104` 加槽的收益要按重尾算，不能按均值算。

**给窗口的一条预注册**：如果 `kvg` 真的多给了槽，应当看到的是 **miss 数下降**，而不是「CPU 段均匀变快」；两者在重尾下不是一回事。窗口里我会同时抓 `CPU experts` 与 `CPU ms` 两列。

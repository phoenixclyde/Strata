# W1039 追加：DP4A 为什么反而慢

## 一、先把每一块的时间预算算清楚（源码常数，非估算）

常数：`CHUNK = 64` cells/块、`THREADS = 256`、`WARPS = 8`、`G = 12`（24 头 / 2 KV 头）、`HD = 256`、`NSC = HD/64 = 4`。
每个 query 的选择上限 `top_k = 2048` ⇒ `n_chunks = 32`；`n_kv_heads = 2` ⇒ **每个 query 有 64 个块**。

**量化阶段的形状**（`qsa_decode_attn.cu:234-247`）：`if (t < G * NSC)` = **只有 48 个线程**（256 的 19%），
每个线程串行跑 **64 次 amax + 64 次 `div+cvt`**（约 340–450 条指令）。其余 208 个线程在 `__syncthreads` 上等。

**分数阶段的形状**：8 个 warp 各分 8 个 cell；每个 lane 每 cell 算 12 个头：

| | 每 cell 每条 lane | 每块每 warp（8 cell） |
|---|---|---|
| 基线（`OPT=0`，REDUCE12 开） | 12×8 FMA = 96，加 K 反量化（12 头共用，≈20）、`reduce12` ≈25 ⇒ **≈130** | **≈1040** |
| `OPT=2`（dp4a） | 12×(`2×v_dot4` + `cvt` + `2×mul`) = 60，加 `reduce12` 25 ⇒ **≈85** | **≈680** |

⇒ dp4a 把分数段砍掉 **35%**，但它自己带来的量化段是 **≈400 周期**，而且被 `__syncthreads` 隔开、无法和分数段重叠：

`680 + 400 = 1080` vs 基线 `1040` ⇒ **净 −3.8%**（实测 attn **+6.8%**，同一个量级，方向一致）。

## 二、真正的病：量化被放在了「每块一次」，而块数是 64 倍冗余

同一个 query 的 3072 个元素（12 头 × 256 维），被**每个块各量化一遍**——32 个 chunk × 2 个 KV 头 = **64 次重复**。
量化总工作量 ≈ 64 × 48 线程 × 448 指令 = 138 万条 lane 指令，而分数段总共是 64 块 × 8 warp × 680 = 35 万条 warp 指令。
**准备工作的指令量是它要加速的那段的好几倍**——这就是"照理会快"和实测变慢之间的全部落差。

## 三、对照项目是怎么写的（本地源码 + 上网核）

**① iacop 的 `fattn-q8.cuh`（我们 §4.F 的手法来源）**：它也有一个 `flash_attn_tile_q8_quantize_Q_to_shared`，但形状完全不同：

```cpp
const int total_blocks = ncols * blocks_per_col;              // ncols 个 query × 每 query 8 个 32-值块
for (int block_idx = tid; block_idx < total_blocks; block_idx += blockDim.x * blockDim.y)
```

- **所有线程参与**（`blockDim.x*blockDim.y` 步长），不是 48/256；
- **一块覆盖 `nbatch_K` 个 key**（它的 tile 配置里 `nbatch_K` 通常 128–256），量化一次摊销掉的分数工作量是每块 `ncols × nbatch_K × 256` 个 MAC；
- 更关键：它的 KV 本来就是 **Q8_0 存着的**，K 侧根本不需要反量化，只用 `sdot4` 直接吃 int8。

我们这边：块只覆盖 64 个 cell、量化只摊销 64 个 cell、而且块数是 64 倍冗余。

**② skyne98 在同代卡上量过这件事（`fp32-vs-qdq-dot-gfx906`，2026-02-21）**：

| 场景 | fp32 | dot4 | 比值 |
|---|---|---|---|
| **热循环里现场 QDQ**（FP32 → int8 → dot4 → 反量化） | 5.95 TOPS | **2.00 TOPS** | **0.34×（慢 3 倍）** |
| 转换一次、复用多次（GEMM 形态） | 13.0 TOPS | **21.7 TOPS** | 1.67×（快） |

结论原文：*"If conversion/deconversion is paid every use, they do not [outperform fp32]"*。
**我们的写法正落在第一行**——每块量化一次、复用得极少。所以 +7% 不是"dp4a 没用"，是"我们付了热路径 QDQ 的钱"。

**③ 同一个站的 dot 吞吐测量**（`gfx906-dot4-dot8-exploration`）：`sdot4` 依赖链 21.7–22.3 TOPS、ILP4 43.0–44.4 TOPS，理论 26.5 TMAC/s
⇒ **硬件本身没打折**，v_dot4 确实是 4 MAC/指令。问题不在指令，在喂给它的数据。

**④ 顺带一条外证**：llama.cpp 上游社区实测（2026-10 构建，A100）`-ctk q8_0 -ctv q8_0` 在 64K 上下文的 decode 只有 f16 的 **56%**
——"量化 KV 一定更快"这个直觉在别的卡上也同样不成立。

## 四、如果真要救，改法与它的天花板

三个改法，效果按上面的预算推：

| 改法 | 量化段 | dp4a 分数段 | 相对基线 | 代价 |
|---|---|---|---|---|
| 现状 | 400 周期/块 · 64 块冗余 | 680 | **+4%** | — |
| ① 256 线程全参与量化 | 400/5.3 ≈ **84** | 680 | **−33%** | 改动小，但仍是 64 倍冗余 |
| ①+② `CHUNK` 64→256（摊销 ×4） | 84 / 块（块数 ÷4） | 680×4 | **−33%** | **CHUNK 是全局常数，基线也被改**，A/B 会串味 |
| ③ 独立 prologue 内核，每 query 量化一次 | ≈0（读 global） | 680 | **−45%** | 要一块 `nq×12×256 B` 的 scratch（16K query = 50 MB）+ 一次额外 launch |

**天花板**：分数段只占 attn 的一部分，attn 在 8K 占 16.5%、16K 占 17.2%。
即便分数段砍 45%，总 prefill 也就 **−3.5%**（16K）。而 `R104`（`--kv-grow`）一次能动 **770+ 专家槽、约 +10%**。
⇒ **不建议继续投 B1/B2**；把机制写进账本，判 DONE_NEG 收口。

## 五、这一轮学到的判据（写进方案）

> **在 gfx906 上把 dot4 引进热路径之前，先算净节省：每 8 个 MAC 只省 3 条指令。**
> 8 MAC = 2 条 `v_dot4` + 3 条收尾（`cvt` + 2 个 `mul`，把 int32 累加和两个 scale 乘回 float）＝ 5 条；
> 基线是 8 条 `fma`。**4× 的算术密度，被"每头一次收尾"吃回到 1.6×。**
> 再把量化成本摊进去：一个 cell 只省 36 条（12 头 × 3），而每块 448 条的量化摊到 8 个 cell 上是 **56 条/cell** ⇒ 净 **+20 条/cell**，
> 与实测 +6.8% 同量级。
>
> 两条推论，下次直接套：
> ① **收尾能不能省**？`dot8_dp4a` 里 `(float) acc * (qs * ks)` 是每头每 cell 一次；若把 12 个头的 acc 先加总再乘（数学上不等价，
> 因为每头 qs 不同）或把 qs 融进 k scale（可行：qs 是每 64 值一个的常数），就能把这 36 条压到 ~3 条。
> ② **量化摊销比**：量化一次要能被 ≥4 个"用到它的 cell"共享才划算（skyne98：摊薄 1.67×，热路径 0.34×）。
> 我们每块量化一次、每块只 64 个 cell、且**每个 query 有 64 个块各做一遍** ⇒ 摊销没发生。

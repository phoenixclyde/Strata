## 1 重排原则（为什么这个顺序）

1. **先修"判据不可信"的项**：一个结论如果连"用什么数判"都没统一，再测也是白测。
2. **再做"从未测过"的项**：那些不是"测了没用"，是"根本没测"。
3. **最后才碰"改约束"**（换位宽／换硬件／降上下文）：代价最大，且会动质量线，必须放在最后。
4. 每一轮必须**先写判据、再跑**；判据里必须含"停机条件"（什么结果等于直接放弃）。

**现行（2026-11-01 起，AUDIT16 后）**：上面四条是历史沿革；**当前按 §6.5 顶部的四条权重排序**
（①可达性 → ②判据强度 → ③成本 → ④战线集中）。三个直接后果：

- **先问"这个开关在二进制里存在吗"**（AUDIT16 P0-4 的教训：P112 记着 MMQ 已采纳，实际 `PREFILL_MMQ=OFF`）；
- **相位表 > 总量**：总量噪声 3.9–10.8%，而相位复本极差 0.2%（P114 的方法论）。任何 <3% 的总量结论不许写"提升"；
- **warm 不入表**：重启后前两个请求是异常点（W844 warm0 +32%），A/B 只能用 `rep0` 起的数据（`P231`）。

## 4 执行记录

### 4.1 P0-a　`--spec-min-p` / `--pcie-frac` 同实例重判（2026-10-31 11:42–11:48）

**方法（与旧法的三处不同）**

1. **单次启动**，`STRATA_DECODE_TIMING=1`，用 `strata_tune` **逐请求**下发参数（`serve/server.py:1446-1452`）⇒ **换臂不重启**，
   跨容器那 12–16% 的漂移在这个设计里根本不存在。
2. **6 组随机区组**：每块里每个取值各出现一次，块内顺序随机 ⇒ 块内配对，整机漂移对消。
3. 判据用**声明的那一列** `tokens/win ÷ ms/win`（引擎自打），不做任何换算。

每臂 6 条 512-token 贪心，共 36 条。

| 轴 | 取值 | median tok/ms | ms/win | 配对 Δ（中位） | 为负的块 |
|---|---|---:|---:|---:|---:|
| `spec_min_p` | 0.50 | 0.0527 | 46.81 | −1.4% | 5/6 |
| | **0.70（生产）** | **0.0539** | 42.84 | — | — |
| | 0.85 | 0.0536 | 40.11 | +0.0% | 3/6 |
| `pcie_frac` | 0.10 | 0.0539 | 43.13 | −1.5% | 4/6 |
| | **0.20（生产）** | **0.0548** | 44.93 | — | — |
| | 0.30 | 0.0531 | 46.79 | −4.4% | 4/6 |

**噪声底盘：每臂 max/min 离散 3.9% – 10.8%，中位 6.0%。**

**判词（三条，按审计口径写）**

1. **没有任何邻居优于生产值** —— 最好的也是 0.0%（`spec_min_p 0.85`），其余全为负。
2. 但**效应全部 ≤4.4%，小于 6.0% 的噪声底盘** ⇒ 结论只能是 **不可判（UNRESOLVED）**，
   **不能**写"生产值最优"。⇒ 这两项从旧方案的"已结清 / 最优点"**改判为"保留现值、不再花窗口重测"**。
3. 这条同时**作废旧数字**：`0.50 只高 0.4%`、`0.20 是全局最优` —— 两个数都小于噪声底盘，当初就不该被写出来。

**噪声是从哪来的（本轮顺带量到，比上面的结论更值钱）**

同一个 prompt、同一 `seed`、`temperature=0`，**36 条 512-token 生成给出 36 个不同的 sha**（AUDIT13 更正：原写 33/33。原始 `w832_tune_results.jsonl` 是 36 条、36 个不同 sha，且其中 3 条只生成 446/318/420 token，被当成 512-token 计入上表） —— 连两次同为 `0.70` 的也不一样。
⇒ 这个引擎的**生成路径本身不可复现**（与 W816 的"生成不可复现"一致，也与 W824 §10 的"teacher-forced logprob 可复现"不冲突）。
不同 token 序列 ⇒ 接受率不同 ⇒ 每条的 `tok/win` 不同 ⇒ 6% 噪声。

**要压低这个噪声只有两条路**：把每臂样本加到 20 条以上（SEM 降到 ~1.5%），
或改用**与内容无关的量**（如每窗口成本 `ms/win`、或 teacher-forced 固定序列）。**加臂没用，只会把噪声一起平均掉。**

**成本**：停机约 5 min（288 s 载入）+ 测试 6 min；脚本内置"无论成败恢复生产"，已自动恢复。

**对方案的影响**：参数层的这两项到此**关账**（不是"证明最优"，是"低于可分辨门限，保留现值"）。

### 6.1 原则（先读这段，否则会重做已经做过的）

1. **配置级优先于源码级**：能在 env/args 上一次 A/B 判掉的（6.4 的 #3073、#4781），不要先去改 kernel。
2. **别人的倍数是别人的卡**：gfx1151/gfx12 的"bitwise +1.9%"在 gfx906 上是 **0（decode）/ −4.5%（prefill）**（W835 §11 实测）。
   ⇒ 任何来自别的架构的开关一律按"未知"处理，**先单项测、禁叠加**。
3. **gather 型 vs dense 型**：KI 的 DEAD-ENDS 已证"gather 路径 ALU 已满速，换 dot2/dp4a 不产生结果"。
   ⇒ 换指令前先做 **roofline**（该 kernel 达到 fp32-FMA 记录速率的百分比），否则可能白干一整轮。
4. **probe GO ≠ serving GO**（KI 的 T-1 反例：+15–18% 是冷启动误读）⇒ 任何探针收益都要过 serving 门。

### 6.13 干扰纪律（W860 新增，`P242`）

**硬约束**：单卡 MI50、模型驻留 **33.5 / 34.3 GB** ⇒ **起不了第二个实例**。
所以"引擎级 A/B"在生产机上只有一种形态：**停服 → 换二进制/env → 重启 → 测 → 再重启恢复**。
而机主随时可能在用这个模型（本轮 03:26–03:36 就被我堵了约 10 分钟）。

| 类别 | 允许吗 | 说明 |
|---|---|---|
| 读日志 / 读源码 / 解析已有数据 | ✅ 随时 | 零干扰。`albus/w860/real_traffic.py` 即此类 |
| CPU-only 构建（`ninja`/`cmake`/codegen） | ✅ 但须限核 | `nice -n 19` + `taskset` 限 4–8 核 + `ionice -c3`；**跑完即停** |
| `--rm` 容器里的探针/编译 | ✅ | 不挂 `/data`、不占 GPU 或只占数秒 |
| `docker stop/start/rename` 生产容器 | ❌ 需事先获批 | 每次重启 = 4–5 分钟模型重载 |
| 换 `/data/bin/strata-*` / 改 config 的 `exe`/`env` | ❌ 需事先获批 | 同上，且改完必须恢复并复核 |
| 微基准占 GPU | ⚠️ 慎 | 显存只剩 ~800 MiB，大分配会抢走生产的余量；只做 ≤64 MB 的短跑 |

**窗口申请模板**（写清这四项再问）：

```
要停多久：约 N 分钟（含每次 4–5 分钟重载 × 重启次数）
验什么：<一个窗口里合并的 2–3 件事>
怎么回滚：<镜像/二进制/表/config 的确切回滚路径>
窗口后自查：/health ok + TIP-OK + restarts=0 + 记 started
```

**这一轮的直接教训**：R4 的两轮 A/B 一共触发了 **4 次 engine started**（03:16/03:20/03:26/03:31）
= 4 次重载 ≈ 16 分钟空窗。**下次一个窗口验多臂，不要为每臂单独重启。**
